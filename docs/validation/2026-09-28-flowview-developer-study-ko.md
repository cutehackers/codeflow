# FlowView 실제 개발자 평가 기록지

- 기준: [Requested Flow 관문과 실행 타임라인 §16.59](../design/specs/2026-09-18-flowsequence-requested-flow-hierarchy-ko.md)
- 상태: 평가 준비. 참가자 관측 결과와 배치 비교 결과는 아직 없다.
- 목적: 개발자가 요청 흐름을 따라 실제 코드와 확인되지 않은 관계를 올바르게 이해하는지 확인한다.

## 준비

1. 저장소 루트에서 `python3 scripts/prepare-flowview-developer-study.py --check`로 네 사례가 분석되는지 확인한 뒤, 옵션 없이 실행한다. 스크립트가 실제 분석 API로 저장한 각 `viewId`와 접속 URL을 출력한다. 참가자가 과제를 수행하는 동안 터미널을 열어 둔다. 종료하면 임시 저장소와 저장 분석이 지워지므로 참가자 기록에 필요한 ID와 관찰 내용은 종료 전에 남긴다. 동일 사례의 현재 배치와 대안 배치는 **같은 저장 결과**를 사용한다. 정적 시안이나 자동 브라우저 검사 결과를 참가자 결과로 대체하지 않는다.
2. 참가자에게 소스의 정답과 조작 경로를 미리 보여 주지 않는다. 과제마다 시작 화면, 화면 크기, 비교 기준과 타이머 시작·종료 지점을 기록한다.
3. 배치 비교에서는 참가자별 제시 순서를 바꾸고, 양쪽에 같은 요청·코드·과제를 사용한다. 기본 배치는 저장 화면 URL, 대안 배치는 같은 URL에 `studyLayout=code-focused`를 추가해 연다. 대안은 데스크톱에서 작업 영역을 2열로 두어 코드 폭을 넓히고 관계 맥락을 아래로 옮긴다. 1150px 이하에서는 두 배치가 사실상 같으므로 배치 비교 대상으로 쓰지 않는다. 대안에서도 실제 코드를 열고 선택·복귀할 수 있는지 먼저 확인한다.
4. 참가자에게 생각을 말하면서 조작하도록 요청한다. 진행자는 답이나 버튼 위치를 가르치지 않고, 막힌 지점과 조작 실패를 기록한다.

## 과제와 정답 기준

| 과제 | 참가자에게 제시할 말 | 준비할 실제 저장 결과 | 정답·관찰 기준 |
| --- | --- | --- | --- |
| 1 | “카드와 계좌이체 중 어느 코드가 실행되는지, 두 경로가 어디에서 다시 만나는지 코드로 보여 주세요.” | `checkoutPayment`의 `if (card)`와 `chargeCard(amount)`, `transferFunds(amount)`, `receipt(payment)`가 있는 결제 흐름 | 참은 카드, 거짓은 계좌이체이며 두 경로는 하나의 `receipt(payment)` 처리로 합류한다. 공통 처리를 두 번 실행하는 것으로 설명하면 오해로 기록한다. |
| 2 | “다른 파일에서 실행되는 처리의 코드를 연 다음, 읽던 관문으로 돌아와 주세요.” | `checkoutCrossFile`에서 `payment-helper.ts`의 `evaluatePayment`를 호출하는 흐름 | 참가자가 다른 파일·심볼·해당 코드 줄을 찾고, 복귀 후 출발 관문과 선택 상태를 유지하는지 확인한다. |
| 3 | “이전 분석과 현재 분석에서 바뀐 규칙을 찾고, 각각 근거가 되는 코드 줄을 보여 주세요.” | 실제 소스를 `setStatus('completed')`에서 `setStatus('confirmed')`로 바꾸기 전후에 저장한 두 분석 | 변경 설명과 양쪽 소스 줄이 맞는지 확인한다. 코드가 화면 밖으로 밀리거나 읽던 위치를 잃으면 기록한다. 주석만 추가한 분석은 규칙 변경 사례로 쓰지 않는다. |
| 4 | “이 흐름에서 코드가 연결된 사실과 실행 여부를 아직 알 수 없는 부분을 구별해 설명해 주세요.” | 콜백 전달을 분석했지만 호출은 확인되지 않은 `Service.run` 흐름 | 콜백 코드가 전달된 근거와 콜백이 실제 실행됐다는 근거가 없다는 점을 구별한다. 미확인 연결을 확정된 실행 순서나 완료 결과로 말하면 오해로 기록한다. |

위 사례의 원본 생성 경로는 [`saved-flowview.spec.ts`](../../web/live-comprehension-workspace/tests/saved-flowview.spec.ts)에 있다. 테스트는 분석·저장·화면 조작의 자동 검증에만 사용한다. 평가 전에는 참가자용 저장 결과를 독립적으로 만들고, 참가자가 연 코드가 그 저장 결과의 snapshot에 속하는지 확인한다.

정답과 근거 도달은 각각 `성공`·`실패`·`부분`으로 기록하고, 실제 답과 연 파일·줄을 메모한다. 복귀를 요구하지 않은 과제는 `해당 없음`으로 둔다. 시간은 과제 문장을 읽은 직후부터 참가자가 답변 또는 포기를 선언할 때까지 잰다. 진행자의 힌트가 들어가면 시점과 내용을 별도로 적는다.

## 판정

과제별 원문 답, 실제로 연 코드, 시간, 복귀 상태와 오해를 두 배치에서 대조한다. 차이가 있다면 어떤 정보나 조작 때문에 생겼는지 참가자 기록에 근거해 설명한다. 참가자 결과가 없거나 대안 배치의 실제 코드 탐색이 불가능하면 AC-14와 UX-AC-15·17의 사용자 검증을 완료로 표시하지 않는다. 관찰값 없이 합격 수치나 디자인 우위를 만들지 않는다.
