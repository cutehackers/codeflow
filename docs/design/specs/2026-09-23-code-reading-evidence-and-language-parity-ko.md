## 1. 문제와 목표

기본 탐색 항목을 눌렀을 때 실제 코드가 정확하게 보이는지 아직 실사용 증거로 확인되지 않았다. 수집 단계의 문장 누락, 잘못 연결한 실행 관계, 요약 중 소스 근거 손실은 모두 같은 사용자 실패로 이어진다. 언어를 늘릴 때마다 같은 흐름 의미 규칙을 다시 구현하면 언어별 결과가 달라진다.

- INT-01: 사용자가 요청한 구현을 실제 코드와 확인된 실행 관계로 끝까지 읽게 한다.
- GOAL-01: 사용자는 기본 탐색 항목을 선택할 때마다 같은 분석의 정확한 코드와 주변 문맥을 본다.
- GOAL-02: 사용자는 Dart 흐름에서 결과에 영향을 주는 중간 처리와 확인된 분기·비동기 관계를 읽는다.
- GOAL-03: 사용자는 상세 단계를 잃지 않는 짧은 읽기 경로로 흐름을 이해한다.
- GOAL-04: 사용자는 지원 언어가 달라도 같은 근거 규칙으로 FlowView를 읽는다.

## 2. 범위

포함: CodeView 표시 가능성의 저장 전 검증과 실제 화면 회귀, Dart의 실행 문장·관계 근거, 1:N 포함의 검증, 공통 단계·관계·소스 근거 계약을 사용하는 TypeScript와 Go의 독립적인 읽기 경로.

제외: 모든 문장을 무조건 화면에 노출하는 정책, 근거 없는 100% 실행 경로 주장, 언어 독립 파서, Kotlin·Swift 지원, 새 화면 설계, 기존 계약의 수정·대체·상태 변경.

## 3. 주체와 전제

- 주체: 자연어 요청으로 FlowView를 여는 개발자.
- 전제: 요청한 흐름이 선택됐거나 직접 지정됐고, 분석할 소스 snapshot에 접근할 수 있다.
- 기존 계약과의 관계: 이 계약은 기존 공개 동작을 재정의하지 않는다. 실제 CodeView 표시, 수집 품질, 언어 간 동일 기준을 별도 결과와 검증 단위로 다룬다. 기존 계약 파일과 VS 파일은 변경하지 않는다.

### 기존 계약과 이 계약의 책임

| 기존 공개 동작의 기준 | 이 계약에서 추가하는 결과 |
|---|---|
| 2026-09-21 FA-07·FA-11·FA-15·FA-18: 항목에서 정확한 CodeView 코드로 이동 | VS-01이 **실제 View의 모든 기본 항목을 순회**해 표시 성공·실패를 항목별로 남긴다. 코드 표시 의미는 기존 계약을 따른다. |
| 2026-09-21 FA-17과 §12.4.2: 대표 코드 검증 실패 시 저장 중단 | VS-01은 이 동작을 회귀 검증한다. 새 실패 상태나 저장 규칙을 정의하지 않는다. |
| 2026-09-18 AC-04·05·07 및 2026-09-21 FA-07·FA-13: 관문, 자식, 저장·MCP의 관계와 코드 이동 | VS-04는 **누락됐던 중간 처리도 자식에서 읽을 수 있는지** 확인한다. 기존 관문 의미와 호환 계약은 그대로 따른다. |
| 2026-09-21 §2: TypeScript·Go 실행 관계 확장은 해당 계약 범위 밖 | VS-05·06이 각 언어의 별도 확장 결과를 소유한다. 기존 계약의 Dart 수용 기준을 바꾸지 않는다. |

겹치는 수용 기준은 새 공개 규칙이 아니라 회귀 의무다. 상충하는 결과가 나오면 위 기존 계약을 기준으로 판단하며 이 계약만으로 그 조항을 바꾸지 않는다.

## 4. 확인된 근거와 가정

- 이전 조사에서는 실제 Molycard View의 67개 항목에 소스 줄이 표시됐으나 정확한 줄 강조는 17개였다. 다른 실제 메서드 분석은 실패했다. 이는 2026-09-23 이전 관찰이며, 현재 작업 트리가 변하고 있으므로 구현 착수 시 같은 공개 경로에서 재현 여부를 확인한다.
- 기존 2026-09-21 계약은 대표 코드 범위를 열 수 없으면 새 View를 저장하지 않도록 요구한다. 이번 계약은 그 결과를 항목별 화면 조작으로 확인한다.
- ASM-01: 언어별 parser는 해당 언어 문법을 이해해야 한다. 공통화 대상은 문법 parser가 아니라 검증 가능한 단계·관계·소스 근거와 이후 처리다. 거짓이면 TypeScript·Go fixture의 코드 범위와 관계 일치 검증에서 드러난다.

## 5. 불변식

- INV-01: 기본 항목은 같은 snapshot·computed basis의 실제 심볼과 관련 문장 범위를 열어야 한다.
- INV-02: 대표 코드가 열리지 않으면 정상 View를 저장하거나 이전 View를 교체하지 않는다. 비대표 연결의 누락은 마지막 확인 지점의 분석 경계로 남긴다.
- INV-03: AST로 확인하지 못한 실행 순서, 분기 합류, `await` 성공 복귀를 만들지 않는다.
- INV-04: 상세 문장은 요약에서 삭제하지 않는다. 상위 항목에서 감추더라도 확인 가능한 자식 단계와 코드 근거로 접근할 수 있어야 한다.
- INV-05: 언어별 adapter는 언어 문법과 프레임워크 사실을 수집한다. 공통 검증, 의미 단계, 요약, 저장, 화면 계약은 같은 기준을 사용한다.
- INV-06: 기존 source read-only, 인증, secret redaction, 과거 View 복원, immutable View와 공개 protocol 호환성을 유지한다.
- INV-07: 폐기된 `architecture` 값을 새 분석이나 화면 판단 근거로 되살리지 않는다.

## 6. 사용자 흐름과 실패

1. 사용자가 요청을 분석해 FlowView를 연다.
2. adapter가 실제 문장·직접 관계·소스 범위를 수집하고, 공통 검증과 curator가 읽기 경로를 만든다.
3. 저장 전에 대표 항목의 소스 표시 가능성을 확인한다.
4. 사용자는 상위 항목과 상세 단계를 선택해 같은 snapshot의 정확한 코드와 주변 문맥을 본다.
5. 코드 범위를 확인할 수 없으면 원인과 마지막 검증 지점을 보고, 이전 View와 읽기 위치는 보존된다.

## 7. 결정

| ID | 결정 | 이유 |
|---|---|---|
| D-01 | CodeView에서 실제 소스가 열리는 결과를 항목별 수용 조건으로 둔다. | 데이터 필드나 테스트 통과만으로 화면의 코드 표시를 보장할 수 없다. |
| D-02 | 동작을 바꾸는 문장은 수집하고, 실행 관계는 확인된 경우에만 확정한다. | 첨부안의 무조건적 100% 수집·인입 간선 규칙은 비실행 선언과 예외·취소 경로까지 정상 실행으로 오해시킬 수 있다. |
| D-03 | 언어별 AST 해석은 adapter에 두고 이후 계약을 공유한다. | 문법 차이는 피할 수 없지만 의미 검증과 화면 동작의 중복은 줄일 수 있다. |
| D-04 | TypeScript와 Go는 별도 사용자 결과로 검증한다. | 한 언어의 성공을 다른 언어의 성공으로 간주하지 않기 위해서다. |

## 8. 기능 수용 기준

- FA-01: 새 View의 모든 기본 탐색 항목을 선택하면 설명과 같은 심볼·문장이 주변 문맥과 함께 CodeView에 열린다.
- FA-02: 대표 코드가 열리지 않으면 구조화된 분석 실패를 반환하고 새 TaskView를 저장하지 않는다.
- FA-03: Dart의 결과를 바꾸는 선언·대입·변환·호출·반환이 정확한 소스 범위와 함께 전달된다.
- FA-04: 조건·반복·예외·취소·`await`의 연결은 확인된 경우만 확정 실행으로 전달된다.
- FA-05: FlowSequence 상위 항목의 상세 단계는 누락 없이 접근 가능하고 각 단계에서 실제 코드로 이동한다.
- FA-06: TypeScript 요청은 같은 근거 계약으로 실제 CodeView 읽기 경로를 만든다.
- FA-07: Go 요청은 같은 근거 계약으로 실제 CodeView 읽기 경로를 만든다.
- FA-08: FlowView, 저장 후 재조회, MCP compact 응답의 항목·관계·소스 상태가 같은 snapshot에서 일치한다.

FA-01·02·08은 위 기존 공개 동작의 회귀 검증이다. FA-05의 관문·자식 의미도 기존 계약을 따르며, 새 검증 대상은 VS-02에서 보존한 중간 처리의 접근성이다.

FA-06의 최소 검증 범위는 조건·변환·비동기 실패 경계를 가진 TypeScript 함수와 이벤트 진입점이 있는 TSX 컴포넌트다. 두 사례 모두 진입부터 결과 또는 확인 가능한 분석 경계까지 CodeView로 읽는다. FA-07의 최소 검증 범위는 receiver 메서드의 조건·호출·오류 반환과 같은 이름의 다른 receiver가 있는 Go 사례다. 정상 결과와 오류 경계를 각각 코드로 읽는다. 이 범위를 넘어서는 문법·프레임워크는 지원으로 선언하지 않는다.

## 9. 품질과 검증

각 VS는 변경 언어의 adapter 테스트, Go 경계 테스트, 저장 왕복, UI 선택 테스트와 실제 공개 경로 검증 중 적용되는 검사를 기록한다. 전체 완료 시 `make fmt`, `make vet`, `make check-naming`, `make test`, `make test-flowview`, `make test-ui`, `make build`와 변경한 언어 adapter 테스트를 실행한다. 저장 또는 MCP 계약을 변경한 VS는 호환성 왕복과 race 검사를 포함한다. Molycard 실제 요청은 사용자 조작으로 각 기본 항목의 코드 표시를 확인한다.

## 10. Open Decisions

없음. 새로운 protocol 필드나 migration이 필요해지면 기존 consumer와 저장 데이터를 조사하고 별도 계약 개정으로 결정한다.

## 11. 완료 조건

FA-01~08의 현재 실행 증거가 있고, 각 VS의 검토·승인·검증 상태를 독립적으로 기록한다. 기존 계약의 완료 여부는 이 계약만으로 변경하지 않는다.
