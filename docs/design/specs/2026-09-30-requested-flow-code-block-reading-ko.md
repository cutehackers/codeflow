## 1. 문제와 목표

현재 개요는 `CodeReadingPath.nodes`의 각 문장을 나열하고 선택한 `stepId`를 기존 CodeFlowPanel에 전달한다. 중앙 패널의 읽기 단위는 여전히 선택한 frame과 문장이다. 선별 목록과 탐색 전환을 추가해도 처리 목적별 코드를 함께 읽는 경험은 생기지 않는다.

이 작업의 결과는 **처리 목적별 구간을 고르면 그 처리를 구현한 실제 코드 블록들을 중앙에서 읽고, 필요한 문장만 상세 탐색하는 FlowView**다. 개요 제목 변경, 항목 수 감소, 탭 추가, 주변 코드 줄 수 확대만으로 완료할 수 없다.

| 의도 | 목표 | 관찰할 결과 |
|---|---|---|
| INT-01 큰 흐름을 코드로 이해한다 | GOAL-01 시작부터 결과까지 목적별 코드를 읽는다 | 구간에 속한 여러 문장을 반복 선택하지 않고 실제 구현을 읽는다 |
| INT-02 요약의 근거와 예외를 확인한다 | GOAL-02 분기·인계·실패와 해당 코드를 찾는다 | 조건 결과, 구간 사이 관계, 미확인 연결을 구별한다 |
| INT-03 필요할 때 상세를 확인한다 | GOAL-03 코드 블록에서 문장별 탐색 후 돌아온다 | 출발 구간·블록·읽던 위치·비교 기준을 유지한다 |

기존 대화에서 목적·사용자·실패 원인·단순성 제약을 확인했다. ‘빠르다’는 처리 목적과 그 구현을 반복적인 문장 선택 없이 읽을 수 있다는 뜻이다. 시간 단축률이나 고정 구간 수는 요구하지 않는다. 부모 계약의 Approved는 Codify의 의도 확정 상태이며 제품 구현이나 티켓 승인을 뜻하지 않는다.

## 2. 범위와 기존 계약의 관계

이 문서는 기존 승인 계약의 미구현된 코드 블록 읽기를 전달하는 새 작업 계약이다. 기존 계약과 과거 티켓의 상태·완료 기록은 변경하지 않는다. 이 작업의 티켓은 이 문서만 직접 부모로 삼으며, 기존 계약은 사용자 결과와 보안·호환성의 기준으로 상속한다.

- 범위1: 기존 분석에 처리 구간, 실제 코드 블록, 근거 있는 구간 관계를 추가하고 저장·HTTP·MCP·FlowView까지 전달한다.
- 범위2: 에이전트에 요청하면 기존 분석 이후 구간 제안·검증·새 View 저장·해당 View 열기까지 이어진다. 사용자가 단계 ID나 JSON을 직접 조립하지 않는다.
- 범위3: 개요 화면의 중앙 읽기 단위를 코드 블록으로 바꾸고 기존 문장별 탐색을 별도 모드로 보존한다.
- 범위4: 브라우저 직접 분석에 구간 생성자가 없으면 개요 미생성을 명시한다. 기존 문장 화면을 새 개요처럼 보여 주지 않는다.

새 parser, 범용 자동 묶기 엔진, 별도 모델 서비스, 별도 저장소, watcher, 과거 버전 비교 연구, 다른 기기 간 상태 동기화는 추가하지 않는다. 기존 에이전트가 의미를 제안하고 기존 서버가 근거를 검증한다. 브라우저만으로 에이전트를 자동 호출하는 기능은 현재 존재하지 않으며 이 작업이 이를 제공한다고 주장하지 않는다. 기존 상위 계약 전체의 완료와 이번 작업의 완료는 구별한다.

[최소 구현 계획](../2026-09-29-requested-flow-overview-implementation-ko.md)의 ‘기존 CodeReadingPath 직접 표시’는 이 작업의 완료 기준이 아니다. [읽기 회복 초안](2026-09-29-requested-flow-reading-recovery-ko.md)의 별도 영구 상태 저장과 과거 버전 비교도 이 작업의 선행 조건이 아니다.

## 3. 사용자와 전제

사용자는 요청한 코드 동작을 이해하려는 개발자다. 기존 로컬 인증과 프로젝트 읽기 권한을 사용한다. 확정된 요청·진입점, 같은 snapshot의 단계·간선·소스 문맥을 입력으로 사용한다. 코드를 바꾸거나 실행 기록을 수집하지 않는다.

발견1: `web/flowview/src/stores/flowNavigation.ts`의 `requestedFlowOverview`는 노드별 항목을 만든다.
발견2: `RequestedFlowOverview.svelte`는 단일 step을 선택하고 `CodeFlowPanel.svelte`는 선택 frame의 코드를 표시한다.
발견3: 일반 `/api/task/view`는 현재 개요를 생성하지 않으며 별도 선별 요청이 새 View를 만든다. 검증된 View ID를 실제로 여는 것까지 전달 책임에 포함해야 한다.

## 4. 화면 계약

### 4.1 첫 화면

유효한 Requested Flow Overview가 있고 보존된 읽기 상태가 없는 View는 다음 구성을 기본으로 연다. 보존된 상태가 있으면 마지막 탐색 모드·선택·위치를 우선 복원한다.

| 위치 | 표시 내용 | 기본으로 표시하지 않는 내용 |
|---|---|---|
| 흐름 탐색 | 요청의 시작, 목적별 처리 구간, 확인된 관계·조건 결과·경계 | 모든 frame 또는 문장 목록 |
| 중앙 읽기 영역 | 선택 구간의 목적 설명과 실제 코드 블록들 | 선택 문장 한 개를 중심으로 한 기존 frame 카드 |
| 상세 진입 | 블록의 실제 문장 선택과 ‘문장별 탐색’ 동작 | 개요를 읽기 위해 필수로 거쳐야 하는 문장 선택 절차 |

첫 구간의 코드는 별도 클릭 없이 열린다. 구간을 바꾸면 해당 구간의 코드 블록들을 함께 제공한다. 서로 다른 파일의 코드는 파일·함수·행 범위를 구별한 별도 블록으로 표시한다. 여러 블록을 가상화하더라도 존재와 접근 경로는 유지한다.

### 4.2 코드 블록

코드 블록은 같은 파일의 실제 연속 소스 범위다. 구간에는 여러 블록이 들어갈 수 있다. 한 블록에 여러 검증된 문장이 있으면 함께 읽고 각각 상세로 이동할 수 있다. 불연속 범위를 한 코드처럼 붙이거나 파일 사이를 합성하지 않는다.

구간에 포함된 문장과 이해를 위한 주변 문맥을 시각적으로 구별한다. 주변 문맥을 포함 단계나 실행 근거로 승격하지 않는다. 블록 범위는 서버가 검증된 단계 범위와 같은 snapshot의 소스로 결정한다. 제안자가 임의 코드 본문을 제공할 수 없다. 긴 블록은 생략 구간과 펼침을 표시하되 해당 구간의 핵심 구현을 첫 화면에서 전부 숨기지 않는다.

‘정확한 문장 강조’는 유지하지만 화면의 읽기 단위를 한 문장으로 제한하지 않는다. 한 문장만으로 완결되는 구간은 허용하되 전체 분석의 각 문장을 이름만 바꿔 구간으로 만들면 실패다.

### 4.3 구간을 나누는 기준

에이전트는 원문 요청과 실제 소스를 읽고 하나의 처리 목적으로 설명되는 단계들을 제안한다. 요청의 진입 사건에서 각 계층의 처리와 인계를 거쳐 결과 또는 확인이 끊기는 지점까지 설명한다. 중요한 판단, 결과를 바꾸는 상태 변화, 외부 효과, 실패·종료를 숨겨 합치지 않는다.

같은 파일·함수·인접 행이라는 이유만으로 목적을 정하지 않는다. 반대로 함수가 다르다는 이유만으로 같은 목적의 구현을 서로 무관한 구간으로 강제 분리하지 않는다. 함수·파일 경계는 블록 경계와 출처 표시에 사용한다. 고정 구간 수는 없다.

## 5. 데이터와 전달 계약

기존 `SemanticMapIR`, `FlowSequence`, `CodeReadingPath`는 보존한다. 저장 View에 선택적 `requestedFlowOverview` 객체를 추가한다. 기존 필드의 의미와 schema ID를 바꾸지 않는다. 새 객체는 자체 schema version 1을 사용한다. 아래는 필수 의미이며 소비자 검사에서 직렬화 이름·schema 파일을 함께 확정한다.

| 정보 | 필수 내용 |
|---|---|
| 분석 기준 | 원문 요청, snapshot ID, computed basis ID, schema ID·version |
| 처리 구간 | 구간 ID, 구체적인 목적 설명, 선택 이유, 포함 step ID 목록, 블록 목록, 한계 |
| 코드 블록 | 블록 ID, 파일·함수 출처, 연속 소스 범위, 포함 step ID와 정확한 강조 범위. 본문은 기존 snapshot 소스를 참조 |
| 구간 관계 | 출발·도착 구간 및 step, 순서 있는 실제 edge 참조, 조건 결과, 관계 종류 |
| 한계 | 마지막 확인 step, 미확인 대상과 이유, 요약할 수 없는 처리와 상세 진입 |

결정1: 에이전트의 구간 제안은 사실이 아니다. 서버는 포함 step·소스 범위·관계·분기 참조를 검증한다. 제목의 의미 적절성까지 자동으로 증명했다고 주장하지 않는다.
결정2: 새 개요 제출은 기존 선별 경로와 같은 인증·검증·불변 저장 흐름을 재사용한다. 개요용 MCP 입력과 HTTP 진입은 동일한 서버 검증을 호출하고 검증된 새 View ID를 반환한다. 기존 reading-path 입력·응답은 유지한다.
결정3: MCP full·compact, HTTP 응답과 저장 복원은 구간·블록·step·관계·한계를 동일하게 보존한다. compact는 코드 본문을 줄일 수 있으나 참조를 제거하지 않는다.

전달 순서: **원문 요청 → 기존 분석 → 에이전트의 구간·블록 제안 → 서버 검증 → 새 immutable View 저장 → 반환 View ID 열기 → 블록 읽기**. 생성 중인 중간 분석 View를 완성된 개요 결과로 열고 종료하면 실패다.

UI는 구간 소속이나 실행 관계를 추론하지 않는다. `CodeReadingPath`를 새 개요로 자동 변환하지 않는다. 배열 순서와 소스 행 순서만으로 실행 화살표를 만들지 않는다.

## 6. 분기와 상세 왕복

구간 내부와 구간 사이의 분기·합류·반복·실패를 보존한다. 접힌 경유 코드에도 결과를 바꾸는 분기와 미확인 연결이 있음을 보여 준다. 확인된 연결만 진행으로 표시하며 부분 분석을 완료된 실행으로 표현하지 않는다.

블록에서 문장을 선택해 상세로 이동하면 해당 step이 선택된다. 구간 수준에서 상세로 이동하면 그 구간의 검증된 진입 step을 사용한다. 명시적으로 선택한 문장이 있으면 그것이 이전 상세 모드의 마지막 선택보다 우선한다. 개요 복귀 시 구간·블록·펼침·스크롤·초점·baseline을 복원한다. 같은 세션에서 View를 다시 열 때도 유지한다. 기존 복원 기능을 재사용하며 영구 저장 확대는 요구하지 않는다.

## 7. 실패·보안·호환성

| 상황 | 관찰할 결과와 저장 동작 |
|---|---|
| 요청·진입점 또는 기존 분석 검증 실패 | 기존 오류를 표시하고 현재 View·선택·baseline을 유지한다 |
| 구간 참조, 코드 범위, 관계 또는 snapshot 불일치 | 후보 개요를 거부한다. 개요 View를 저장하지 않고 유효한 원본 분석을 보존한다 |
| 일부 후속 연결 미확인 | 검증된 구간과 경계를 함께 제공하며 성공·완료를 추정하지 않는다 |
| 새 브라우저 분석에 생성자가 없음 | ‘처리 구간 개요가 생성되지 않았습니다’와 이유를 표시하고 사용자가 명시적으로 문장별 탐색을 열 수 있게 한다. 기존 열린 View는 자동 교체하지 않는다 |
| 과거 View 또는 CodeReadingPath만 있는 View | 기존 상세 또는 선별 지점 읽기를 보존하고 목적별 개요와 구별한다. 열기만으로 분석·변환·재저장하지 않는다 |
| 저장된 새 개요의 version·참조가 유효하지 않음 | 이유를 표시하고 상세 접근을 제공한다. 저장 원본을 고치지 않는다 |
| 재요청·취소·늦게 도착한 응답 | 실패한 요청과 이전 요청의 결과로 현재 선택을 덮어쓰지 않는다. 기존 요청 식별·취소 정책을 재사용한다 |
| 인증 실패 또는 소스 secret | 기존 인증과 단일 redaction 경계를 적용한다. 새 제목·설명·블록도 동일 규칙을 통과한다 |

새 개요 추가는 새 View ID를 만든다. 동일 ID의 내용을 수정하지 않는다. 화면 전환은 분석·저장을 실행하지 않는다. 임의 절대 경로와 다른 snapshot 소스를 블록의 본문으로 읽지 않는다. 비교 기준은 사용자 선택 없이 바뀌지 않는다.

## 8. 수용 기준

- FA-01: 실제 에이전트 요청으로 생성·검증·저장한 View를 열면 목적별 구간과 첫 구간의 실제 코드 블록이 기본으로 보인다. 수동 DB 수정이나 UI 주입만으로 통과할 수 없다.
- FA-02: 여러 문장으로 구현된 한 처리를 선택하면 관련 문장들이 블록으로 함께 보인다. 파일이 다른 구현은 출처를 구별한 여러 블록으로 읽으며 각 문장의 정확한 근거로 이동한다.
- FA-03: 구간 내부·사이의 조건 결과, 실패, 반복, 합류, 미확인 인계는 기본 개요에서 존재와 결과 또는 한계를 구별하고 해당 코드로 이동할 수 있다.
- FA-04: 블록에서 지정한 문장으로 상세 진입하고 모든 기존 단계를 탐색한 뒤 출발 구간·블록·위치·baseline으로 돌아온다.
- FA-05: 같은 View의 저장 복원·HTTP·MCP full·compact가 동일한 개요 참조를 제공하고 과거 View와 기존 reading-path 소비자가 계속 동작한다.
- FA-06: §7의 실패·부재·늦은 응답에서 잘못된 개요나 조용한 상세 전환이 발생하지 않으며 원본·현재 View를 보존한다.
- FA-07: 대표적인 실제 큰 요청에서 개발자 참가자가 기본 화면을 읽고 시작, 주요 판단, 계층 간 인계, 결과 또는 경계를 설명하며 각 설명의 코드 블록을 연 관찰 기록이 있다. 구간별 정답 근거와 누락·오해를 함께 기록한다. 자동 검사가 통과해도 이 증거 없이 기능 완료를 선언하지 않는다.

반례1: 주요 문장 열 개를 목록에 두고 하나씩 클릭해야 구현을 읽으면 FA-02 실패다.
반례2: 함수 전체를 표시했지만 어떤 문장들이 해당 처리인지 알 수 없으면 FA-02 실패다.
반례3: 테스트에서만 개요 데이터를 넣고 실제 요청은 기존 View를 열면 FA-01 실패다.
반례4: 선별된 성공 경로만 보여 주고 실패·미확인 경계를 숨기면 FA-03 실패다.

## 9. 검증과 완료 판정

티켓마다 실제 공개 경로의 입력 요청·snapshot·분석 View ID·개요 View ID·스크린샷·소스 대응·검사 결과를 남긴다. ID와 내부 검증 정보는 검사 산출물에 기록하며 기본 제품 화면에 노출하지 않는다.

첫 티켓에서 여러 문장과 여러 파일을 포함하는 실제 분석 사례를 사용한다. 마지막에는 개발자가 사용하는 대표 큰 요청을 같은 snapshot에서 검증한다. 시작·핵심 판단·인계·결과를 설명하는 답과 실제 코드를 대조한다. 개발자 참가자의 설명·코드 추적 과제는 기능 완료의 필수 증거이며 에이전트 자체 설명으로 대체하지 않는다. 참가자 검증이 아직 없으면 자동 검사 통과와 사용자 결과 검증 대기를 구분한다. 속도 향상률과 만족도 측정은 별도이며 관찰 근거 없이 주장하지 않는다. 과거 버전 재현이나 전체 분기 전수조사를 선행 조건으로 만들지 않는다.

필수 구현 검사는 `make fmt`, `make vet`, `make check-naming`, `make test-ui`, `make test-flowview`, `make test`, `make build`, `git diff --check`다. 변경한 Go 계약에는 `go test ./internal/curator/semantic ./internal/presenter/flowview ./internal/agentgateway/mcp`를 먼저 실행한다. 실행하지 못했거나 실패한 필수 검사는 사유와 영향을 남기고 완료로 처리하지 않는다. 이번 문서 작성은 구현 검사 실행을 뜻하지 않는다.

## 10. 가정·결정과 티켓 적용

- ASM-01: 기존 snapshot 소스에서 블록 범위를 복원할 수 있다. 첫 티켓에서 검증하며 불가능하면 같은 snapshot의 필요한 소스를 기존 View 저장에 포함한다. 현재 작업 파일로 대체하지 않는다.
- ASM-02: 기존 연결 에이전트가 원문 요청과 전체 분석을 읽고 구간을 제안할 수 있다. 실제 요청으로 검증하며 실패 시 의미 생성 부재를 기록한다. 새 모델 서비스를 임의로 추가하지 않는다.
- ASM-03: 브라우저 직접 분석에는 에이전트 생성자가 없다. 해당 경로는 명시적 미생성 안내로 처리하며 자동 개요 지원으로 집계하지 않는다.

구현 방향은 결정 기록에 제안으로 남긴다. 공개 schema의 구체적인 파일·직렬화 선언은 티켓1의 소비자 대조에서 정하며 여기의 의미·호환성·사용자 결과를 축소할 수 없다. 이를 바꿔야 하면 영향을 명시하고 계약을 수정한다. 현재 사용자 의도에 관한 차단 결정은 없다.

티켓은 GOAL-01 → GOAL-02 → GOAL-03 순서로 진행한다. 각 티켓은 요청·저장 결과부터 실제 화면까지 검증한다. 구간 생성이나 중앙 코드 블록 표시를 제외한 UI 작업으로 다시 축소하지 않는다.
