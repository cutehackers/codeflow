## 1. 문제와 사용자 목표

현재 FlowView는 실제 소스, 처리 구간, 조건과 연결을 보여 준다. 그러나 개발자는 그 코드가 어떤 값을 확인하고 무엇을 바꾸며 어떤 결과를 만드는지 직접 해석해야 한다. 기존 SLM Labeler는 관문 제목·역할·조건으로 한 줄 라벨을 제안하므로 실제 코드와 문맥을 해석하는 역할을 충분히 수행하지 못한다.

소형 모델은 CodeFlow가 확보한 코드와 근거를 읽고 이해하기 쉬운, 한국어 원어민에게 가장 자연스러운 한국어 해설을 제안한다. 메인 에이전트의 요청 해석, 전체 흐름 선정, 구간 구성과 복잡한 판단은 그대로 둔다. 메인 에이전트의 토큰 절감은 부가 효과이며 이번 기능의 완료 기준이 아니다.

| 의도 | 목표 | 관찰 가능한 결과 |
|---|---|---|
| INT-01: 코드의 국소 동작을 쉽게 이해한다 | GOAL-01 | 사용자는 중앙 코드 블록의 해설을 읽고 입력·처리·상태 변화·결과를 설명하며 해당 소스를 연다. |
| INT-02: 여러 블록이 수행하는 처리 목적을 이해한다 | GOAL-02 | 사용자는 선택한 처리 구간의 목적과 요청에서의 역할을 읽고 이를 뒷받침하는 블록으로 이동한다. |
| INT-03: 조건에 따른 처리 차이를 이해한다 | GOAL-03 | 사용자는 선택한 문장의 조건과 확인된 결과별 후속 처리를 구별하고 해당 조건·결과 소스를 연다. |

## 2. 범위

### 포함

- 역할1: 중앙 코드 블록의 짧은 해설.
- 역할2: 이미 구성된 처리 구간의 목적과 관련 블록들의 역할 해설.
- 역할3: 오른쪽 선택한 코드의 맥락에서 조건·상태 변화·반환·실패·확인된 후속 처리 해설.
- 같은 저장 View의 소스와 분석으로 모델 입력을 구성하는 기능.
- 필요한 주변 문맥을 제한적으로 확보하고 부족·생략·마스킹을 기록하는 기능.
- 로컬 모델 HTTP 호출, 구조화된 응답 검사, 기존 탐색 대상에 연결되는 소스 참조, 취소와 기존 안내 방식의 실패 처리.
- 세 역할을 실제 화면 경로와 실제 모델로 평가하는 검증 계획.

### 제외

- 현재 화면 배치, 왼쪽 처리 구간의 역할·소속·정렬, 코드뷰의 원문·범위·강조·접기·선택·탐색 변경.
- 코드 위 해설 영역, 새 패널·열·탭·버튼·근거 발췌 뷰 추가. 기존 표시 지점이 부족하면 기능 범위를 조정하고 화면을 임의 확장하지 않는다.
- SLM이 카테고리·구간 소속·관계·코드 범위를 만들거나 수정하는 기능. 기존 에이전트와 서버의 책임이다.
- 역할4의 구간 사이 연결 전용 해설과 역할5의 상위 카테고리 요약.
- 메인 에이전트에 해설을 전달하는 새 MCP 도구, 전체 저장소 사전 해설, 범용 검색 에이전트.
- 코드 수정·실행, 실행 추적, 기능 완료 판정, 보안·업무 정책 적합성 확정.
- 새 parser, CodeGraph 재색인, 모델 자동 다운로드·설치·실행, 학습과 미세 조정.
- watcher 기반 갱신, 기본 화면 교체, 비교 기준 변경, 기존 계약의 상태 수정.
- 원격 모델 서비스는 첫 설계 제안의 지원 범위에서 제외한다. 기존 라벨 API의 설정 계약은 변경하지 않는다.

## 3. 사용자와 전제

- 주 사용자: 요청한 코드 동작을 읽는 개발자.
- 권한: 기존 FlowView 토큰과 로컬 프로젝트 읽기 권한을 재사용한다.
- 대상: 서버가 읽을 수 있는 immutable View ID와 그 안의 block ID, segment ID 또는 step ID.
- 역할1·2는 유효한 Requested Flow Overview가 필요하다. 없는 과거 View에서도 정확한 문장 근거가 있으면 역할3은 가능하다.
- 모델 사용은 선택 기능이며 비활성 상태에서도 기존 소스·탐색이 작동한다.
- 기본 입력 언어가 코드이고 출력은 한국어다. 코드 식별자는 원문을 유지한다. 다국어 출력 설정은 이번 범위에서 추가하지 않는다.
- 현재 버전의 코드를 알고 싶으면 사용자가 명시적으로 재분석한다. 과거 View 해설은 그 View의 분석 시점에 한정한다.

### 점검 결론

기본 소스 수집을 다시 구현하지 않는다. 새로 필요한 핵심은 **서버 소유 근거 구성, 세 역할의 해설 계약, 모델 응답 검사, 별도 화면 상태, 실제 설명 품질 평가**다. 추가 문맥 검색은 기존 저장 소스와 snapshot 접근을 재사용하되, 의미 해석에 필요한 정의·호출 대상의 확보 가능성을 정확히 제한한다.

## 5. 세 역할의 출력과 화면 계약

| 역할 | 대상과 입력 | 출력 | 표시 위치 |
|---|---|---|---|
| 역할1 / `block` | 블록의 전체 연속 범위, 강조 문장, 필요한 함수·조건 문맥 | 목적 한 문장과 입력·처리·상태 변화·결과 중 근거가 있는 항목 | 기존 설명 지점에서 선택 블록의 의미를 보조. 코드 본문에 해설 영역 삽입 금지. 구체적인 표시 매핑은 질문6 |
| 역할2 / `segment` | 구간의 모든 블록, 포함 문장, 확인된 내부 관계·분기·진입·경계, 원문 요청 | 처리 목적, 요청과의 관련성, 블록별 기여, 중요한 판단·결과·한계 | 기존 구간 설명 지점을 활용하는 제안. 왼쪽 처리 구간과 중앙 코드 구성 유지. 표시 매핑은 질문6 |
| 역할3 / `step` | 선택 문장, 감싸는 조건, 관련된 확인된 간선과 대상 소스 | 조건의 뜻, 결과별 다음 처리, 상태 변화·반환·실패 또는 확인되지 않은 부분 | 기존 선택 코드 맥락의 설명 지점 활용 제안. 조건·소스·탐색 동작 유지. 표시 매핑은 질문6 |

- SLM은 이미 선택된 처리 구간·블록·문장의 의미를 보조한다. 왼쪽 처리 구간은 흐름 탐색을, 코드뷰는 실제 구현 확인을 계속 담당한다.
- 모델 결과는 내부적으로 원본 분석과 분리한다. 기존 설명 지점에서 표시할 경우 모델 제안임을 구별하며 canonical purpose·inclusionReason·frame.text·근거 상태를 덮어쓰지 않는다. 구체적인 표현은 질문6에서 확정한다.
- 새 해설 영역·소스 발췌 뷰를 추가하거나 코드 행 사이에 자연어를 삽입하지 않는다. 원문·강조·접기·선택·탐색·코드 범위는 유지한다.
- 근거 확인은 기존 코드 블록·문장별 탐색·복귀 동작만 사용한다. 새 근거 링크 UI나 표시 대상은 임의로 추가하지 않는다.
- 해설 수신과 기존 설명 문구의 변화가 선택·스크롤·초점·baseline을 이동시키지 않아야 한다.
- 일반 처리 문장에 참·거짓 결과를 억지로 만들지 않는다. 조건이 없는 문장은 처리·상태·결과를 설명한다.
- 참·거짓·null 여부 같은 구분은 분석이 확인한 결과 종류를 사용한다. 예외·반환·반복·비동기 처리를 직렬 성공 흐름으로 단순화하지 않는다.
- 기술적으로 가능한 경로를 실제 실행된 결과라고 표현하지 않는다.
- 선택한 조건 경로 필터는 해설과 별도로 유지한다. 첫 제안에서는 조건의 전체 확인된 결과를 설명하고, 필터가 한 경로를 선택했다는 이유로 반대 결과를 숨기지 않는다.
- 실행 트리거와 저장 정책은 질문1·2의 답에 따라 확정한다. 답변 전까지 자동 생성이나 영구 저장을 구현 요구로 간주하지 않는다.

## 6. 서버가 구성하는 해설 문맥

### 6.1 근거 구성 순서

1. 인증된 요청에서 View ID와 대상 종류·ID를 받는다. 클라이언트의 코드 본문, 소스 경로·범위, 임의 prompt, 모델 endpoint는 받지 않는다.
2. 저장 View의 무결성을 확인하고 원본 요청·분석 기준·대상 소속을 확인한다. 응답 표시용 보정 정보만으로 원본 근거를 대체하지 않는다.
3. 정확한 문장과 코드 블록을 저장된 flowContexts·sourceFiles·sourceFileDigests에서 검증한다. 구조 문맥과 주변 코드는 포함 문장의 실행 근거와 구별한다.
4. 화면에서 접힌 행도 포함한 실제 블록 범위를 사용한다. `blockSourceLines`가 반환하는 표시용 부분 소스만 모델에 보내지 않는다.
5. 설명에 필요한 함수 서명, 감싸는 조건·콜백, 같은 함수의 관련 정의, 직접 호출 대상과 확인된 결과 소스를 추가한다. 추가 문맥은 같은 snapshot에서 출처·범위를 확인한 경우에만 사용한다.
6. 비밀정보 마스킹과 입력 크기 검사를 통과한 문맥 묶음을 만든다. 제공되지 않은 문맥, 제외 이유와 분석 경계를 기록한다.
7. 모델에 소스별 식별자와 허용된 대상·결과 참조 목록을 제공한다. 설명 본문과 참조를 구조화된 응답으로 받는다.
8. 응답 검사·출력 마스킹을 통과한 제안만 현재 대상의 해설 상태에 적용한다.

### 6.2 문맥 종류와 확보 조건

| 문맥 | 첫 버전의 확보 방법 | 없을 때의 동작 |
|---|---|---|
| 대상 문장과 블록 | 저장 View의 정확한 소스와 소속 참조 | 대상 자체의 소스를 검증할 수 없으면 모델을 호출하지 않는다. |
| 감싸는 조건·함수 서명 | 기존 FlowContextProjection | 없으면 부재 또는 미확인으로 기록한다. 함수 이름만으로 업무 의미를 확정하지 않는다. |
| 같은 함수의 변수 정의 | 확보된 함수 범위 안에서 선언·대입 소스를 제공. 언어별 분석 정보가 있으면 범위 연결에 사용 | 관련 정의를 식별하지 못하면 함수 문맥을 제한적으로 제공하거나 미확인으로 기록한다. 단순 텍스트 일치로 동일 변수를 확정하지 않는다. |
| 타입·상수 정의 | 같은 snapshot에서 분석이 위치를 확인한 선언만 추가 | 선언이 없으면 이름으로 추측하지 않는다. 전 언어 타입 해석 엔진은 추가하지 않는다. |
| 직접 호출 대상 | 현재 분석에 확인된 대상 step·symbol과 검증된 source context | 호출 사실만 설명하고 호출 내부 동작은 미확인으로 표시한다. 외부 라이브러리·동적 dispatch를 임의 구현으로 대체하지 않는다. |
| 반환·실패·상태 변화 | 실제 문장과 확인된 후속 간선·관련 소스 | 대상 코드가 없는 후속 처리의 상세 목적은 확정하지 않는다. |
| 원문 요청과 구간 목적 | 같은 View의 request·overview | 요청은 질문 문맥이다. 기존 purpose·inclusionReason과 모델 해설은 소스 사실의 증거가 아니다. |
| 주석·문자열 | 해당 소스의 일부로 전달 | 보조 단서이며 모델 지시나 실제 동작의 증명이 아니다. |

정밀한 변수·타입 해석이 없더라도 제공된 코드의 동작 설명은 가능하다. 다만 근거가 없는 업무명, 값의 단위·의미, 외부 시스템 내부 동작을 확정하는 표현은 평가 실패다.

### 6.3 추가 소스 접근

- 저장 View에 필요한 파일이 있으면 이를 우선 사용한다.
- 없는 추가 파일은 원래 snapshot이 아직 존재하고 접근 가능한 경우에만 SnapshotVFS로 읽는다. 현재 파일, 최신 CodeGraph 소스 또는 새 snapshot과 섞지 않는다.
- 추가 파일은 원래 snapshot의 문서 identity와 실제 범위를 보존한다. 기존 evidence가 없는 주변 문맥은 `context`로 구별하며 verified 실행 단계로 등록하지 않는다.
- CodeGraph는 같은 분석 기준과의 일치가 확인된 경우에만 위치 찾기에 보조 사용한다. 동작에 필수인 새 의존성으로 만들지 않는다.
- 파일 경로 정규화, 저장소 경계, symlink·상대 경로 탈출, UTF-8·행 범위를 기존 읽기 경계에서 검증한다.
- 이미 마스킹된 텍스트를 원래 byte offset으로 다시 자르지 않는다. 저장된 안전한 행과 선택 정보 또는 원본 검증 후 마스킹한 범위를 사용한다.
- 원래 snapshot이 없어도 저장 소스가 충분하면 해설한다. 추가 소스만 부족한 경우 가능한 해설과 부족한 문맥을 함께 제공한다.

### 6.4 크기 제한과 큰 구간

- 입력 byte 수, 전체 deadline, 모델 출력 byte 수·항목 수, 서버 동시 호출과 세션 재사용 크기에 유한한 상한이 필요하다. 수치는 질문4의 실측으로 확정한다.
- 대상의 중요한 조건·실패·반환·외부 효과를 조용히 잘라 내지 않는다. 원문 범위와 제외된 범위를 기록한다.
- 모델 문맥 안에 들어오지 않는 블록은 정적 범위로 나누어 각 부분을 해설하고 참조를 유지할 수 있다. 일부만 설명하면 전체 블록 설명으로 표시하지 않는다.
- 큰 구간은 블록별 해설 후 구간 수준 합성을 허용한다. 합성 입력에는 확인된 원본 소스·관계·필수 조건·경계를 함께 남긴다. 블록 해설만을 유일한 증거로 사용하지 않는다.
- 일부 블록 실패 시 구간 전체를 설명했다고 표시하지 않는다. 필요한 합성이 입력 상한을 넘으면 `partial` 또는 `unavailable`로 제공한다.
- 모델이 추가 도구 호출로 파일을 무제한 탐색하지 않는다. 서버가 범위와 호출 수를 통제한다.

### 6.5 기존 화면에서 확인할 수 있는 근거만 사용한다

- 추가 변수·타입 정의에도 기존 화면의 소스 확인 경로가 필요하다. 같은 snapshot의 파일을 읽을 수 있다는 사실만으로 입력에 포함하지 않는다.
- 현재 코드뷰의 기존 펼침·문장 탐색 등으로 해당 안전한 원문 범위를 확인할 수 있는지 서버와 화면 계약에서 대조한다. 확인 가능한 범위에만 sourceRef를 부여한다.
- 기존 경로로 열 수 없는 추가 소스는 첫 범위의 모델 입력에서 제외하고 부족한 문맥으로 기록한다. 새 블록·step 생성, 중앙 발췌 표시, 최신 `/api/source` 조회로 우회하지 않는다.
- 이 제한으로 세 역할의 설명이 부족하면 해설 범위를 제한하거나 미결정으로 남긴다. 화면 보존 요구를 해설 완전성보다 우선한다.
- 이전 초안의 추가 발췌 표시 제안은 사용자 화면 보존 지시에 따라 철회한다. 추가 소스 접근과 그 근거 확인은 같은 View·snapshot 원칙을 유지한다.

## 7. 해설 데이터 계약 제안

새 데이터는 canonical SemanticMapIR·FlowSequence·Requested Flow Overview와 분리한다. 아래 이름은 새 API 제안이며 구현 시 JSON schema와 소비자 fixture로 고정한다.

### 7.1 요청

`POST /api/view/explanation`을 새 경로로 제안한다. 기존 `/api/semantic/labels`의 요청·응답은 유지한다.

```json
{
  "schemaVersion": 1,
  "requestId": "explanation-request-1",
  "viewId": "<immutable-view-id>",
  "expectedSnapshotId": "<snapshot-id>",
  "expectedComputedBasisId": "<basis-id>",
  "target": {"kind": "block", "id": "<block-id>"}
}
```

- `kind`는 `block`, `segment`, `step` 중 하나다. ID는 지정한 View 안의 해당 종류에 속해야 한다.
- snapshot·computed basis는 경쟁 상태 검사에만 사용한다. 실제 입력 기준은 서버가 저장 View에서 읽는다.
- 프런트엔드 요청은 기존 `X-CodeFlow-Token` 인증 패턴을 사용한다. 토큰을 모델 입력·응답·로그에 포함하지 않는다.
- JSON 본문과 필드 크기를 제한하고 알 수 없는 종류·필드·중복 필드·뒤따르는 JSON을 거부한다.
- 저장 View 없는 임시 분석의 자동 변환·저장은 이번 API가 수행하지 않는다.

### 7.2 응답의 필수 의미

| 정보 | 필수 내용 |
|---|---|
| 식별 | schemaVersion, requestId, viewId, snapshotId, computedBasisId, target |
| 처리 결과 | `proposed`, `unavailable`, `timed_out`, `failed` 중 하나 |
| 해설 범위 | `complete`, `partial`, `none`. complete는 입력 대상 해설 범위이며 분석 완전성이나 의미 정확성 승격이 아니다. |
| 해설 항목 | 서버가 구성한 항목 ID, 종류, 한국어 text, sourceRefs, 필요 시 outcomeRef |
| 항목 종류 | purpose, input, process, condition, state_change, external_effect, result, failure, request_relevance |
| 소스 목록 | sourceRef ID, repo-relative path, symbol, 안전한 행 범위, 기존 탐색 대상과 확인 가능한 범위, 문맥 또는 실행 근거 구분. 기존 화면에서 확인할 수 없는 소스는 §6.5에 따라 입력에서 제외 |
| 제한 | 마스킹, 미확인 호출, 문맥 부재, 입력 제한, 설명하지 않은 블록·결과와 이유 |
| 의미 권한 | 표시되는 모든 본문은 model_proposal. 참조 검증 상태와 의미 정확성은 별도다. |
| 내부 재사용 식별 | context digest, prompt version, 모델 설정 identity. API 내부에서만 사용하며 기본 화면에 표시하지 않는다. |

모델은 입력에 등록된 sourceRef와 outcomeRef만 반환할 수 있다. 파일 경로, 새 step·edge ID, source range와 검증 상태를 모델이 정하지 않는다. 서버가 응답의 출처 목록을 만든다.

### 7.3 참조 검증과 의미 평가의 구별

- 자동 검사: JSON 구조, 항목 종류, 대상 identity, 소스 참조 소속, 결과 참조 소속, 필수 참조, 길이·항목 상한, 마스킹, 알려진 경계 보존.
- 자동으로 증명할 수 없는 내용: 문장의 실제 의미가 해설과 일치하는지, 업무 목적이 타당한지, 중요한 의미가 빠졌는지, 한국어가 이해하기 쉬운지.
- 각 동작 설명에는 적어도 하나의 유효한 sourceRef가 필요하다. 제한 안내는 서버가 별도로 생성할 수 있다.
- 참조가 유효하다는 이유로 본문을 verified·approved라고 표시하지 않는다. 모델의 자기 평가 점수도 검증을 대체하지 않는다.
- 조건별 결과 설명은 확인된 outcomeRef와 관련 소스를 연결한다. 소스가 없는 결과는 존재 여부와 확인 불가 범위만 알린다.
- 잘못된 참조·소속·응답 구조가 하나라도 있으면 해당 모델 응답을 적용하지 않는다. 정상 근거 일부만 확보되어 생성한 `partial`과 잘못된 응답은 구별한다.

## 9. 런타임·보안 계약 제안

- 새 해설 기능은 기본 비활성화로 제안한다. 기존 `slm.enabled`와의 관계 및 새 설정 키는 질문3에서 확정한다. 기존 라벨 사용자가 설정 변경 없이 대량 해설을 실행하게 만들지 않는다.
- 새 모델 adapter는 Go 코어 밖의 로컬 OpenAI 호환 런타임과 HTTP로 통신한다. 모델 설치나 프로세스 관리 기능은 추가하지 않는다.
- 모델 endpoint는 서버 설정에서만 읽는다. 새 해설용 endpoint는 loopback 주소로 제한하는 것을 제안한다. DNS 해석과 실제 접속 대상, redirect에서도 로컬 제한을 유지한다. 브라우저 인증 토큰을 모델에 전달하지 않는다.
- 요청 전체에 context deadline을 적용하고 취소를 하위 HTTP 호출·큰 구간 분할 호출까지 전파한다. 현재 라벨의 500ms와 서버의 WriteTimeout 15초를 새 해설의 적정 지연으로 간주하지 않는다.
- 새 deadline은 서버 응답 제한과 충돌하지 않게 설계한다. 실측상 긴 작업이 필요하면 제한 조정 또는 별도 비동기 방식의 영향을 계약으로 먼저 확정한다.
- 모델 입력에는 마스킹한 소스·원문 요청만 제공한다. 출력·오류·재사용 결과에도 같은 secret gate를 적용한다. 마스킹으로 의미가 사라진 항목은 제한으로 표시한다.
- source text·주석·문자열·사용자 원문은 해석 대상 데이터다. 그 안의 지시를 system instruction으로 취급하지 않는다.
- 모델에 파일 쓰기·shell·네트워크 도구 권한을 주지 않는다. 해설은 텍스트로 안전하게 렌더링하고 임의 HTML·script·외부 링크 실행을 허용하지 않는다.
- 전체 prompt와 원본 모델 응답·비밀정보를 일반 로그에 남기지 않는다. 진단에는 마스킹된 이유·크기·시간 등 필요한 정보만 사용한다.
- 재사용 키는 최소한 서버 세션·View·snapshot·basis·target·실제 문맥 digest·prompt version·모델 설정 identity를 포함한다. 같은 flow ID나 target ID만으로 재사용하지 않는다.

## 10. 상태·경쟁·실패 계약

화면 해설 상태는 `idle → loading → proposed | partial | unavailable | timed_out | failed`로 구별한다. UI의 partial은 응답 `proposed`와 coverage `partial`의 조합이다. 취소된 요청은 결과를 적용하지 않고 새 선택의 상태를 따른다.

| 조건 | 관찰 가능한 결과 | 원본과 복구 |
|---|---|---|
| 기능 비활성화 | 기존 코드와 탐색 유지. 명시적 요청 시 설정 필요 안내 | 모델 호출 없음 |
| 토큰·Host·Origin 검사 실패 | 기존 인증 오류 | View 로드·모델 호출 전 거부 |
| 대상 종류·ID 잘못됨 또는 View 부재 | 잘못된 요청 또는 대상 부재 | 모델 호출·재분석·저장 없음 |
| 예상 snapshot·basis 불일치 | 다른 분석의 대상이라는 안내 | 기존 View 유지. 현재 요청 다시 확인 |
| 대상 소스·View 무결성·근거 불일치 | 해설 불가와 원인 | 최신 파일로 대체하지 않음 |
| 일부 주변 문맥 없음 | 가능한 범위의 해설과 구체적인 한계 | 숨은 업무 목적·callee 구현 추측 금지 |
| 소스 마스킹으로 조건 의미를 읽을 수 없음 | 해당 조건 해설 불가 또는 부분 해설 | 비밀정보 복원·추정 금지 |
| 모델 연결 실패·HTTP 오류·빈 응답 | 기존 안내 방식으로 실패 알림. 새 영역·버튼 추가 금지 | 기존 제목이나 소스를 생성된 해설로 표시하지 않음 |
| deadline 초과 | 시간 초과 안내 | 모든 분할·합성 호출 취소. 자동 무한 재시도 없음 |
| JSON·참조·결과 소속 오류 | 응답 적용 거부와 재요청 가능 안내 | 임의 수정한 본문으로 성공 처리하지 않음 |
| 구간의 일부 블록 해설 실패 | 설명한 블록과 실패 블록 구별 | 구간 전체를 해설했다고 표시하지 않음 |
| 선택·모드·View 변경 중 응답 도착 | 기존 대상의 응답을 새 대상에 적용하지 않음 | 요청 identity와 별도 해설 순번을 비교. 취소 무시 모델도 방어 |
| 중복 클릭·동시 요청 | 같은 identity·문맥의 진행 요청을 재사용하거나 하나로 제한 | 서로 다른 대상을 혼합하지 않음. 취소가 다른 구독 요청을 잘못 종료하지 않게 함 |
| 모델·prompt·문맥 변경 | 이전 재사용 결과 폐기 | 재요청 전 기존 해설을 새 조건의 결과로 표시하지 않음 |
| 과거 View에 개요 없음 | 역할1·2 비지원 안내. 역할3은 정확한 근거가 있을 때 가능 | 개요 생성·기존 View 재저장 없음 |
| 실제 파일이 이후 변경·삭제됨 | 보존된 과거 소스 해설임을 알림 | 저장 소스의 검증 가능 여부로 판단. 현재 디스크의 부재만으로 입력 소스를 바꾸지 않음 |

실패는 기존 안내 방식으로 알린다. 오류 모달로 탐색을 막지 않으며 원본 분석·읽기 상태·비교를 유지한다. 자동 재시도보다 사용자의 명시적 다시 요청을 우선하는 것을 제안한다.

## 11. 불변식

- INV-01: 모델 해설과 canonical 코드 사실·소스 근거·실행 관측·인간 승인을 구별한다.
- INV-02: 한 해설은 하나의 View·snapshot·basis·대상을 참조한다. 현재 workspace·다른 View·baseline을 섞지 않는다.
- INV-03: 서버가 입력 소스·범위·소속을 결정한다. 모델과 브라우저는 검증 근거를 생성하지 않는다.
- INV-04: 근거 참조 검증은 의미 정확성 검증이 아니다. 본문은 항상 모델 제안이다.
- INV-05: 원본 분석, 구간 소속, 관계, 제목, 근거 상태, 저장 View ID를 해설로 수정하지 않는다.
- INV-06: 화면 배치, 왼쪽 처리 구간과 코드뷰의 역할·구조·원문·범위·강조·접기·선택·탐색을 유지한다. 해설 수신·실패·취소는 선택·초점·읽던 위치·baseline·조건 필터를 변경하지 않는다.
- INV-07: 중요 조건·실패·반환·반복·미확인 경계를 해설에서 숨기거나 완료로 승격하지 않는다.
- INV-08: 같은 secret gate, 읽기 전용 소스, 인증과 유한한 실행 제한을 유지한다.
- INV-09: 기존 `/api/semantic/labels`, 저장 View·HTTP·MCP의 공개 계약은 유지한다. 새 기능의 데이터는 별도다.
- INV-10: 내부 model identity·context digest·검사 시간과 엔진 telemetry는 기본 읽기 화면에 노출하지 않는다.

## 12. 수용 기준과 증거

| 기준 | 사용자 또는 API에서 확인할 결과 | 필수 증거 |
|---|---|---|
| FA-01 / GOAL-01 | 실제 View의 코드 블록 해설이 목적·처리·결과를 설명하고 같은 소스로 연결됨 | 실제 모델 응답, 화면, 원문과 해설 대응 기록 |
| FA-02 / GOAL-02 | 여러 블록·파일을 포함한 구간 해설에서 공통 목적·각 블록 기여·주요 판단과 한계를 읽음 | 여러 파일 구간 사례. 단일 블록 요약만으로 대체 불가 |
| FA-03 / GOAL-03 | 조건 결과별 진행·중단·반환·실패를 구별하고 조건과 결과 소스를 엶 | 양쪽 결과가 있는 조건, 조기 반환, 비조건 처리 사례 |
| FA-04 | 서버가 View와 target으로 근거를 구성하며 위조 소스·참조·다른 snapshot 요청을 거부 | 인증된 API·schema·대상 소속·source integrity 테스트 |
| FA-05 | 접힌 코드와 주변 문맥을 모델에 적절히 제공하고 마스킹·부족·생략을 표시. 추가 근거는 기존 코드뷰의 확인 경로가 있는 범위에만 사용 | 긴 블록, 정의 부재, unresolved call, redaction, 기존 화면의 정의 확인 가능·불가와 현재 파일 변경 후 열기 사례 |
| FA-06 | Semantic Assistant 적용 전후 화면 구조·왼쪽 구간·코드뷰 표시와 기존 탐색 유지. 원래 선택·위치·baseline 보존 | 동일 View·선택의 적용 전후 화면과 코드 행·강조·접기·탐색 대조, 지연 응답·취소·복귀 검사 |
| FA-07 | 비활성·실패·시간 초과·잘못된 응답에서도 기존 코드 탐색 계속 가능 | 실패 주입 테스트와 실제 모델 중단 사례 |
| FA-08 | 같은 기존 라벨·저장 View·HTTP·MCP 소비자가 계속 작동 | 호환 fixture와 변경 전후 저장 원본 digest 대조 |
| FA-09 | 모델 입력·응답·로그에서 secret 노출이 없고 소스 내 악성 지시를 데이터로 취급 | 마스킹·prompt injection·안전 렌더링·endpoint 경계 검사 |
| FA-10 | 한국어 해설이 원문 의미와 일치하고 사람이 설명·근거 추적 과제를 수행함 | 고정 corpus의 사람 평가와 모델별 오류 기록. 구조 검사만으로 통과 불가 |
| FA-11 | 확정된 실행·재사용·저장 정책대로 작동 | 질문1·2 확정 후 정책별 호출·재접속·삭제·원본 보존 증거 |
| FA-12 | 확정된 입력·출력·deadline·동시 호출 상한에서 끝나고 과부하 때 탐색 유지 | 질문4 확정 후 실제 장비 cold/warm 측정과 제한·취소 검사 |

### 반례

- 반례1: 함수명만 보고 배송 주소 검증이라고 설명하지만 실제 소스는 수량만 확인한다. 참조가 유효해도 FA-10 실패다.
- 반례2: 첫 블록만 설명하고 구간 전체 해설이라고 표시한다. FA-02·05 실패다.
- 반례3: 조건의 성공 경로만 설명하고 조기 반환을 생략한다. FA-03 실패다.
- 반례4: 현재 작업 파일에서 과거 View에 없던 조건을 읽어 설명한다. FA-04 실패다.
- 반례5: sourceRef는 실제 코드지만 모델이 호출 대상의 내부 처리나 실제 실행 결과를 지어낸다. FA-10 실패다.
- 반례6: 모델 모의 응답 테스트만 통과하고 실제 인증 API와 모델을 실행하지 않았다. FA-01~03·10 완료 증거가 아니다.
- 반례7: 해설이 도착하면서 소스가 아래로 밀려 읽던 행을 놓친다. FA-06 실패다.

## 13. 실제 모델과 사용자 평가

모델 후보와 장비를 먼저 고정한 뒤 같은 소스·prompt·입력 상한·양자화 조건으로 비교한다. 현재 기본 모델 이름이 새 해설에도 적합하다는 가정은 하지 않는다. 이번 스펙 작성은 모델 추천이나 품질 입증을 포함하지 않는다.

corpus에는 지원 대상 언어의 실제 코드와 다음 유형을 포함한다: 단순 변환, 조건 양쪽 결과, 조기 반환·실패, 상태 변경, 외부 호출, 비동기 처리, 여러 블록·파일 구간, 동적 호출 미확인, 정의·타입 부재, 마스킹된 소스, 모델 지시처럼 보이는 주석, 입력 상한을 넘는 블록·구간.

각 사례의 사람이 작성한 판정 자료에는 필수 동작·조건·결과, 설명하면 안 되는 추측, 소스 대응, 필요한 주변 문맥, 설명 가능한 범위와 한계가 있어야 한다. 자연어 표현의 단어 일치로 채점하지 않는다.

| 평가 항목 | 기록할 내용 |
|---|---|
| 의미 정확성 | 코드와 반대 설명, 업무 목적 추측, callee 내부 동작 추측, 실제 실행 단정 |
| 누락 | 중요한 조건·실패·반환·상태 변화·경계와 블록 기여 누락 |
| 근거 추적 | 해설 항목의 참조가 실제 설명을 뒷받침하는지 |
| 한국어 이해 | 개발자가 해설 후 목적·조건·결과를 자신의 말로 설명할 수 있는지 |
| 사용자 과제 | 해설 내용에 해당하는 코드를 찾아 여는지, 오해가 줄었는지 |
| 비용·성능 | cold/warm 지연, 입력·출력 크기, 메모리 사용, 동시 요청·취소 동작 |

숫자 성공률·지연 목표는 근거 없이 만들지 않는다. 질문4·5에서 corpus·장비·수용 기준을 확정한 뒤 모델을 선택한다. 필수 조건의 반대 설명·근거 없는 업무 사실·미확인 상태 승격은 중대한 실패로 기록한다. 개선 효과는 기존 코드만 읽는 경우와 비교 관찰한 뒤 주장한다.

## 14. 구현 검증 계획

이 문서 작업에서는 제품 코드를 변경하지 않았으며 아래 명령을 실행했다고 주장하지 않는다. 구현 시 Go 표준과 기존 프로젝트 필수 검사를 따른다.

| 검사 | 적용과 명령 | 확인 목적 |
|---|---|---|
| 집중 Go 검사 | `go test ./internal/curator/... ./internal/presenter/flowview/... ./internal/collector/secret/...` | 근거 구성·모델 응답·API·마스킹 동작 |
| 저장·snapshot 검사 | 변경 시 `go test ./internal/collector/storage/... ./internal/analyzer/workspace/...` | 원본 무결성·snapshot 읽기·과거 소스 보존 |
| 프런트엔드 정적 검사 | `npm --prefix web/flowview run check` | 새 DTO·Svelte 상태·렌더링 |
| 화면 단위 검사 | `make test-ui` | 역할별 표시·취소·재사용·복원 |
| 브라우저 공개 경로 | `make test-flowview` | 실제 인증 API→해설→근거 클릭→상세→복귀 |
| 프로젝트 필수 검사 | `make fmt`, `make vet`, `make check-naming`, `make test`, `make build` | 전체 회귀·명명·배포 UI 빌드 |
| 문서·diff | `git diff --check`와 링크·상태·용어 검토 | 스펙과 기존 계약 관계, unrelated 변경 없음 |
| 실제 모델·사용자 | §13의 확정 corpus와 실행 장비에 맞는 명령은 구현 준비 시 기록 | mock으로 입증할 수 없는 의미 품질과 이해 결과 |

모델 호출은 테스트 대체 경계를 제공해 성공·잘못된 참조·시간 초과·취소·출력 상한을 검사한다. 보안·호환·경쟁 상태는 동작 중심 사례로 확인한다. 숫자 coverage 기준이나 반복 실행 횟수는 새로 발명하지 않는다.

## 15. 가정과 미결정

### 가정

- ASM-01: 저장 소스와 기존 context만으로 대표 사례의 짧은 설명이 가능하다. 실제 모델로 확인하며 틀리면 필요한 추가 문맥을 사례별로 식별한다.
- ASM-02: 추가 문맥이 없어도 한계를 표시한 설명이 사용자에게 유용하다. 사용자 과제로 확인하며, 혼란을 만들면 해당 대상은 해설 불가로 처리한다.
- ASM-03: 한국어 해설을 요구한다. 현재 대화 언어를 근거로 한 제안이며 다른 출력 언어가 필요하면 별도 결정한다.
- ASM-04: 모델을 개발자가 별도로 설치·운영할 수 있다. 이를 전제로 로컬 HTTP 연동을 제안하며 제품이 자동 설치한다고 약속하지 않는다.

## 16. 승인과 완료 조건

현재 문서는 필요한 기능 점검에 근거한 상세 제안 스펙이다. Codify의 intent hardening 기준에 따라 미결정 실행·저장·보안·수용 정책이 남아 있어 Approved 또는 Hardened로 표시하지 않는다. 기존 승인 계약과 구현은 변경하지 않는다.

구현 착수 전에는 질문1~6의 적용 정책과 수용 조건을 확정하고 그 답을 이 문서·결정 기록·관련 용어에 반영한다. 현재 요청은 스펙 작성이며 구현·티켓 분해·모델 설치 승인이 아니다.

기능 완료는 FA-01~12의 공개 경로 증거, 필수 검사, 실제 모델 품질과 사람의 코드 추적 과제 결과가 모두 있어야 한다. 코드와 자동 검사만 완료된 경우 이를 사용자 이해 개선 검증 완료로 표현하지 않는다.
