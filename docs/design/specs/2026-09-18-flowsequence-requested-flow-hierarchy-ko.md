## 1. 문제와 목표

사용자는 요청한 기능이 어디서 시작하고, 각 아키텍처 계층에서 어떤 주요 판단·처리와 실행 전환을 거쳐 결과에 도달하는지 빠르게 파악하려 한다. 개별 코드 클릭이 작동하거나 카드가 7개 이하라는 사실만으로 이 목적을 달성했다고 판단할 수 없다.

현재 구현에는 관문을 생성하는 서로 다른 경로가 있다. FlowView는 연속 검증문과 상태 변경을 개별 관문으로 노출할 수 있는 생성 경로를 사용한다. 화면의 하위 타임라인도 특정 관문을 선택하고 그 관문에 상세 단계가 여러 개 있을 때에만 나타난다. 따라서 새 구조의 부분 기능이 존재해도 사용자는 상위 관문과 실행 단계의 포함 관계를 인지하기 어렵다.

| 의도 | 목표 | 관찰 가능한 결과 |
|---|---|---|
| INT-01 | GOAL-01 | 사용자가 관문 목록에서 요청한 흐름의 시작, 주요 판단·처리, 결과 또는 미확인 연결을 설명할 수 있다. |
| INT-01 | GOAL-02 | 사용자가 관문을 펼쳐 실제 실행 단계를 확인하고 필요한 문장의 소스로 이동할 수 있다. |
| INT-02 | GOAL-03 | 동일한 분석의 MCP 요약과 FlowView에서 같은 관문 구성과 단계 소속을 확인할 수 있다. |
| INT-02 | GOAL-04 | 저장한 뷰를 다시 열거나 관계 탐색에서 돌아와도 읽던 관문과 단계 맥락을 유지할 수 있다. |

화면 수용 검증은 다음 세부 목표를 사용하며 별도 기능 계약으로 분리하지 않는다.

| 기존 의도 | 화면 세부 목표 | 사용자 결과 |
|---|---|---|
| INT-01 | GOAL-UX-01 | 조건부 분기·합류·종료를 설명한다. |
| INT-01 | GOAL-UX-02 | 실행 단계의 근거 코드를 확인하며 전후 맥락을 유지한다. |
| INT-02 | GOAL-UX-03 | 요약 한계·미확인 연결·소스 한계를 구별하고 다음 행동을 안다. |
| INT-02 | GOAL-UX-04 | 복잡한 흐름, 좁은 창, 키보드 탐색과 실패에서도 같은 기능을 이용한다. |

‘빠르게’에 대한 시간 단축 수치는 아직 없다. 구현 완료의 필수 기준은 핵심 결정 발견, 근거 코드 접근, 맥락 복원이며 시간 개선은 §12의 사용자 검증으로 별도 측정한다.

## 2. 범위와 기존 계약의 관계

### 2.1 포함 범위

- 범위1: Requested Flow에 따른 관문 선정·병합·대표 단계 선정 규칙.
- 범위2: 분석, MCP, FlowView 생성·저장 간 동일한 관문 결과 사용.
- 범위3: 관문과 실행 타임라인의 1:N 표현, 전체 인과관계 요약, 조건 강조, 선택·펼침·패널별 위치·초점 복원, 접근성과 반응형 동작.
- 범위4: 단계·분기·코드 근거 보존, 부분 분석과 과거 저장 뷰 처리.
- 범위5: 실제 API와 브라우저를 통과하는 수용 검증.

### 2.2 제외 범위

## 4. 사용자와 입력 계약

- 주체1: 개발자가 자연어 요청이나 명시적인 진입점으로 Requested Flow를 선택한다.
- 주체2: analyzer와 collector가 확인한 단계, 관계, 소스 근거를 curator가 사용한다.
- 주체3: presenter와 agentgateway는 같은 분석의 관문 결과를 표현한다.

큐레이션 입력에는 요청 문맥, 선택된 흐름 식별자, 순서 있는 단계, 검증된 연결과 분기, 단계별 근거 상태, 미확인 연결이 필요하다. 요청 문맥은 이미 존재하는 분석 요청에서 가져오며 이름이 비슷하다는 이유로 다른 기능의 단계들을 추가하지 않는다.

기존 원시 trace만 받는 호출도 지원한다. 요청 문맥이 없다면 진입점부터 확인된 결과까지의 흐름으로 범위를 제한하고, 요청 특화 처리 목적를 추정했다고 표시하지 않는다. 후보가 여러 개라 범위를 확정할 수 없으면 기존 후보 선택 절차를 사용한다.

공개 JSON 필드명이나 schema를 이 문서에서 새로 확정하지 않는다. 기존 입력으로 내부 처리를 구성하고, 추가 정보가 필요하면 producer·consumer와 저장 호환성을 확인한 뒤 변경 계약을 마련한다.

## 5. 관문 선정과 병합 규칙

### 5.1 의미와 실행 범위

Requested Flow는 진입 이벤트에서 처리 완료까지 이어지는 계층 간 실행 흐름이다. FlowSequence 관문은 이 흐름의 주요 판단·처리를 이해하기 위한 상위 단위이며 SemanticStep은 그 처리를 수행하는 실제 실행 단계다.

관문 요약에서 프레임워크 세부 처리를 접는 것은 허용하지만, 요청 흐름의 계층 이동을 설명하는 단계를 원본 분석이나 하위 타임라인에서 삭제해서는 안 된다. 새로운 호출·가드·상태 변경은 확인된 분석 결과에 있을 때만 표시한다.

### 5.2 요청과 인과관계에 따른 필수 관문 판정

기준 질문은 “이 처리를 설명하지 않으면 사용자가 요청한 동작을 잘못 이해하는가”다. 도메인 코드, framework, 라이브러리라는 구분은 선정 기준이 아니다. 인과관계는 분석에서 확인한 제어 흐름·값의 의존·상태 변화·실행 인계를 뜻하며, 이름의 유사성이나 실행 시간의 근접성을 뜻하지 않는다. 정적 분석 결과를 실제 실행을 관측한 기록으로 표현하지 않는다.

큐레이터는 먼저 기존 요청을 시작 상황, 알고 싶은 동작, 확인하려는 결과로 정리한다. 사용자가 말하지 않은 조건이나 원하는 결과를 보충하지 않는다. 이어서 다음 기준에 해당하는 단계와 검증된 관계를 관문 후보로 판정한다.

| 규칙 | 관문으로 드러낼 내용 | 근거 예시 |
|---|---|---|
| 규칙1 | 실행을 시작·허용·차단하는 지점 | 진입 이벤트, 접근 허용·거부 조건 |
| 규칙2 | 어느 구현이나 경로로 진행할지 결정하는 지점 | 분기 조건, 라우팅, 확인된 동적 호출 대상 |
| 규칙3 | 요청을 설명하는 데 필요한 주요 처리의 전환 | 입력 해석에서 처리 계획 수립으로의 전환과 연결 |
| 규칙4 | 요청 결과를 좌우하는 값·상태·외부 효과 | 계산·변환, 영속화, 캐시 갱신, 외부 요청 |
| 규칙5 | 결과나 순서를 설명하는 데 필요한 실행 방식 | 비동기 인계, 재시도, 트랜잭션, 취소 |
| 규칙6 | 확인된 종료 또는 더 확인하지 못한 연결 | 성공·실패·중단, 미확인 호출 경계 |

조건문·할당·호출이 존재한다는 사실만으로 필수 관문을 만들지 않는다. 예를 들어 저장이 반영되지 않는 이유를 묻는 요청에서는 캐시 무효화, 트랜잭션 종료, 비동기 완료 처리가 핵심이 될 수 있다. 접근 거부 원인을 묻는 요청에서는 인증 middleware가 핵심이다.

각 후보의 판정에는 요청의 어느 부분을 설명하는지, 생략하면 놓치는 판단·결과·실행 전환, 이를 뒷받침하는 단계 ID와 관계, 분리 또는 병합 이유를 연결한다. 이 내용은 내부 판정과 테스트에서 확인 가능해야 한다. 공개 필드를 임의로 추가하거나 내부 판정 정보를 기본 화면에 그대로 노출하라는 요구는 아니다.

관문 구성의 책임은 curator에 있다. analyzer·collector의 확인된 사실과 기존 요청 문맥을 입력으로 사용하고, presenter와 agentgateway는 이를 다시 판단하지 않는다. 영향 관계를 입증할 근거가 부족하면 중요하지 않다고 판정하지 않고 §5.4의 요약 한계로 남긴다.

역할 `entry`, `decision`, `process`, `effect`, `result`, `boundary`는 유지한다. 모든 역할을 채우거나 계층마다 관문을 하나씩 만들지는 않는다.

### 5.3 병합·분리와 재검토

- 병합1: 여러 단계를 하나의 처리 목적으로 설명해도 요청에 필요한 판단·결과·실행 인계가 가려지지 않아야 한다.
- 병합2: 확인된 실행 연결을 따라 묶으며, 내부 조건과 서로 다른 실패 이유를 자식 단계와 관계로 보존한다.
- 병합3: 다른 함수·파일·계층도 같은 처리를 뒷받침하면 묶을 수 있다. 같은 함수나 계층이라는 사실만으로 병합하지 않는다.
- 병합4: 독립적으로 설명해야 할 조건·상태 변화·외부 효과·인계·결과·분석 경계가 가려지면 분리한다.
- 병합5: 연결이나 의미가 불확실하면 보수적으로 분리하되 요약에 성공했다고 판정하지 않는다. 제목 유사도나 순번만으로 합치지 않는다.

첫 구성이 끝나면 인접 관문을 합쳐도 필요한 구별이 남는지 검사한다. 남는다면 병합한다. 반대로 한 관문 안에 반드시 드러내야 할 별도 판단이나 전환이 숨겨졌다면 분리한다. 후보 판정과 같은 근거를 사용하며 같은 입력에서 판정 순서가 바뀌어 결과가 달라지지 않도록 결정적인 규칙을 적용한다.

연속 검증문이라도 권한 확인과 결제 한도 판정처럼 서로 다른 핵심 판단이면 분리한다. 요청 구성과 직후 외부 요청처럼 하나의 처리를 설명하고 별도 판단을 가리지 않는 단계는 묶을 수 있다. 함수 진입·복귀 중 같은 심볼이 다시 나타나는 것만으로 재귀로 묶지 않는다.

반환식 묶음은 같은 호출 문맥에서 하나의 return 문장 범위에 포함된 계산 호출과 반환 단계가 확인된 정상 진행으로 연결될 때 적용한다. 별도 조건 판단·상태 변경·외부 효과가 포함되면 분리한다. 하나의 미확인 호출이 포함된 경우 그 호출을 대표 단계로 삼고 분석 경계와 unknown 상태를 유지하므로 경계를 숨기지 않는다. 서로 다른 미확인 호출 여러 개는 독립 경계로 남긴다. 이름이 같거나 줄이 가깝다는 사실은 이 묶음의 근거가 아니다. 제목은 확인된 함수의 ‘반환’으로 표현하고 사업 의미를 만들어내지 않는다.

한 반환식의 내부 조건만으로 값을 선택하는 경우에는 ‘반환값 판단’ 관문으로 묶을 수 있다. 이 경우 구성 단계는 같은 반환 문장 범위의 branch와 마지막 return으로 제한한다. 각 판단의 두 결과가 명시되어야 하고, 모든 내부 연결은 해당 반환으로 이어져야 한다. 다른 호출·상태 변경·외부 효과·미확인 경계·중간 외부 진입이 있으면 묶지 않는다. 첫 판단을 대표 코드로 삼고 조건 관계와 공통 반환을 자식으로 보존한다. 서로 다른 return 문장이나 독립 검증문을 이 규칙으로 합치지 않는다.

검증 조건식 내부의 단락 평가도 하나의 판단 관문으로 묶을 수 있다. 같은 호출 문맥과 guard 소스 범위 안에 있는 branch 단계들만 포함하고, 모든 내부 경로가 최종 guard 판단으로 이어지며 최종 판단의 참·거짓 연결이 관문 밖으로 보존되어야 한다. 대표 코드는 전체 guard 조건이다. 호출·상태 변경·외부 효과·미확인 경계·중간 외부 진입이 있으면 적용하지 않는다. 서로 다른 guard 문장과 실패 반환은 별도 관문으로 유지한다. 이 규칙은 연속된 독립 검증문들의 목적이 같다는 추론을 허용하지 않는다.

### 5.4 관문 수, 제목과 요약 품질

4~7개는 요약 결과를 살피는 참고 범위다. 개수를 맞추기 위해 합치거나 나누지 않는다. 실제 1~3개 처리만 있는 흐름에는 관문을 추가하지 않고, 서로 다른 필수 판단이 8개라면 8개를 보여 준다. 점수와 순위는 필수 판단을 숨기는 근거가 될 수 없으며 기본 화면에 노출하지 않는다.

구조적으로 유효한 결과와 의미 요약에 성공한 결과를 구분한다. 참조·근거 검증을 통과해도 묶음의 의미를 판단하지 못해 단계별 나열이 남았다면 “일부 처리를 관문으로 묶지 못했습니다”라고 알리고 해당 관문을 식별할 수 있게 한다. 코드 탐색은 제공하지만 완성된 요약으로 평가하지 않는다. 반대로 독립적인 필수 판단이 많아 관문 수가 큰 결과는 그 이유만으로 요약 실패가 아니다.

요약 한계는 코드 근거의 `verified`·`partial`·`unknown`과 별개다. 묶음의 의미가 불확실하다는 이유로 검증된 코드를 미확인 코드로 바꾸거나, 요약에 성공했다는 이유로 근거 상태를 승격하지 않는다. 한계 정보는 동일 분석의 저장·재조회·MCP와 FlowView에서 보존해야 한다. 기존 metadata로 표현할 수 없는 경우 호환 가능한 표현 계약을 구현 전에 확정한다.

관문 제목은 근거가 있는 처리 목적을 사용한다. 목적을 확인하지 못하면 확인된 기술 동작으로 표시하고 의미 확인의 한계를 알린다. 모델 라벨 제안은 제목·설명의 보조 수단이며 단계 소속·역할·연결·검증 상태를 바꾸지 못한다.

### 5.5 대표 단계

`primaryStepRef`는 관문의 판단·상태 변화·외부 요청 등을 가장 직접적으로 보여 주는 실제 자식 단계다. 항상 `stepRefs`에 포함되어야 한다. `entry`는 진입 이벤트를 대표하고, `boundary`는 마지막으로 확인한 관련 호출 또는 단계를 대표한다. 존재하지 않는 boundary용 실행 문장을 만들지 않는다.

### 6.1 생성 책임

원본 분석과 요청 문맥 → curator의 단일 관문 생성 → 참조·근거 검증 → 저장된 분석 결과 → FlowView 및 MCP 표현 순서로 처리한다.

구현 함수명은 별도 선택할 수 있으나 동일 규칙의 복제 구현은 허용하지 않는다. 새 분석의 저장 진입점에는 검증된 관문이 있어야 한다. 기존 호출자가 이를 제공하지 못하면 동일한 생성 책임을 호출하도록 연결하고, 저장 전용 대체 알고리즘을 만들지 않는다.

전체 원시 trace와 요청 흐름에 포함된 단계의 범위가 다르면 기존 범위 판정 결과를 사용한다. 필터링 이후의 단계 수를 원본 전체 분석의 완전성으로 표현하지 않는다. 선택되지 않은 분석 정보도 저장 계약을 우회해 삭제하지 않는다.

`codeflow curate`와 원시 trace API도 같은 semantic projection과 관문 생성 규칙을 사용한다. CLI의 기존 `flowId`·`frames` 응답은 유지하고 원본 의미 단계·연결·미확인 사유를 `steps`·`edges`·`unknowns`로 전달한다. 요약 한계가 있으면 `summaryLimitations`를 함께 전달한다. 순회 중단은 전체 분석의 미확인 사유로 보존한다. 원시 trace의 함수명 반복만으로 재귀를 만들거나, 인접한 조건 검사를 근거 없이 병합하거나, 고정 관문 상한에 맞춰 중요한 처리를 합치지 않는다. CLI는 출력 전 참조 유효성을 검증한다.

### 6.2 포함 관계와 실행 관계

각 단계의 부모 관문과 단계 사이의 실행 연결을 별도로 관리한다. `stepRefs`는 소속과 읽기 순서를 나타내며, 나란히 배치됐다는 이유로 연속 실행을 뜻하지 않는다. 단계의 단일 부모 규칙은 실제 호출 그래프에 복수의 선행 단계가 존재하는 것을 금지하지 않는다.

| 관계 규칙 | 요구 동작 |
|---|---|
| 관계1 | 한 관문 내부에서 갈라지는 경로는 조건별로 구분하고 원래의 단계 연결을 유지한다. |
| 관계2 | 서로 다른 주요 처리로 갈라지면 별도 관문으로 분리하고 관문 간 조건부 연결을 원본 단계 관계에서 도출한다. |
| 관계3 | 여러 관문 뒤의 공통 후속 처리는 한 번만 소속시킨다. 양쪽 관문에 복제하거나 한쪽 분기의 전용 자식으로 표현하지 않는다. |
| 관계4 | 공통 후속 처리가 분리된 주요 처리라면 공통 후속 관문을 만들고 합류 연결을 표시한다. 분기 전체가 하나의 처리라면 같은 부모 안에 공통 자식을 한 번 두고 내부 합류를 표시한다. |
| 관계5 | 재귀·재시도는 확인된 되돌아가는 연결을 표시한다. 이미 구분된 실행 단계 ID를 합치거나 단계를 무한 복제하지 않는다. |
| 관계6 | 비동기 연결은 확인된 인계·대기 관계만 표시한다. 확인되지 않은 완료 순서나 동기 합류를 만들지 않는다. |

관문 간 연결은 소속 관문이 다른 실제 단계 간 연결에서만 생성한다. 연결마다 원래 단계와 조건의 근거를 추적할 수 있어야 한다. 서로 다른 조건을 단순 중복으로 제거하지 않는다. 같은 공통 단계를 여러 경로가 참조하는 것과 별도 호출 지점의 서로 다른 단계를 혼동하지 않는다. 심볼 이름이 같다는 이유로 별도 실행 단계를 하나로 합치지 않는다.

### 6.3 검증과 복잡도

저장 전에 대표·자식 참조 존재, 단일 부모, 요청 범위 내 단계 보존, 알려진 순서 및 연결 일관성, 근거 상태를 검증한다. JSON 형태 검증만으로 이 검증을 대체하지 않는다. invalid 결과는 새 정상 뷰로 저장하지 않는다.

단계와 관계는 ID 인덱스로 조회한다. 동일 단계를 찾기 위해 전체 배열을 반복 탐색하는 방식은 대규모 입력에서 검토한다. 현재 명세만으로 처리 시간이나 선형 실행 복잡도 달성을 주장하지 않는다.

### 6.4 표현 계층의 책임과 큰 흐름

의미를 결정하는 관문 구성과 관계는 curator의 결과를 사용한다. UI는 배치·강조·표현을 담당하며 관문 재병합, 호출 추정, 근거 상태 승격을 하지 않는다. 전체 관계가 없는 데이터를 그래프처럼 보이게 만들기 위해 이웃을 연결해서는 안 된다.

동일 분석의 관계·조건·요약 한계가 저장과 HTTP·MCP에서 보존된다는 기존 요구를 전제로 한다. 현재 공개 형식이 필요한 정보를 담지 못하면 producer·consumer를 함께 검토해 호환 가능한 계약을 먼저 확정한다. 이 문서는 기존 필드가 이미 충분하다고 주장하지 않는다.

큰 흐름에서는 같은 참조를 찾기 위한 반복 전체 검색을 줄이고, 긴 코드와 목록은 필요할 때 렌더링할 수 있다. 가상화가 선택·초점·관계 이동·텍스트 접근성을 깨뜨리면 적용하지 않는다. 처리 속도를 위해 단계나 연결을 삭제하지 않는다. 점진적 공개는 허용하지만 생략된 내용의 존재와 접근 방법을 제공한다.

외부 그래프 서비스나 원격 분석 서비스로 코드를 전송하지 않는다. 기존 로컬 실행·인증·secret redaction 경계를 유지한다. 오류와 관계 이름을 포함한 사용자 코드 유래 텍스트는 실행 가능한 HTML로 삽입하지 않는다.

## 7. 화면과 사용자 동작

### 7.1 정보 배치와 화면 역할

**고정 제약은 흑백 테마, 요청 흐름의 빠르고 정확한 이해, 코드 근거와 탐색 맥락의 보존이다.** 영역의 위치, 열 수, 읽기 방향, 관계도·목록·단계별 탐색의 선택은 고정하지 않는다. 아래 표는 초기 비교안이다. 정보 역할을 지킨다는 것은 모든 영역을 동시에 보여 주거나 반드시 같은 위치에 둔다는 뜻이 아니다.

| 영역 | 사용자의 질문 | 기본 표시 | 선택 후 표시 |
|---|---|---|---|
| 요청 영역 | 무엇을 분석한 결과인가? | 요청 문장, 분석 대상, 기존 다시 분석·비교 조작 | 선택한 경로 조건과 해제 조작 |
| 상단 FlowSequence | 전체 흐름이 어떻게 이어지는가? | 관문 제목과 방향·조건을 가진 관계 | 선택 관문, 조건부 경로, 합류·경계 강조 |
| 좌측 실행 탐색 | 이 관문은 어떤 단계로 구성되는가? | 관문 제목, 펼치기, 자식 수 | 단계 목록, 내부 분기·합류, 현재 선택 |
| 중앙 코드 | 지금 어떤 코드와 판단을 읽는가? | 선택한 대표 코드와 주변 문맥 | 자식 코드, 도달 조건과 직접 전후 처리 |
| 우측 직접 관계 | 이 코드가 무엇을 호출하고 누가 호출하는가? | 선택 단계의 확인된 직접 관계 | 요청 흐름 밖의 관계임을 구분한 탐색과 복귀 |

상단은 관문을 재선별하지 않고 같은 분석의 전체 관문을 사용한다. 좌측은 단계 소속을 보여 준다. 두 영역은 같은 선택 상태를 공유하되 똑같은 상세 카드를 반복하지 않는다. 중앙의 전후 처리는 현재 Requested Flow 안의 실행 연결이고, 우측 관계는 코드의 직접 호출 관계다. 두 종류를 하나의 ‘다음 단계’ 목록으로 섞지 않는다.

데스크톱의 초기 비교안은 상단 요약과 기존 3열이다. 단계별 집중 화면, 코드 중심 문맥 탐색, 전체 개요와 상세 전환 등도 같은 사용자 과제로 비교할 수 있다. 상단 관계도는 코드 읽기 공간을 밀어내지 않도록 독립된 접기·펼치기를 제공한다. 이를 접으면 요청, 선택 관문과 경로 조건을 한 줄로 남기고 ‘전체 흐름 보기’를 제공한다. 접기는 분석 결과나 선택을 바꾸지 않는다.

### 7.2 상단 인과관계 표현

#### 7.2.1 관문과 관계

초기 관계도안은 위에서 아래로 읽고 대안 분기를 옆으로 분리한다. 실제 과제에서 더 잘 이해되는 방향·표현을 선택할 수 있지만 같은 화면에서 읽기 방향이 일관되고 관계 의미가 보존되어야 한다. 관문에는 제목·역할·관련 한계만 표시한다. 소스 본문, 모든 자식, 긴 기술 경로는 상단 카드에 넣지 않는다. 긴 제목은 펼쳐 확인할 수 있어야 하며 hover만으로 전체 제목을 제공하지 않는다.

| 관계 | 표시 의미 | 금지 사항 |
|---|---|---|
| 순차 연결 | 확인된 방향 화살표 | 배열상 이웃 사이에 자동 연결 생성 |
| 조건부 분기 | 분기점의 조건과 경로별 이름 | false 조건을 근거 없이 계산하거나 성공 경로를 기본값으로 선택 |
| 배타적 합류 | 공통 후속 관문과 들어오는 연결 | 병렬 작업 완료를 기다리는 것으로 표시 |
| 병렬·비동기 | 확인된 ‘인계’, ‘완료 대기’ 등의 관계명 | 인계만 확인됐는데 완료·대기 표시 |
| 반복·재시도 | 원래 관문으로 돌아가는 연결과 관계명 | 실행 횟수를 추정하거나 관문을 계속 복제 |
| 미확인 연결 | 마지막 확인 지점에 ‘다음 연결 미확인’ | 정상 종료 화살표로 대체 |

흑백 선의 방향·형태, 관계명과 조건을 함께 사용한다. 연결 교차점과 실제 합류 지점을 구별한다. 자동 배치 실패나 복잡한 교차로 읽기 어려운 경우 동일 관계의 목록 표현으로 전환할 수 있어야 한다. 목록에는 출발·조건·관계·도착과 선택 조작이 있어야 하며 생략된 관계가 없어야 한다.

#### 7.2.2 관계 선택과 경로 강조

관문 클릭은 대표 단계 선택이다. 연결의 조건 조작은 경로 강조이며 코드 선택과 분리한다. 연결의 ‘근거 보기’를 누른 경우에만 그 조건·연결을 뒷받침하는 단계를 선택한다. 조건에 해당하는 소스를 확인하지 못하면 조작을 허위 코드로 연결하지 않는다.

경로 강조는 확인된 연결을 따라 도달할 수 있는 범위만 표시한다. 관문 전체가 선택됐다는 이유로 내부의 모든 분기가 실행된 것처럼 강조하지 않는다. 공유 후속 단계, 순환과 미확인 연결에서 멈추거나 이어지는 규칙은 실제 관계에 따른다. 합류를 확인하지 못하면 가장 가까운 관문을 합류로 추정하지 않는다.

하나의 조건 선택 뒤 중첩 분기를 선택할 수 있다. 선택한 조건을 순서 있는 목록으로 표시하고 개별 조건과 전체 조건을 해제할 수 있게 한다. 부모 조건을 바꿔 도달할 수 없어진 자식 조건은 해제하고 변경 사실을 알린다. 기존 코드 선택이 강조 범위 밖에 있으면 코드를 바꾸지 않고 ‘현재 선택은 강조 경로 밖입니다’라고 표시한다.

이 조작은 코드로 확인한 가능한 연결을 살펴보는 기능이다. 전체 조건 조합의 실행 가능성이나 실제 실행 결과를 입증하지 않는다. 도달 범위를 계산할 근거가 부족하면 ‘직접 연결 강조’로 명칭과 범위를 제한하고 전체 경로가 확인됐다고 표시하지 않는다. 분석의 필수 관계가 누락됐다면 제품 수용 검증을 통과한 것으로 처리하지 않는다.

#### 7.2.3 많은 관문과 화면 밖 연결

7개를 넘는 관문도 같은 규칙으로 표시한다. 의미를 바꾸는 프런트엔드 재병합이나 ‘덜 중요함’을 이유로 한 삭제는 금지한다. 큰 관계도는 스크롤과 ‘선택 위치로 이동’을 제공한다. 모든 관문을 한 화면에 맞추려고 글자를 읽을 수 없게 축소하지 않는다.

화면 밖에 연결된 관문은 방향과 대상 이름을 제공하고 클릭하면 해당 위치로 이동한다. 이 표시는 연결된 추가 관문이 있다는 뜻이며 새 관문이나 새 분석을 뜻하지 않는다. 레이아웃 재계산과 라벨 도착만으로 전체 도형을 다시 중앙 정렬하지 않는다.

### 7.3 좌측 상세 탐색과 중앙 코드

좌측 관문마다 펼치기와 ‘실행 타임라인 N단계’를 항상 제공한다. 펼침과 관문 선택은 독립 조작이다. 한 단계 관문도 같은 규칙을 사용한다. 자식 단계에는 처리 목적, 해당 구현이 속한 함수·클래스 이름과 선택 상태를 표시한다. 왼쪽 탐색에서 코드 본문·조건식을 반복하지 않는다. 분석이 코드 문장만 제목으로 제공하면 확인된 소속 심볼로 표시하고 의미 있는 목적을 지어내지 않는다. 실제 호출자는 소속 함수와 구분하고 확인된 호출 관계에서만 표시한다. 번호는 읽기 순서이며 배타적 경로의 실행 순서가 아니다.

내부 분기는 조건별 묶음으로 표시하고 공통 후속 단계는 한 번만 표시한다. 같은 관문의 분기 간 이동은 부모 선택을 유지한다. 다른 관문으로 갈라지면 상단의 해당 관문으로 이동할 수 있는 연결을 제공한다.

중앙의 고정 문맥은 다음과 같다.

- 문맥1: 현재 관문명과 선택한 실행 단계명. 두 항목을 시각적으로 구별한다.
- 문맥2: 해당 코드로 도달하는 확인된 조건. 여러 경로가 합류하면 선행 경로 목록을 펼칠 수 있다.
- 문맥3: 현재 Requested Flow 안의 직접 선행·후속 처리. 후보가 여러 개면 선택 목록을 제공하며 임의로 하나를 다음으로 정하지 않는다.
- 문맥4: 선택 단계의 파일·심볼·코드 범위와 정밀도. 대표 관문의 경로를 자식의 경로로 잘못 사용하지 않는다.

기본 코드는 선택한 문장과 이해에 필요한 주변 문맥을 보여 준다. 코드 더 보기와 접기는 코드 스크롤을 보존한다. 관문·단계·근거를 명시적으로 선택하면 같은 파일 안에서도 목표 코드 범위가 보이도록 이동한다. 이미 보이는 범위는 불필요하게 재정렬하지 않고, 라벨·레이아웃 변경만으로 읽던 위치를 바꾸지 않는다. 근거 줄 표시와 실행 결과 표시를 혼동하지 않도록 ‘선택 문장’으로 안내한다.

우측에서 요청 흐름 밖의 관계를 탐색할 때에는 ‘요청 흐름 밖의 직접 관계’라고 알린다. 확인된 소스 문맥을 열거나 기존 명시적 흐름 열기 절차를 사용한다. 관계 클릭이 원래 Requested Flow에 새 단계를 삽입하지 않는다.

### 7.4 상태와 탐색 복원

| 동작 | 관문 선택 | 실행 단계 선택 | 화면 결과 |
|---|---|---|---|
| 관문 클릭 | 클릭한 관문 | 그 관문의 대표 단계 | 중앙에서 대표 코드와 주변 문맥 표시 |
| 펼치기 클릭 | 유지 | 유지 | 해당 관문의 자식만 펼치거나 접음 |
| 자식 클릭 | 그 자식의 부모 | 클릭한 단계 | 관문 맥락 유지, 해당 문장 강조 |
| 다른 관문 선택 | 새 관문 | 새 대표 단계 | 이전 관문의 펼침 상태 유지 |
| 선택한 자식의 부모 접기 | 유지 | 유지 | 중앙 코드는 유지하고 부모에 현재 선택 표시 |

| 상태 | 소유·수명 | 변경 계기 |
|---|---|---|
| 분석 결과와 baseline | 기존 저장·분석 계약 | 명시적 분석·비교 성공 |
| 관문·단계 선택 | 현재 뷰의 공통 상태 | 관문·단계·근거 선택 |
| 관문 펼침과 코드 확장 | 현재 뷰의 독립 상태 | 각 펼치기 조작 |
| 조건별 강조 | 현재 뷰의 독립 상태 | 경로 선택·해제 |
| 상단·좌측·코드의 읽기 위치 | 각 영역의 현재 상태 | 사용자 스크롤·명시적 위치 이동 |
| 키보드 초점 | 현재 조작 요소 | 사용자 이동·명시적 탐색 복귀 |

관계 탐색으로 떠나기 전에 위 탐색 상태와 원래 뷰 식별자를 보관한다. 돌아오면 동일 분석의 상태를 복원한다. 대상 요소가 더 이상 없으면 가장 가까운 상위 조작 요소에 초점을 복원하고 이유를 알린다. 문서 전체 스크롤만으로 패널별 위치 복원을 대체하지 않는다.

새로 연 다른 뷰는 첫 관문의 대표 단계를 기본 선택하고, 브라우저 뒤로 가기로 돌아온 같은 뷰는 보관한 탐색 상태를 복원한다. 새 탭·새 세션의 저장 뷰는 저장된 분석을 복원하되 이전 세션의 탐색 위치까지 영구 저장한다고 보장하지 않는다. 탐색 상태를 저장된 분석 bytes에 덮어쓰지 않는다.

명시적 재분석에 대해 기존 대응 규칙을 적용한다. 유일한 대응과 부모 관계가 확인된 선택만 복원하며 조건 강조도 새로운 관계와 대응될 때만 유지한다. 복원할 수 없는 항목은 알리고 임의 선택하지 않는다. 실패·취소·늦은 응답에서는 기존 코드와 상태를 보존한다.

레이아웃 크기 변경이나 요약 라벨 도착은 분석 선택·baseline을 바꾸지 않는다. 코드 영역을 보여 주기 위한 스크롤과 키보드 초점 이동을 분리한다. 일반 관문 클릭은 조작 초점을 유지하고 ‘코드로 이동’을 명시적으로 실행했을 때 코드 영역에 초점을 준다.

### 7.5 한계·로딩·실패의 제품 표현

| 상태 | 표시 위치와 문구 예시 | 가능한 행동 |
|---|---|---|
| 의미 요약 한계 | 해당 관문 ‘처리 묶음 미확정’ 및 전체의 한계 안내 | 상세 단계 확인 |
| 실행 연결 미확인 | 해당 연결 끝 ‘다음 호출 대상을 확인하지 못했습니다’ | 마지막 확인 코드 보기 |
| 정확한 문장 범위 없음 | 코드 영역 ‘주변 코드 · 정확한 문장 범위 미확인’ | 주변 문맥 확장 |
| 저장 소스 없음 | 코드 영역 ‘이 분석에 보존된 소스가 없습니다’ | 명시적 다시 분석 |
| 분석 중 | 요청 영역의 진행 상태, 기존 뷰 유지 | 취소 |
| 최초 조회 중 | 읽을 수 있는 로딩 안내 | 요청 취소·이전 화면 복귀 |
| 조회 실패 | 해당 요청의 오류와 대상 | 같은 읽기 요청 재시도 |
| 관계 조회 실패 | 우측 영역의 국소 오류 | 해당 관계만 재시도 |
| 미지원 과거 관계 표현 | ‘저장된 분석에 관계 정보가 부족합니다’ | 기존 코드 탐색, 명시적 다시 분석 |
| 유효하지 않은 참조 | 결과 적용 거부, 기존 뷰 유지 | 오류 확인과 명시적 다시 분석 |

안내문에는 문제의 위치, 확인하지 못한 내용, 가능한 다음 행동을 담는다. 일반 사용자에게 내부 schema·규칙 버전·처리 순번 등으로 원인을 대신 설명하지 않는다. 기술 진단은 기존 진단 경로에 둔다.

상태는 명도만으로 구분하지 않는다. 전체를 가리는 오류 모달은 정상 코드 탐색이 가능한 국소 실패에 사용하지 않는다. 모델 라벨 실패는 정적 텍스트를 유지하며, 관계·소스의 실패를 라벨 오류로 감추지 않는다. 자동 재분석으로 오류를 숨기거나 저장된 분석을 현재 코드로 교체하지 않는다.

### 7.6 접근성, 반응형과 긴 콘텐츠

- 품질1: 마우스 없이 관문·자식·조건·관계 선택, 펼치기, 코드 문맥 확장과 복귀가 가능하다. Tab은 조작 요소로 이동하고 Enter·Space는 버튼을 실행한다. Escape는 일시적인 패널·목록을 닫고 원래 조작에 초점을 돌린다.
- 품질2: 연결 그래프와 동등한 텍스트 관계 목록을 제공한다. 그래프를 읽기 어려운 환경에서도 출발·조건·도착과 근거 이동이 가능해야 한다. 그래프와 목록이 보조기기에 같은 내용을 중복 낭독하지 않도록 활성 표현을 구분한다.
- 품질3: 선택, 키보드 초점, 경로 강조와 미확인 상태는 흑백 안에서 구별되는 테두리·선형·텍스트로 표시한다. 움직임 감소 환경에서는 자동 이동 애니메이션을 생략한다.
- 품질4: 각 관문의 접근 가능한 이름에 제목·단계 수·펼침 상태를 제공한다. 간단한 선택 결과만 상태 알림으로 전달하며 소스 본문 전체를 다시 읽지 않는다.
- 품질5: 3열 기본안을 사용하는 좁은 창에서는 코드를 우선하고 좌측·우측을 명시적으로 여닫는 패널로 전환한다. 다른 배치도 같은 과제의 접근성과 상태 보존을 충족해야 한다. 패널 닫기와 복귀를 제공하며 선택·펼침 상태는 유지한다. 숫자 breakpoint는 코드와 조작이 겹치기 시작하는 실제 레이아웃 검증으로 정한다.
- 품질6: 코드 자체의 가로 스크롤은 허용하되 페이지 전체가 긴 심볼·조건문 때문에 가로로 밀려나지 않는다. 긴 조건과 제목은 키보드로 전체 내용을 볼 수 있다.
- 품질7: 화면 확대, 긴 한국어·영문 혼합 제목, 깊은 분기와 큰 글꼴에서 버튼·초점·연결 라벨이 가려지지 않아야 한다.

지원 플랫폼은 기존 제품의 실제 실행 환경을 유지한다. 새 모바일 서비스나 추가 브라우저 지원을 약속하는 문서가 아니다. 출시 검증 보고서에는 시험한 브라우저·창 크기·확대 조건을 명시한다.

### 7.7 흑백 시각 체계와 디자인 자유도

- 테마1: 배경·텍스트·선·아이콘·코드 강조·선택·경고를 흑백과 중간 회색으로 구성한다. 상태나 분기를 구별하려고 유채색을 추가하지 않는다. 문법 강조도 무채색·굵기·밑줄 등을 사용하고 코드 가독성으로 검증한다.
- 테마2: 선택은 명확한 테두리·반전과 선택 표시, 키보드 초점은 별도의 외곽선, 미확인 연결은 점선과 문구 등으로 구별한다. 세부 스타일은 검증으로 조정하되 선택·초점·근거 상태가 혼동되지 않아야 한다.
- 테마3: 중요 정보는 옅은 회색만으로 표현하지 않는다. 강조되지 않은 대안 경로도 읽을 수 있어야 하며 색각·hover·애니메이션에 의존하지 않는다.
- 테마4: 장식, 내부 분석 수치, 불필요한 화면 전환을 기본 화면에 추가하지 않는다. 모든 시각적 요소와 조작은 요청 흐름 이해·근거 접근·맥락 복원 중 어떤 목적을 돕는지 설명할 수 있어야 한다.

탐색 방식은 실제 사용 과제로 선택한다. 전체 관계도와 상세 레일, 개요에서 선택 부분으로 집중하는 방식, 코드 옆에서 선행 조건·후속 처리를 따라가는 방식 등을 비교할 수 있다. 특정 스타일이 보기 좋다는 이유만으로 채택하지 않는다. 여러 대안을 제품의 여러 모드로 전부 제공해야 한다는 요구도 아니다.

대안 평가에서는 사용자에게 동일한 Requested Flow의 시작·주요 판단·결과 설명, 조건별 경로 구별, 근거 문장 찾기와 복귀를 수행하게 한다. 경로 오해·핵심 누락·잘못된 코드 선택을 먼저 비교하고, 이 정확성을 충족한 대안 사이에서 시간과 불필요한 이동을 비교한다. 빠르지만 잘못 이해하게 하는 안은 채택하지 않는다.

## 8. 저장, 재분석과 호환성

- 보존1: 기존 `viewId`는 저장된 관문과 근거를 복원한다. 화면을 열었다는 이유로 새 규칙을 적용해 저장 내용을 덮어쓰지 않는다.
- 보존2: 과거 뷰의 관문이 7개를 넘거나 1:1로 구성돼 있어도 새 생성 규칙을 소급해 정상 데이터로부터 제거하지 않는다.
- 보존3: 관문이 없는 과거 형식은 기존 지원 계약을 유지하되, 새 규칙을 적용한 결과로 위장하지 않는다. 현재 코드 분석이 필요한 경우 명시적 재분석을 안내한다.
- 보존4: 명시적 재분석은 새 결과를 검증한 뒤 새 뷰로 저장한다. 이전 뷰와 소스 근거는 유지한다.
- 보존5: 같은 분석 안에서는 ID로 선택을 복원한다. 재분석 사이에서는 안정된 단계·관문 대응이 유일하고 부모 관계가 일치할 때만 복원한다. 제목이나 순번만으로 대응하지 않는다.
- 보존6: 대응이 모호하거나 실패하면 기존 화면과 비교 기준을 유지한다. 새 결과 적용은 기존 명시적 선택 절차를 따른다.

규칙 버전의 구분이 필요하다면 기존 저장 metadata에 호환 가능한 방식으로 기록할 수 있는지 먼저 확인한다. 필수 공개 필드 추가나 저장 형식 변경은 이 문서만으로 실행하지 않는다. 데이터 일괄 마이그레이션은 요구하지 않는다.

## 9. 실패와 경계 동작

| 상황 | 요구 동작 |
|---|---|
| 단계가 0개 | 근거 있는 단계가 없음을 알리고 관문을 만들지 않는다. |
| 실제 단계가 1~2개 | 존재하는 처리만 표시한다. 가짜 result·decision을 생성하지 않는다. |
| 필수 결정이 7개 초과 | 각 결정을 보존하며 스크롤로 접근 가능하게 한다. 초과를 분석 실패로 처리하지 않는다. |
| 단계 참조 누락·중복 부모 | 새 결과 저장·적용을 거부하고 기존 뷰를 유지한다. |
| 요청 범위가 모호함 | 후보 선택을 사용하고 서로 다른 흐름을 임의로 합치지 않는다. |
| 의미 묶음이 불확실함 | 보수적으로 분리하고 요약 한계를 표시한다. 코드 탐색은 유지하되 요약 성공으로 판정하지 않는다. |
| 외부·동적 연결 미확인 | 마지막 확인 지점과 분석 경계를 표시한다. 구현 부재나 성공으로 판정하지 않는다. |
| 반복 심볼·재귀 | 호출 근거로 구별하고 보존된 반복·종료 범위를 표시한다. 반복 이름만으로 재귀 판정하지 않는다. |
| 소스 없음·근거 불일치 | 코드 위치를 추정하지 않는다. 한계를 표시하고 필요한 명시적 재분석을 안내한다. |
| 라벨 실패·지연 | 정적 제목을 유지한다. 이전 요청 응답은 현재 분석을 바꾸지 못한다. |
| 재분석 실패·취소·늦은 응답 | 기존 선택, 펼침, 읽던 위치와 baseline을 유지한다. |
| 권한 없는 조회·저장 | 기존 인증·권한 검사를 유지하며 새로운 우회 경로를 만들지 않는다. |

## 10. 가정과 구현 선택

| ID | 가정 또는 선택 | 틀릴 때 영향 | 확인 방법 |
|---|---|---|---|
| ASM-01 | 기존 요청 문맥과 분석 근거로 요청 결과에 필요한 처리와 인과관계를 식별할 수 있는 사례가 있다. | 요청별 그룹을 만들 수 없으므로 보수적인 기술 동작 표현과 범위 한계 표시가 필요하다. | 서로 다른 요청을 같은 진입점에 적용해 근거 기반 관문 구성이 가능한지 확인한다. |
| ASM-02 | 현재 식별자로 같은 분석의 관문과 단계를 일관되게 공유할 수 있다. | producer·consumer 및 저장 호환 변경 계약이 필요하다. | 실제 응답·저장·MCP fixture로 필드와 identity를 비교한다. |
| ASM-03 | 세부 단계가 충분히 수집돼 있다. | 관문 UI만 개선해도 없는 실행 근거를 만들 수 없다. | 수집 단계와 소스 대조 후 누락은 별도 분석 한계로 기록한다. |

필수 관문 판정 규칙을 구현하는 내부 함수 구조는 구현 단계의 선택이다. 모델 의존은 요구하지 않는다. 근거 없는 처리 목적·인과관계 추론을 허용하거나 기존 공개·저장 계약을 변경해야 한다면 이 명세의 단순 구현 선택으로 처리하지 말고 별도 변경 결정을 기록한다.

### 10.1 화면 구현·출시 전 확정 사항

| ID | 항목 | 영향과 처리 |
|---|---|---|
| ASM-UX-01 | 기존 분석 결과가 조건·인계·합류를 구별할 근거를 제공한다. | 부족하면 명시적 한계 표현을 사용한다. 지원 범위 확대나 schema 변경은 별도 계약으로 확인한다. |

### 10.2 반환과 호출 진입점의 추가 전달 계약

새 Core는 slice 요청의 `opts.includeExecutionSemantics=true`로 확장 필드 지원을 알린다. 해당 옵션이 없는 이전 호출에는 기존 단계 종류와 필드만 반환한다. 지원하지 않는 분석기는 기존 결과를 반환할 수 있으며 소비자는 없는 실행 근거를 추정하지 않는다.

지원 응답은 `return`·`throw` 단계를 원본 문장 범위와 함께 보존한다. 각 단계의 선택 필드 `invocationId`는 해당 정적 호출 문맥을 구별한다. 하위 호출의 `callerStepOrdinal`은 호출을 발생시킨 단계를 가리킨다. 같은 문맥의 단계는 파일·심볼·호출자 참조가 같아야 한다. 연결의 선택 필드 `targetStepOrdinal`은 같은 payload에서 실제 수집된 대상 문맥의 첫 단계를 가리킨다. 본문이 없거나 깊이 제한·순환으로 진입점을 수집하지 못하면 이 값을 만들지 않는다. 배열상 다음 단계나 같은 이름의 첫 함수를 대신 쓰지 않는다.

반환은 해당 함수에서 호출자로 제어를 돌려주는 문장이고, 예외는 catch에서 처리되거나 finally를 거칠 수 있다. 반환·예외 종류만으로 Requested Flow 전체의 최종 결과나 종료를 확정하지 않는다. 명시적인 복귀·예외 관계가 없으면 이를 추정해 만들지 않는다.

Core는 ordinal 중복 여부, 대상 ordinal과 invocation 존재, 대상 심볼·파일 일치, 해당 invocation의 첫 단계 여부, 대상의 호출자 참조와 연결의 출발 ordinal 일치를 검사한다. 잘못된 명시적 참조는 오류로 처리하며 모호한 이름 탐색으로 되돌아가지 않는다. 선택 필드가 없는 과거 결과에는 기존의 유일한 대상 검사와 미확인 표시를 유지한다. 동일 함수의 별도 호출은 단계 식별자가 충돌하지 않아야 한다. FlowSpec의 선택 invocation·target 참조도 저장과 공통 투영에서 보존한다.

새 schema는 과거 payload를 계속 읽는다. 이전 Core가 새 adapter에 요청할 때는 지원 옵션이 없으므로 확장 응답을 받지 않는다. 기존 저장 뷰는 변경하지 않으며 새 의미 계약은 slice 캐시 키에도 반영한다. 이 계약은 실제 실행 기록을 추가하거나 코드 근거의 검증 상태를 승격하지 않는다.

### 10.3 함수 내부 제어 흐름의 전달

실행 정보 지원 응답은 같은 invocation 안에서 AST로 확인한 후속 처리 관계를 `control_flow` 연결로 보존한다. 출발·대상 ordinal을 모두 명시하며 대상은 해당 함수의 진입 단계로 제한하지 않는다. Core는 두 단계의 같은 호출 문맥·파일·심볼을 확인한다. 다른 invocation으로 이동하는 호출 연결에는 §10.2의 진입점·호출자 검사를 그대로 적용한다.

제어 흐름은 소스에서 가능한 정상 진행이며 실제 실행 기록이나 호출된 함수의 정상 반환 보증이 아니다. 조건의 양쪽 처리는 서로 직렬 연결하지 않고, 가능한 정상 완료 지점만 다음 처리와 연결한다. return·throw 뒤의 같은 블록 문장에 정상 진행 연결을 만들지 않는다. 예외·finally·라벨 이동처럼 관계를 충분히 확인하지 못한 구간은 연결을 생략하고 미확인 범위를 남긴다. 전역 단계 배열의 인접 여부로 관계를 만들지 않는다.

제어 흐름의 존재만으로 같은 처리 목적이 입증되지는 않는다. 관문 병합에는 §5.3의 의미 기준과 판단·효과·분석 경계 보존 기준을 함께 적용한다.

### 10.4 선택 코드 범위와 Flow Context

Flow Context의 기존 `statement.nodeKind`는 기본 `statement` 외에 실제 선택 범위가 AST 표현식이면 `expression`, 조건문의 본문을 제외한 헤더이면 `control_header`를 허용한다. 기존 필드명과 문장 값은 유지한다. 표현식을 문장 전체라고 표시하지 않으며, 선택 범위는 원래 단계의 바이트 범위·스냅샷·소스 해시·근거와 일치해야 한다. 함수 시그니처와 선택 범위를 포함하는 호출 단위, 그 안에서 선택 범위를 감싸는 조건 구조를 별도로 제공한다. 구문 오류나 일치하는 AST 범위를 확인할 수 없는 단계는 정밀 범위를 선언하지 않는다. 정확한 위치가 확인되어도 미확인 실행 연결이나 전체 분석 상태를 검증 완료로 올리지 않는다.

### 10.5 소스 검증과 전체 분석 상태의 분리

Semantic Evidence의 선택적 `sourceValidationStatus`는 스냅샷 소스를 검증한 결과를 보존한다. 컴파일러가 전체 분석의 미확인 연결 때문에 기존 `validationStatus`를 unknown으로 유지하더라도 소스 검증 결과는 덮어쓰지 않는다. 기존 proof·공개 권한·관문 상태 판정은 기존 상태를 계속 사용한다. Flow Context는 해당 근거의 소스 검증 상태를 전달하며, 화면은 정확한 범위와 verified 소스 근거가 함께 있을 때만 ‘소스 확인’을 표시한다. 분석 경계는 ‘연결 미확인’, 그 밖의 미확인 분석은 ‘분석 미확인’으로 구분한다. 필드가 없는 과거 분석에 소스 검증 결과를 임의로 추가하지 않는다.

## 12. 검증 계획과 완료 증거

### 12.1 의미 검증

실제 소스와 요청으로 구성한 대표 사례를 먼저 정한다. 관문 생성 결과를 정답으로 복사하지 않는다. 각 사례에는 요청, 확인된 진입·결과, 필수 판단·처리·인계와 이를 선정한 요청 관련성 및 근거 위치, 허용 가능한 병합, 분리해야 하는 판단, 미확인 연결을 기록한다. 서로 다른 합리적인 관문 제목은 허용하지만 판단 누락, 근거 없는 병합과 같은 처리의 불필요한 분리는 실패다. 요약 한계 표시가 탐색을 가능하게 하더라도 의미 요약 성공의 증거를 대신하지 못한다.

필수 사례는 저장 반영 실패의 framework·실행 방식 분석, 과도한 분리와 과도한 병합, 요약 한계, 배타적 분기 이후 합류와 병렬 대기의 구별, 공통 단계와 같은 심볼의 별도 호출 구별, 연속 동일 목적 검증, 인접한 다른 판단, 7개 초과 필수 결정, 프레임워크 처리가 핵심인 요청, 여러 계층에 걸친 동일 처리, 분기·실패·비동기, 재귀와 정상 복귀, 0~2단계 및 150단계 이상 흐름이다.

### 12.2 통합 화면 검증과 출시 판단

검증1은 실제 분석 결과를 사용한 흑백 화면 시안 비교다. 3열 기본안과 과제에 적합한 다른 배치를 비교하고, 선택한 안과 제외한 안의 이유를 기록한다. 전체 인과관계 → 조건 선택 → 상세 단계 → 코드 → 관계 탐색 → 복귀의 과제를 수행한다. 시안은 구현 완료가 아니며 이 문서 작성만으로 시안 검증을 수행했다고 기록하지 않는다.

검증2는 데이터·선택·조건 상태의 동작 테스트와 실제 API·저장·브라우저 통합 검증이다. `web/flowview`의 기존 명령은 `npm run check`, `npm test`, `npm run build`다. Go 변경이 있으면 `make fmt`, `make vet`, `make test`를 수행한다. 실제 제품 FlowView 브라우저 E2E는 저장소 루트의 `make test-flowview`로 실행한다. 이 대상은 `web/live-comprehension-workspace`에서 실제 제품 서버를 열고 Playwright 과제를 수행한다.

검증3은 키보드·텍스트 관계 목록·좁은 창·확대·긴 콘텐츠·요청 취소를 실제 브라우저에서 확인한다. 자동 접근성 검사만으로 이를 대체하지 않는다.

검증4는 사용자 이해 검토다. 검토자가 소스를 기준으로 정한 주요 판단과 경로를 사용자가 설명하고 근거 코드를 찾도록 한다. 오해·누락·복귀 실패와 탐색 시간을 기록한다. 테스트 사용자 수나 속도 향상 수치를 임의로 만들지 않는다. 시간 향상을 주장하려면 같은 조건의 이전 화면과 비교한 측정이 필요하다.

출시 판단에는 각 UX-AC의 사례, 실행 환경, 증거와 미해결 항목을 연결한다. 잘못된 분기·합류 표현, 다른 코드 선택, 소스 유출, 키보드 핵심 동작 불가, 탐색 상태 손실, 실제 API 미검증은 출시를 막는 결함이다. 코드 근거는 정직하게 표시되지만 의미 요약이 부족한 사례는 지원 한계를 명시하며 해당 사례를 완전 지원으로 집계하지 않는다.

성능은 대표 대규모 입력의 최초 표시, 선택 반응, 확장, 스크롤을 측정하고 상태 손실·응답 불능을 확인한다. 합격 시간과 제품의 지원 범위는 측정 환경·사례와 함께 출시 전에 정한다. 현재는 수치 기준이 없으므로 ‘빠르다’ 또는 ‘production-ready’라고 주장하지 않는다.

## 13. 전달 순서와 미수행 항목

진행 순서는 대표 실제 분석으로 인과관계와 화면 과제 확정 → 공통 생성·저장 결과를 실제 화면에 연결 → 조건·상세·코드·복귀 동작 검증 → 실패·접근성·복잡한 사례와 사용자 이해 검증이다. 데이터와 화면은 같은 기능·수용 기준으로 진행하며 백엔드 완료만으로 화면 개선 완료를 선언하지 않는다. 결정2의 관문 수 정책 변경은 관련 기존 수용 기준과 함께 관리한다.

화면 구현은 §15에 기록했다. 후속 작업은 §16의 슬라이스로 수행하며 실제 생성·저장·MCP·브라우저를 통과한 증거로 완료를 판단한다. 기존 저장 데이터를 일괄 변환하지 않는다.

## 14. 이번 개정의 근거와 영향

- 개정1: 발견1을 반영해 도메인 분류 중심 표현을 요청의 주요 처리와 인과관계로 변경했다. §4·§5와 AC-01·02·12·15에서 입력, 판정 책임과 근거를 연결한다.

## 15. 화면 구현과 검증 기록 (2026-09-18)

### 15.1 이번 구현의 범위

구현1: 기존 `flowSequence.frames[].stepRefs`를 그대로 읽는 관문 개요와 실행 탐색을 구현했다. 다른 관문을 펼쳐도 코드 선택은 바뀌지 않으며, 자식 단계 선택은 부모 관문을 유지한다. 전체 관계는 실제 `semanticMap.edges`로만 표시한다. 같은 대상의 여러 선행 연결은 출발 단계를 구분하며 동시 완료로 단정하지 않는다.

구현2: 코드 본문은 중앙에 두고 왼쪽은 처리 목적과 소속 함수·클래스 중심으로 구성했다. 직접 전후 연결 탐색과 최초 위치 복귀를 제공한다. 선택, 보기 종류, 관문·코드 펼침, 조건 강조, 패널 위치와 키보드 초점을 복원한다. 같은 페이지 세션의 저장 화면 재진입·브라우저 뒤로 가기도 복원한다. 페이지 새로고침 이후의 탐색 위치 영구 보존은 이번 범위에 포함하지 않는다.

구현3: 초기 화면도 같은 흑백 테마로 구현했다. 요청 입력, 읽기 순서 안내, 저장 분석 카드 목록으로 구성하고 요청 진행·취소·오류 및 빈 목록 안내를 유지했다. 카드에서 저장된 분석을 열며 분석 시점은 데이터가 있을 때만 표시한다.

### 15.3 아직 통과하지 않은 출시 조건

제한1: 이번 화면 구현은 저장·MCP 경로의 관문 생성 통합을 완료한 것이 아니다. 실제 분석에서 필요한 인과 연결과 적절한 묶음이 생성되는지는 의미 생성 파이프라인의 후속 검증이 필요하다.

제한2: 현재 edge 데이터에는 각 조건의 분기별 결과와 병렬 완료 대기 근거가 충분하지 않다. UI는 직접 연결 강조·연결 종류·미확인 경계를 제공하며 완전한 조건부 실행 경로로 표시하지 않는다. UX-AC-01~05 전체 통과를 선언하지 않는다.

제한3: 실제 제품 서버의 Playwright 과제는 390px 뷰포트에서 대규모 흐름 선택과 비교 코드 패널의 경계를 확인했다. 브라우저 확대, 긴 제목과 긴 코드의 복합 조작, 실제 사용자 과제 시간·오해율, 대안 배치 비교, 보조기술 전 범위 검증은 미완료다. 이 기록은 production quality 출시 승인이나 사용자 이해도 검증 완료를 뜻하지 않는다.


### 15.4 자동 검사 결과

- 검사1: `npm run check` 오류·경고 0건, `npm test` 21개 통과, `npm run build` 통과.
- 검사2: `make fmt`, `make vet`, `make test` 통과. 최초 검사에서 이전 레이더 DOM을 요구하던 서버 테스트를 현재 계층·코드·관계 영역 검사로 갱신했다. snapshot 일관성 오류로 실패한 e2e 패키지도 별도 재실행과 전체 재실행에서 통과했다.
- 검사3: 최종 화면 번들을 서버 내장 HTML과 기존 샘플 HTML에 동기화하고 `go test ./internal/presenter/flowview`를 다시 통과했다. 소스 변경의 `git diff --check`는 통과했다. 생성 HTML 내부 Svelte 문자열의 줄 끝 공백은 의미 변형을 피하려고 유지했다.

### 16.1 VS-01 첫 구현 단위: 저장 시 관문 보존

구현 범위는 `SaveTaskView`의 입력 관문 보존과 새 저장의 참조 검증이다. 공급된 유효한 관문은 다시 생성하지 않고 선택 필드까지 보존한다. 관문이 없는 새 결과는 기존 curator 생성 진입점을 사용한다. 단계의 단일 부모·누락·대표 소속·관문과 자식 읽기 순서·분석 identity를 검증하고, 근거 없는 verified 승격과 대표 단계에 맞지 않는 소스 위치를 거부한다. 검증 실패 시 저장과 호출자 입력 변경이 없다. 진입 단계가 미확인 경계이기도 한 경우 entry 역할을 유지하되 unknown 상태로 생성·저장한다.

`TestTaskViewPreservesCuratedHierarchy`는 기존 저장기가 공급된 한 관문의 두 단계를 두 관문으로 재작성하는 실패를 먼저 확인했다. `TestTaskViewRejectsInvalidHierarchyBeforeStorage`는 기존 코드가 11가지 잘못된 참조·identity·소속을 받아들이는 실패를 확인한 뒤 수정했다. 후속 독립 검토에서 근거 상태·소스 위치·관문 역순·진입 경계의 생성과 검증 불일치를 보완했다. 현재 오류 사례는 14개다.

이 단위는 VS-01 전체 완료가 아니다. MCP compact 경로의 공통 결과 사용, 요약 한계 전달 계약, 실제 브라우저의 세 한계 동시 사례는 남아 있다. `get_flow_payload`의 compact 경로는 아직 `BuildCompactPayload`에 관문 없이 FlowSpec을 넘기며 별도로 큐레이션한다. 다음 구현은 이 경로와 새 분석 생성의 공통 결과 전달을 연결한다.


최종 코드에서 `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다. `go test ./internal/curator/semantic ./internal/presenter/flowview`도 통과했다. 저장 관문 보존과 잘못된 참조의 race 검사는 `go test -race -count=1 ./internal/presenter/flowview -run 'TestTaskView(PreservesCuratedHierarchy|RejectsInvalidHierarchyBeforeStorage)'`로 통과했다. 이후 추가한 진입 경계 사례는 최종 일반 테스트에 포함했으며 별도 race 재검사는 하지 않았다. 이번 단위에서 프런트엔드 코드는 변경하지 않았고 새 브라우저 검증은 수행하지 않았다. 부모·슬라이스 파일 링크를 검사해 모두 유효함을 확인했다.

### 16.2 VS-01 공통 생성·MCP 전달 계약

기존 `get_flow_payload`의 flowId·entrySymbolPath와 full·compact 응답은 유지한다. 선택 입력 `viewId`를 추가해 같은 불변 저장 분석을 정확히 조회한다. viewId와 다른 대상 식별자를 함께 주면 오류로 처리하며 최신 분석으로 대체하지 않는다. viewId의 full 응답은 해당 저장 뷰, compact 응답은 그 뷰의 관문을 요약한다. 읽기는 분석기를 호출하거나 저장 bytes를 다시 쓰지 않는다.

compact의 기존 `id`·`gate`·`symbol`·`steps`·`file` 필드는 유지한다. `id`는 변형된 별칭 대신 원본 관문 ID를 사용하고 `ordinal`·`primaryStepRef`·`stepRefs`를 추가해 동일 분석의 부모 소속을 확인한다. 이전 compact ID는 저장 식별자가 아닌 파생 표시 값이며 원본 ID와의 일치가 이번 계약의 우선 요구다. 바이트 위치를 40으로 나눠 행 번호를 추정하던 동작은 제거한다. source anchor에 행 근거가 없으면 파일 경로만 전달한다. 요약의 읽기 순서는 실제 실행 연결로 표현하지 않는다.

FlowSpec 복원과 compact 기본 생성은 curator의 동일 semantic projection과 관문 생성 함수를 사용한다. 이 변환은 단계 ID·종류·계층·소스·codeLens·조건·효과·상태 변화·미확인 정보를 보존한다. confidence를 검증 근거로 승격하지 않는다. ordinal이나 심볼이 모호한 연결은 확인된 것으로 만들지 않고 출발점을 알 때 미확인 연결을 남긴다. 원시 trace API의 기존 병합 규칙 개편은 VS-02에서 계속한다.

compact에는 원본 관문의 `status`도 보존한다. `radarSummary`는 직접 관계 수를 확인한 경우만 전달하는 선택 필드다. 확인하지 않은 수를 0으로 표시하지 않으며, 필드 부재는 미측정이고 명시적인 0과 다르다. 기존 내부 호출자가 확인된 수를 제공하면 이전 형태를 유지한다.

공통 생성·MCP 조회의 현재 검증은 `TestFlowPayloadMatchesExactStoredHTTPHierarchy`의 저장·HTTP·MCP full/compact 대조, `TestFlowSpecProjectionPreservesEvidenceAndAmbiguousCalls`의 원시 근거 보존, compact 상태·소스 위치 검증이다. 독립 검토에서 근거 상태 손실과 미측정 관계 수의 0 표시를 수정한 뒤 재검토를 통과했다. `make fmt`, `make vet`, `make check-naming`, 최종 `make test`가 통과했고 정확한 저장 뷰 조회 테스트는 race 검사도 통과했다. 이번 단위는 프런트엔드 변경이나 브라우저 실행 증거를 추가하지 않는다. 요약 한계 전달·화면 검증 및 원시 trace 병합 개선은 미완료다.

### 16.3 요약 한계의 전달 계약과 연결 기반 병합

`FlowSequence.summaryLimitations`를 선택 필드로 추가한다. 항목은 `code`, `message`, `frameRefs`를 가지며 `frameRefs`는 같은 분석의 실제 관문 ID를 참조한다. 현재 지원 코드는 `grouping_evidence_missing`이다. 이 정보는 코드의 verified·partial·unknown을 변경하지 않고 저장·HTTP·MCP compact·FlowView에 그대로 전달한다. 과거 필드 부재는 요약 품질 미평가이며 성공으로 해석하지 않는다. 소비자는 모르는 향후 코드를 실행하거나 의미를 추정하지 않고 전달된 안내와 대상만 표시한다.

배열상 인접만으로 일반 단계를 앞 관문에 흡수하지 않는다. 확인된 직접 연결, 같은 호출 문맥, 단일 선행·후속 처리이며 별도 판단·상태·외부 효과·인계·종료를 가리지 않는 경우만 세부 단계로 접는다. 이 제한은 이름이나 같은 파일만으로 병합하지 않기 위한 초기 정적 규칙이다. 결정을 같은 목적으로 묶는 추가 근거는 별도 분석 정보와 함께 구현한다. 마지막 배열 항목이라는 이유로 result를 만들지 않는다.

요약 한계는 연결을 확인하지 못해 세부 단계를 묶지 못한 관문에서 표시한다. 관문 수 초과 자체는 요약 실패로 표시하지 않는다. 유효하지만 의미 묶음이 부족한 결과를 기능 완전 지원으로 집계하지 않으며 실제 호출 수집·관계 전달 개선을 이어간다.


이번 구현에서 같은 파일·심볼만으로 재귀 호출을 같은 실행 문맥으로 취급하던 문제를 수정했다. 초기 병합은 확인된 `sequence`·`control_flow` 연결만 허용하며 `call`·`resolved_call`은 접지 않는다. 같은 심볼의 별도 호출이 분리되는 회귀 테스트가 수정 전 실패하고 수정 후 통과했다.

내부 `CurateFlowSpec`과 `BuildCompactPayload`는 전체 FlowSequence를 주고받도록 변경했다. 프레임 배열만 넘기며 요약 한계를 잃던 경로를 제거했고, 저장 뷰 MCP 조회도 같은 투영 함수를 사용한다. 외부 MCP 입력과 JSON 필드는 유지한다. 독립 재검토에서 두 결함의 해소를 확인했다.

검증: `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다. 프런트엔드 테스트 22건, Svelte 검사(오류·경고 0건), `make build-ui`가 통과했다. 실제 TypeScript 분석의 저장 뷰를 최신 Go 바이너리로 열어 요약 한계의 8번 관문 버튼이 해당 관문·자식 단계 선택과 코드 19행 표시를 함께 변경하는 것을 확인했다. 요약 버튼은 코드 문장 대신 구현 함수 이름을 사용한다. 요약 한계, 확인하지 못한 연결, 정확한 문장 범위 미확인이 각각 표시되고 내부 분석 식별자는 안내에서 제거됐다.

이 검증은 분석 품질 전체의 완료 증거가 아니다. 실제 checkout 분석에는 호출하지 않은 hook 내부 선언이 포함되고 API 호출 대상 연결이 누락된다. 해당 분석기 결함, 인과관계에 따른 의미 묶음, 조건 탐색 및 대규모 흐름의 사용성 검증을 계속해야 한다.


### 16.4 실제 hook 호출의 구현 대상 확인

TypeScript의 hook 반환 멤버를 호출할 때 hook 본체를 대신 실행 경로에 넣던 오류를 수정한다. 별칭을 포함한 import, 변수 선언, 반환 속성, 실제 함수 본문을 확인해 연결한다. 다른 컴포넌트의 같은 이름, 매개변수의 이름 가림, 변경 가능한 함수, 객체 멤버와 단순 별칭을 통한 쓰기는 최초 선언을 확인된 호출로 재사용하지 않는다. React useCallback의 인자를 callable로 취급할 때는 실제 react import 바인딩을 확인한다.

타입 주석과 복잡한 매개변수를 문자열 규칙으로 추측하지 않도록 TypeScript 5.9.3 구문 분석·심볼 바인딩을 사용한다. compiler host는 이미 캡처한 소스만 읽으며 주변 파일·기본 라이브러리·외부 패키지를 읽거나 파일을 생성하지 않는다. 파서는 adapter/vendor에 원본 라이선스·고지·SHA-256 manifest와 함께 포함한다. 개발용 고정 버전과 lockfile에서 `npm --prefix adapters/typescript run bundle:parser`로 재생성한다. 기존 설치기의 디렉터리 복사 후 실행 방식은 유지하며 실행 시 npm 설치가 필요하지 않다.

실제 checkout 샘플은 useCart의 전체 선언 대신 useCart.calculateTotal의 계산 본문으로 연결된다. 함수 인덱싱은 AST를 사용해 타입 주석이 있는 함수와 중첩 객체의 함수도 구별한다. API 객체의 함수 위치는 이제 찾지만 순수 return 문장을 실행 단계로 보존하는 기존 extractor의 보완은 아직 남아 있다. API 결과 표시와 전체 요청 흐름 완료를 이 단위의 성공으로 간주하지 않는다.

회귀 검사는 `slice_hook_binding.test.js`에서 호출 별칭·반환 속성·다른 컴포넌트·복잡한 매개변수·재할당·객체 별칭 변경·가짜 useCallback·타입 주석이 있는 실제 함수 본문을 검사한다. `parser_bundle.test.js`는 파서 해시와 node_modules 없는 설치 사본의 실행을 검사한다. 독립 재검토에서 발견된 허위 연결 사례를 수정하고 재현 검사로 해소를 확인했다.


현재 호출 해석과 다른 이전 캐시가 명시적 재분석에서도 재사용되는 것을 실제 화면에서 확인했다. 내부 slice 캐시 의미 버전을 변경해 이전 처리 방식의 결과를 새 분석에 사용하지 않는다. 저장된 FlowView와 과거 캐시 파일을 삭제하거나 덮어쓰지 않는다. `TestSliceCacheRejectsPriorCallBindingSemantics`는 이전 키에 있는 유효한 캐시가 재사용되면 실패하며, 수정 전 실패·수정 후 통과했다. 기존 동일 snapshot·basis 캐시 재사용 검사는 계속 통과한다.

최종 검증: TypeScript adapter 전체 검사와 설치 사본 검사, `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다. Go 통합에서 발견한 타입 지정 props의 메서드 탐색 퇴행은 interface 속성의 타입과 실제 exported class의 인스턴스 메서드를 확인하도록 수정했다. 비공개 동명 클래스와 export alias를 혼동하는 반례도 미확인으로 처리한다.

브라우저에서 이전 분석 `a46bc8480bc5a785acf8173f04991002dfaff1ae55883516c6e547f3f6f47af5`의 다시 분석을 실행했고, 새 분석 `316677b345324e4b36fafeb54dbb51f6a864c606e7accf6f34b7aea84b1be818`에서 6개 실행 단계와 계산 함수로 향하는 실제 연결을 확인했다. 별도의 캐시 없는 프로젝트에서도 같은 경로의 도착 코드가 useCart.calculateTotal의 27행을 표시했다. 이전 저장 뷰의 SHA-256은 전후 동일했다. 단계를 줄인 사실 자체가 품질 증거인 것은 아니며, 이 사례의 증거는 호출하지 않은 선언의 제거와 호출한 함수 본문의 연결이다. 순수 return 보존, 여러 문장으로 구성된 호출 대상의 진입 단계 식별, 의미 관문 묶음과 조건·대규모 사용성은 계속 구현한다.

### 16.5 반환·호출 문맥 보존 구현 중

TypeScript의 명시적 실행 정보 옵션에 한해 순수 return·throw 문장과 정적 호출 문맥, 실제 대상의 첫 단계 참조를 생성한다. 반복 호출 3건의 문맥 분리, 대상의 호출자 일치, 조건부 반환, catch·finally 보존, 직접 종료 뒤 같은 블록의 도달 불가능한 문장 제외를 검사했다. 기존 옵션 없는 요청은 이전 필드와 단계 종류를 유지한다.

독립 검토에서 미호출 콜백을 실행 경로에 포함하고 else 반환 호출을 중복 수집하는 반례가 발견됐다. 블록 전체를 문자열로 재분석하지 않고 AST 문장별로 처리하도록 바꿨으며 두 반례와 조건 함수 호출을 회귀 검사에 추가했다. 현재 TypeScript 전체 검사는 통과했다. 복합 반환식의 중첩 호출과 조건별 실행 관계, 반복문 등 제어 구문의 충분한 보존은 추가 구현·검증 대상이다.

Core의 선택 필드와 명시적 참조 검증 함수를 추가하는 중이다. 아직 Core의 요청 옵션을 활성화하거나 컴파일·저장·복원 경로 전체에 적용하지 않았다. 따라서 이 기록은 반환 단계가 실제 FlowView에 전달됐다는 증거가 아니다. 후속 작업은 참조 검증 적용, 문맥별 단계 identity, FlowSpec 투영과 반환 의미 보존, 실제 분석·브라우저 재검증이다.

현재 변경에서 `make fmt`, `make vet`, `make check-naming`과 TypeScript 전체 검사는 통과했다. `make test`는 E2E의 Next.js 샘플 게시 검사 한 건에서 workspace snapshot과 live head 불일치로 실패했다. 같은 검사를 단독 재실행한 `go test ./test/e2e -run '^TestChallenger2_PublishCoreFlow_NextJsAppFixture$' -count=1`은 통과했다. 전체 검사 성공으로 기록하지 않으며 통합 완료 시 다시 확인한다.

후속 구현에서 Core의 수신·캐시 복원과 컴파일에 명시적 실행 참조 검증을 적용했다. 같은 호출 문맥의 파일·심볼·호출자 일치, 대상 문맥의 첫 단계, 호출자 일치를 확인한다. FlowSpec 직렬화·복원 투영은 선택 호출 정보를 보존한다. 대상 ordinal을 생략해도 호출 문맥이 있는 단계를 이름만으로 연결하지 않는다. 하위 함수 반환은 전체 흐름의 결과로 분류하거나 다른 문맥과 묶지 않는다.

`TestCompilerPreservesRepeatedInvocationTargets`는 같은 종류의 두 문장과 반환을 가진 함수를 세 번 호출해 단계 ID 충돌 없이 각각의 진입점으로 연결하고, JSON 직렬화·복원 이후에도 대상이 같은지 확인한다. `TestInvocationWithoutTargetDoesNotUseSymbolFallback`은 대상 ordinal 생략으로 다른 호출자의 단계에 연결하는 우회를 차단한다. 독립 검토에서 발견한 대체 ID의 호출 문맥 누락과 대상 생략 우회를 수정한 뒤 재검토에서 해소를 확인했다.

TypeScript AST 추출은 복합 반환의 내부 호출을 먼저 수집하고 조건식·단락 평가의 호출에 조건을 보존한다. if의 조건 함수는 판단 단계보다 먼저 표시되며, for의 조건·본문·증감 호출도 보존한다. 미호출 콜백, else 중복, 양쪽 분기가 모두 종료한 뒤의 문장, 중첩 호출 순서, 조건별 호출과 단락 평가, 반복문 헤더 호출을 adapter 회귀 검사에 포함했다. 이 검사는 모든 제어 구문이나 조건 조합의 완전한 실행 모델을 증명하지 않는다.

최종 Go 변경에서 `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다. 이후 TypeScript의 조건·반복문 보완까지 포함한 adapter 전체 검사도 통과했다. 새 옵션의 기본 활성화와 실제 FlowView 재분석 검증은 아직 수행하지 않았다. switch·for-of/in·break/continue 등 제어 구문과 조건별 관계의 전달을 확인한 뒤 활성화하고, 실제 샘플의 반환 결과와 호출 진입점을 브라우저에서 검증한다.

### 16.6 실행 정보 활성화와 실제 반환 코드 확인

새 Core의 slice 요청은 호출자 옵션을 복사한 뒤 실행 정보 지원을 켠다. 분석 캐시 의미 버전은 `v7-execution-noise-filter`로 갱신했다. 이전 옵션 없는 adapter 호출과 저장 뷰는 유지한다. switch·for-of/in의 헤더·본문과 break/continue 문장을 수집하고, 직접 중단 이후 같은 블록의 문장은 제외한다. 기존 switch·loop 통합 검사를 새 옵션으로 실행해 클래스 메서드의 교차 파일 호출이 유지되는지 확인했다.

실제 Quick checkout의 재분석 결과 `8bcc649525077f37512b7cfb9430ff1731144e9e3f5186ac2d11502519386205`에서 9개 단계, 2개 호출 연결, 2개 반환 단계가 저장됐다. `api.orders.checkout` 호출은 실제 반환 본문으로 연결되고, 브라우저에서 해당 관문을 선택하면 `lib/api.ts` 14행을 포함한 코드와 호출자 HomePage.onQuickCheckout이 표시된다. 기존 결과 `316677b345324e4b36fafeb54dbb51f6a864c606e7accf6f34b7aea84b1be818`과 중간 결과 `cd87669fb59a73a714039c7d39f86f8403eb51295db40fb822841672b7f07fa2`는 파일 SHA-256이 그대로 유지됐다.

새 추출 경로에서 기존 제외 대상인 preventDefault 호출이 다시 노출되는 회귀를 실제 화면에서 발견해 수정했다. 최종 저장 단계에 해당 호출이 없으며 주변 원본 코드에는 그대로 보존한다. adapter 전체 검사와 최종 `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다.

남은 제품 과제: 실제 샘플은 여전히 9개 관문에 각각 1개 단계이며 의미 관문 묶음이 완성되지 않았다. 조건 판단과 그에 따른 후속 단계의 명시적 연결, 검증된 코드와 미확인 연결의 상태 분리, 정확한 문장 표시를 위한 Flow Context 전달을 계속 구현한다. 일반 라이브러리·프레임워크 동작의 분석 경계와 대규모 흐름·좁은 창·사용자 이해 검증도 남아 있다. 이번 브라우저 확인은 반환 누락 해결의 증거이며 전체 명세 완료를 뜻하지 않는다.

### 16.7 소스 제어 흐름과 의미 병합의 분리

AST 문장 방문 중 정상 완료 지점을 추적해 `control_flow`를 수집한다. 같은 함수의 전체 단계 배열에서 인접한 항목을 연결하지 않는다. if의 두 경로를 각각 공통 후속 처리로 연결하고, 한쪽이 비어 있는 경로도 보존한다. return·throw가 끝난 경로는 정상 후속 연결을 만들지 않는다. Core 수신·캐시·컴파일·FlowSpec 복원은 같은 invocation의 명시적 양 끝 참조를 검사한다. 호출 연결의 진입점 검사는 별도로 유지한다.

try/finally와 반복·switch의 충분히 확인하지 못한 합류·반복 연결은 추측하지 않는다. 해당 문장에 `unknown_edge`와 `unresolvedReason`을 남기고, Fusion과 semantic projection의 미확인 정보에 이유를 보존한다. 이 단계는 예외·반복·라벨의 완전한 제어 흐름 분석을 뜻하지 않는다. 조건의 구체적인 결과별 간선 표시는 후속 구현 대상이다.

새 invocation의 제어 연결만으로는 같은 처리 목적을 입증하지 못하므로 기존 직렬 병합 규칙을 그대로 적용하지 않는다. 처리 목적을 확인하지 못한 관문에는 요약 한계를 유지한다. 실제 브라우저 재분석에서 중간 버전이 연결 추가만으로 요약 한계를 없애는 문제를 확인하고 수정했다. 최종 결과 `162b7cfcbf779c4081f2158f0ce126dbf4aabe38d99345c825ca79e6c4c8cd56`은 9개 단계, 호출 연결 2개와 제어 연결 6개를 표시하며 요약 한계 2개 관문을 유지한다. 제어 연결은 화면에서 ‘다음 처리’로 표시한다. 1:N 의미 관문 생성은 아직 완료하지 않았다.

검증: TypeScript 전체 검사, 프런트엔드 22건, Svelte 오류·경고 0건, UI 빌드, `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다. 제어 연결 회귀 검사는 분기 간 허위 직렬화 금지, 빈 분기 후속 처리, 종료 뒤 정상 연결 금지, 예외 구간 한계 표시를 포함한다.

전체 검사 중 Next.js 게시 E2E에서 재발한 상태 불일치를 조사했다. 임시 fixture 복사기가 원본의 실행 중인 `.codeflow` 데이터까지 복사하므로 상태 파일과 live head가 서로 다른 순간의 값이 될 수 있었다. 소스 fixture 복사에서 runtime 상태를 제외하고, 이전 상태가 복사되면 실패하는 검사의 수정 전 실패·수정 후 통과를 확인했다. 기존 fixture runtime 파일은 삭제하지 않았다. 이후 전체 E2E가 통과했다.

### 16.8 반환식의 1:N 관문과 실제 화면 확인

- 같은 호출 문맥의 반환 문장 범위 안에 있는 계산 호출과 반환 단계를 정상 진행 연결로 확인하여 묶는다. 별도 문장, 다른 호출 문맥, 조건 판단, 상태 변경, 외부 효과, 여러 미확인 경계는 합치지 않는다. 호출된 함수의 별도 관문과 원래 실행 연결은 유지한다.
- 미확인 호출 하나를 포함하면 그 호출을 대표 코드로 유지하고 관문을 분석 경계·unknown으로 표시한다. 진입 관문은 최초 단계를 대표 코드로 유지한다. 진입점 자체가 미확인 경계인 경우 병합하지 않는다.
- 실제 Next.js 체크아웃 재분석에서 9개 실행 단계가 8개 관문으로 표시되었다. `useCart.calculateTotal 반환` 아래 호출과 반환 2단계가 있으며, 펼치기와 반환 단계 선택 시 선택 코드·선행 연결이 바뀌는 것을 브라우저에서 확인했다. 기존 저장 분석은 9개 관문으로 유지된다.
- 실행 탐색의 자식은 코드 본문 대신 함수명과 `호출`·`반환` 등 단계 역할을 표시한다. 같은 함수 안의 서로 다른 단계를 구분하기 위한 보완이다.
- 검증: 반환식 병합·미병합, 진입 대표 코드, 독립 경계, 반복 호출 문맥, 중간에 펼쳐진 다른 함수 단계, 입력 불변성, 참조 유효성 테스트 통과. `make fmt`, `make vet`, `make check-naming`, `make test` 통과. 프런트엔드 22개 테스트와 Svelte 검사, UI 빌드 통과. 독립 리뷰의 진입 경계·진입 대표 코드 결함을 수정했다.
- 이 결과는 반환식이라는 명확한 처리 목적의 묶음에 대한 구현 증거다. 다른 처리 목적의 관문 묶음, 정확한 Flow Context, 대규모 흐름과 좁은 화면의 사용성 검증까지 완료했다는 뜻은 아니다.

### 16.9 TypeScript Flow Context와 선택 범위

- TypeScript 실행 분석이 사용하는 AST에서 표현식·문장·조건부 헤더, 함수 시그니처와 호출 단위, 감싸는 조건 구조를 수집한다. UTF-8 바이트 범위와 줄 범위, 스냅샷 ID, 전체 소스 해시를 함께 전달하고 어댑터의 Flow Context 지원을 선언한다. 기존 실행 정보 확장을 요청하지 않은 호출에는 새 단계 메타데이터를 붙이지 않는다.
- Core는 선택 범위가 기존 단계와 근거의 바이트 범위·해시에 일치하는지 확인한다. 정확한 위치와 분석 상태는 독립적이며, 미확인 근거는 그대로 유지한다. 구문 오류·스냅샷 ID 누락·일치하는 구문 범위가 없는 경우 정밀 범위를 선언하지 않는다.
- 비교 화면에서도 현재 코드의 선택 표현식만 강조하고, 정밀 범위가 없는 과거 분석에는 새 강조를 만들어 넣지 않는 것을 브라우저에서 확인했다.
- 실제 Next.js 체크아웃 재분석은 9개 단계 모두 exact 범위를 제공했다. 같은 줄의 호출을 선택하면 `cart.reduce(…)` 표현식만, 반환을 선택하면 `return …;` 문장이 강조되는 것을 브라우저에서 확인했다. 기본 코드뷰가 검증된 문맥을 무시하고 주변 16줄로 늘리던 동작을 제거했다.
- 어댑터 회귀 검사, 한글·이모지 위치, 조건 헤더의 주석과 닫는 괄호, 구문 오류와 스냅샷 누락 테스트가 통과했다. Core의 선택 종류·근거 상태 보존 및 기존 Flow Context 검사가 통과했다. 전체 Go 검사와 프런트엔드 22개 테스트, Svelte 검사와 UI 빌드가 통과했다. UI 생성 중 Go 검사를 병행하여 발생했던 생성 HTML 불일치는 생성 완료 후 전체 검사를 다시 실행해 해소했다.
- 독립 리뷰에서 while·for·switch·for-of 헤더의 잘린 범위를 발견해 닫는 괄호까지 수집하도록 수정했다. do-while 등 정확한 구문 범위가 제공되지 않는 경우는 여전히 제한 상태로 남긴다. 전체 의미 관문 묶음과 대규모 사용성 검증은 계속 필요하다.

### 16.10 검증된 소스와 미확인 분석 상태의 구분

- 컴파일러가 검증한 스냅샷 소스 결과를 `sourceValidationStatus`에 보존한다. 전체 분석의 미확인 연결로 기존 근거 상태가 unknown이 되는 동작과 proof·관문·공개 권한 판정은 유지한다.
- Flow Context가 해당 소스 검증 결과를 전달하고, 코드뷰는 정확한 범위와 verified 소스 근거를 함께 확인한 경우에만 ‘소스 확인’을 표시한다. 분석 경계는 ‘연결 미확인’으로 별도 표시한다. 과거 저장 분석은 새 검증 결과를 추정하지 않는다.
- 실제 체크아웃 재분석에서 일반 단계는 ‘소스 확인 / 분석 미확인’, 미확인 호출을 포함한 `useCart.calculateTotal 반환` 관문은 ‘소스 확인 / 연결 미확인’으로 표시되는 것을 브라우저에서 확인했다. 미확인 연결 5건과 8개 관문·9개 실행 단계는 유지된다.
- 미완료 분석에서도 소스 검증 결과가 보존되고 분석 권한은 승격되지 않는 회귀 테스트, Flow Context 전달 테스트, 독립 리뷰를 통과했다. `make fmt`, `make vet`, `make check-naming`, `make test`, 프런트엔드 22개 테스트, Svelte 검사, UI 빌드가 통과했다.

### 16.11 원시 trace와 CLI의 관문 생성 통일

- `CurateFlowSequence`와 `codeflow curate`가 저장·복원과 같은 semantic projection 및 관문 생성 규칙을 사용한다. 기존 `flowId`·`frames` 출력은 유지하고 `steps`·`edges`·`unknowns`·`summaryLimitations`를 전달한다. CLI는 생성된 계층의 참조를 검사하고 중복 단계 ID가 있으면 실패한다.
- 함수 이름의 반복만으로 재귀를 선언하거나 인접한 조건 검사를 같은 목적으로 합치던 경로를 제거했다. 독립적인 160개 단계는 모두 보존하며 고정 관문 수에 맞춰 합치지 않는다. 이 검사는 대규모 실제 분석이나 브라우저 사용성 검증을 대신하지 않는다.
- 독립 리뷰에서 발견한 미확인 호출 경계와 순회 중단 정보의 손실을 수정했다. 출발 단계를 확인할 수 있는 미확인 호출은 분석 경계로 남기고 원래 사유를 보존한다. 입력의 규칙 배열을 변경하지 않으며 순회 중단도 전체 분석의 한계로 전달한다.
- CLI 입력은 기존 공통 민감 정보 제거 함수를 거친 후 계층을 생성한다. 단계 설명·상태 변화·미확인 사유의 민감 정보가 출력되지 않는 실제 바이너리 검사를 추가했다. 입력을 정제한 뒤 참조를 검사하므로 출력 이후의 문자열 변경으로 참조 일치 여부가 달라지는 경로를 만들지 않는다.
- 검증: `trace_hierarchy_test.go`의 동일 투영·미확인 경계·입력 불변성 검사와 `pipeline_test.go`의 실제 CLI 실행 검사가 통과했다. 마지막 민감 정보 제거 변경을 포함해 `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다. 이번 변경에는 화면 변경이 없으며 이전 브라우저 결과를 새로운 CLI 전체 파이프라인의 완료 증거로 사용하지 않는다.
- 남은 범위: 반환식 이외의 처리 목적 묶음, 조건 결과별 관계 전달과 중첩 경로 탐색, 실제 대규모 흐름·접근성·사용자 이해 검증. `collect → curate → view`의 JSON 입력이 실제 화면까지 전달되는지도 별도로 검증해야 한다.

### 16.12 조건 결과별 관계 수집 시작

TypeScript 내부 AST 분석은 if와 삼항식의 후속 경로에 판단 문장 참조와 `truthy`·`falsy` 결과를 기록한다. JavaScript의 조건 평가 결과이며 값이 boolean 타입이라는 뜻은 아니다. 양쪽 분기가 비어 같은 후속 문장으로 이어지는 경우에도 서로 다른 조건 결과를 보존한다. 실제 문장을 지난 뒤의 공통 후속 연결에 직전 조건을 무조건 복사하지 않는다. 중첩 경로의 도달 조건은 각각의 판단과 연결을 따라 구성해야 한다.

`syntax_branch_paths.test.js`에서 일반 분기·빈 양쪽 분기·중첩 분기·조기 반환·삼항식의 관계를 검사했다. 새 검사는 변경 전 조건 근거 누락으로 실패하고 변경 후 통과했다. TypeScript 전체 검사도 통과했다. 기존 숫자 기반 선행 참조는 유지하여 현재 adapter 응답의 관계를 바꾸지 않는다.

이 정보는 현재 내부 문장 분석에만 존재한다. 공개 관계 형식·참조 검증·저장·MCP·HTTP·화면 전달, 단락 평가와 반복·예외 처리의 조건 모델은 아직 구현 대상이다. 따라서 조건별 화면 탐색이나 VS-03 완료 증거로 집계하지 않는다.

### 16.13 조건 관계 전달 계약과 구현 중인 범위

관계의 선택 필드 `conditions`는 해당 연결을 따르기 위한 판단 결과를 나타낸다. Slice와 FlowSpec은 `stepOrdinal`·`outcome`, SemanticMap은 `stepId`·`outcome`으로 판단 단계와 결과를 전달한다. 지원 결과는 JavaScript의 `truthy`·`falsy`와 null 병합의 `nullish`·`non_nullish`이며, 현재 지원 연결은 출발 판단 단계에서 나오는 `control_flow`다. 따라서 현재 필드가 존재하면 한 개의 조건만 허용하고 판단 참조는 연결의 출발 단계와 같아야 한다. 판단 단계는 branch 또는 guard이며 양 끝은 같은 호출 문맥이어야 한다. 없는 필드는 조건 근거가 없다는 뜻으로 유지한다. 과거 분석의 문자열 조건을 역으로 해석해 이 필드를 채우지 않는다.

동일한 출발·도착에 참·거짓 연결이 각각 있으면 별도 관계로 보존한다. 중첩 경로는 여러 관계의 선택을 순서대로 구성하며, 공통 후속 단계의 소속을 복제하지 않는다. 조건 문자열은 새 필드에 복사하지 않고 판단 단계의 검증된 소스를 사용한다. 새로운 조건 참조는 기존 redaction·저장·HTTP·MCP 전달 경로를 따르며 유효하지 않은 명시적 참조를 무조건 진행 관계로 바꾸지 않는다.

이 절은 구현에 앞서 정한 호환 가능한 전달 계약이다. 실제 전달 검사와 화면 검증 결과는 구현 후 기록한다.

후속 구현에서 adapter 응답·Slice·FlowSpec·SemanticMap과 세 JSON 스키마에 조건 참조를 추가했다. 컴파일과 저장 시 잘못된 판단 참조·결과·연결 종류·호출 문맥을 거부한다. FlowSpec 복원에서는 잘못된 조건을 무조건 진행으로 해석하지 않고 미확인 연결로 남긴다. 정적 분석 캐시 의미 버전을 `v10-branch-conditions`로 변경했으며 기존 저장 뷰는 다시 작성하지 않는다.

검증: 실제 adapter의 일반 분기, 빈 양쪽 분기와 제외된 preventDefault 호출 이후에도 참·거짓 연결이 각각 남는다. `TestBranchConditionsSurviveCompilationAndRestoration`과 `TestValidateBranchConditions`가 조건 identity·직렬화·참조 거부를 검사했다. `TestFlowPayloadMatchesExactStoredHTTPHierarchy`에서 저장 후 HTTP와 MCP full 응답의 두 조건 관계가 원본과 일치함을 확인했다. MCP compact의 조건 관계 제공은 이 검사 범위에 포함되지 않는다. 독립 리뷰에서 확정 결함은 발견하지 못했다. TypeScript 전체 검사와 `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다.

이 단계는 조건 관계의 전달 완료이며 화면 탐색 완료가 아니다. 화면의 참·거짓 표시·중첩 조건 선택·경로 강조, 단락 평가·반복·예외의 조건 모델과 실제 브라우저 검증을 계속 구현한다.

### 16.14 조건 선택과 소스 연결 범위 강조

- 조건 결과를 선택하는 목록과 선택한 조건의 순서 있는 목록을 추가했다. 조건 선택은 코드 선택을 바꾸지 않는다. 부모 결과 변경으로 도달하지 못하는 하위 조건은 해제하고 안내한다. 개별·전체 해제와 조건 근거로 이동, 원래 읽던 코드·조건 목록·초점 복원을 제공한다.
- 선택한 판단에서 실제 관계를 따라갈 수 있는 단계만 강조한다. 공통 후속 단계는 한 번만 유지하고 순환은 방문한 단계에서 반복 탐색을 멈춘다. 미확인 연결과 조건 결과가 없는 판단의 후속 관계는 전체 경로로 추측하지 않는다. 이전 형식의 조건은 별도의 직접 연결 조작으로 유지한다. 이 강조는 실제 실행 결과나 조건 조합의 실행 가능성 증명이 아니다.
- 상단 관계와 중앙 전후 연결에 조건 참·거짓을 표시하며 실행 탐색의 해당 자식에 경로 포함 표시를 붙인다. 강조 범위 밖의 코드도 원래 대비로 읽을 수 있고 점선 테두리와 안내로 구분한다. 화면 수신 시 잘못된 조건 참조는 적용을 거부한다.
- 프런트엔드 29개 검사, Svelte 오류·경고 0건, UI 빌드가 통과했다. 전체 Go 검사는 첫 화면 빌드 후 통과했고, 브라우저에서 발견한 코드 대비·이전 형식 조건 목록 보완 뒤에는 프런트엔드 전체 검사·검사기·빌드 및 presenter 검사를 다시 통과했다. 독립 리뷰에서 확정 결함은 발견하지 못했다.
- 실제 체크아웃의 명시적 재분석 `82f6dfea514e4d257576e31de9d14f9423913ae20352982551498678fc43f2d6`에서 `if (response.success)`의 참 연결이 표시된다. 조건을 선택해도 처음 읽던 setStatus 코드는 유지되고 경로 밖 안내가 나타난다. 근거 보기로 조건 코드에 이동한 뒤 원래 장면 복귀로 코드·조건 선택·초점이 복원되는 것을 브라우저에서 확인했다. 최종 보완 후 경로 밖 코드의 opacity가 1이고 점선 테두리로 표시됨도 확인했다.
- 중첩 조건의 부모 변경은 현재 자동 검사 증거이며 실제 소스 분석부터 브라우저까지의 중첩 사례 검증은 남아 있다. 관문 내부 조건별 자식 묶음, MCP compact의 관계 표현, 단락 평가·반복·예외·비동기 관계, 대규모·좁은 화면·사용자 이해 검증도 완료하지 않았다. 따라서 VS-03 전체 완료를 선언하지 않는다.

### 16.15 실제 중첩 조건 검증과 compact 관계 전달

기존 체크아웃 샘플의 별도 임시 사본에 성공 여부와 주문 합계의 중첩 판단, 실패 경로와 공통 후속 처리를 추가했다. 실행 상태 디렉터리는 복사하지 않았다. 실제 분석 API가 생성한 저장 뷰 `e4100a6b99a983f246f0e47a943a1efe1a226aec792c69976dbdb20d82cfabf7`에서 부모·자식의 네 조건 관계와 공통 후속 처리로 들어가는 세 연결을 확인했다. 브라우저에서 부모·자식 참 선택은 priority와 settled를 강조하며 부모를 거짓으로 바꾸면 자식 선택 해제 안내와 failed·settled 강조로 바뀐다. settled는 하나의 단계·관문으로 유지되고 기존 코드 선택은 바뀌지 않는다.

compact 응답은 기존 관문 필드에 `steps`·`edges`·`unknowns`를 선택 필드로 추가해 같은 분석의 관계와 분석 한계를 보존한다. 간결한 단계에는 단계 ID·종류·이름·호출 문맥·소스 범위를 담고, 관계는 원래 참조·종류·조건·미확인 상태를 유지한다. 저장 뷰를 compact로 읽을 때 다시 묶지 않고 같은 계층을 검증하여 사용한다. 공개 응답 크기를 고정 수치에 맞추려고 단계·관계·조건을 삭제하지 않는다. 필드가 없는 이전 응답은 관계 정보 미제공이며 연결이 없다는 증거로 취급하지 않는다.

구현은 저장 뷰 조회와 활성 FlowSpec 조회 양쪽에 적용했다. MCP 도구 설명에서도 고정 500토큰 응답 보장을 제거하고 소스 참조·관계·조건·분석 한계를 제공함을 명시했다. 기존 관문 요약만 생성하는 내부 API는 호환을 유지한다.

검증: 저장·HTTP·MCP full/compact의 동일 조건 관계 검사에서 수정 전 compact의 관계 누락으로 실패했고 수정 후 통과했다. 단계 소스 위치와 미확인 사유도 보존됨을 검사했다. `TestCompactAnalysisPreservesGraphWithoutAliasing`는 미확인 관계 보존, 조건·소스 범위·미확인 사유·자식 참조의 복사, 잘못된 계층 거부를 확인한다. 독립 리뷰와 `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다. 이번 변경은 새로운 분석 의미를 추가하지 않으며 관문 내부 조건 묶음과 전체 명세의 남은 수용 기준을 완료한 것으로 집계하지 않는다.


### 16.16 단락 평가의 조건 결과

`&&`는 왼쪽이 truthy일 때, `||`는 falsy일 때 오른쪽을 평가한다. `??`는 왼쪽이 null 또는 undefined인 경우에만 오른쪽을 평가한다. 이 세 연산자는 왼쪽 피연산자의 정확한 소스 범위를 판단 단계로 사용하고, 오른쪽 평가와 건너뛰기의 두 연결에 각각 결과를 보존한다. `nullish`·`non_nullish`는 boolean 참·거짓과 구별하여 저장·전달·표시한다. 기존 결과 값은 유지하고 새 결과 값은 동일한 판단 참조 검증을 적용한다. 캐시 의미 버전은 `v11-short-circuit-conditions`다.

공통 후속 처리와 조기 반환 구조만으로 서로 다른 검사를 같은 목적의 관문으로 병합하지 않는다. 이 구조는 권한과 결제 한도처럼 별개의 핵심 판단에도 나타날 수 있다. 한 조건식의 내부 평가를 보존하는 것은 이후 묶음 판단에 필요한 근거이며, 그 자체가 전체 의미 묶음의 완료는 아니다.

검증: 새 AST 경로 검사는 수정 전 오른쪽 평가의 조건 연결 누락으로 실패하고 수정 후 통과했다. 실제 adapter 응답에서도 세 연산자의 평가·건너뛰기와 정확한 대상 참조를 검사했다. Core 컴파일·직렬화·복원은 nullish/non_nullish 쌍까지 검사하며 프런트엔드는 boolean 거짓과 별도로 표시·선택한다. TypeScript 전체 검사, 프런트엔드 30개 검사, Svelte 오류·경고 0건, UI 빌드, `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다. 독립 리뷰는 중첩 표현식 5개에서 조건 참조를 추가 확인했고 확정 결함을 발견하지 못했다.

별도 임시 체크아웃 사본의 실제 분석 `d67dab95ea383603e8f43be963b47200a31de064f44cfb57894f6bc79730ef4c`에서 &&·||·??의 조건 관계를 저장했다. 브라우저에서 response.orderId의 non_nullish 선택은 createReference 호출과 반환을 강조하지 않고 공통 후속 조건으로 진행한다. nullish 선택은 createReference 호출·실제 반환 코드와 같은 공통 후속 처리를 강조한다. 이 확인은 단락 평가 경로의 근거이며 다른 함수의 검증문을 같은 목적으로 묶거나 관문 내부 분기 묶음까지 완료했다는 뜻은 아니다.

### 16.17 조건부 반환의 관문과 내부 연결

같은 반환식에 속한 조건 판단과 마지막 반환만으로 구성된 영역을 하나의 `반환값 판단` 관문으로 묶는다. 각 판단의 상보 결과 두 개, 내부의 전진 연결, 중간 단계에 외부 진입이 없음을 확인해야 한다. 대표 코드는 첫 판단이며 기존 시작 역할과 가장 낮은 검증 상태를 유지한다. 호출·상태 변경·외부 효과·미확인 경계가 포함되면 이 규칙을 적용하지 않는다. 별도 검증문들이 공통 후속 처리를 갖는다는 이유만으로 병합하지 않는다.

독립 리뷰에서 `return flag ? (state.value = 1) : (state.value = 2)`와 `return flag && state.count++`의 상태 변경이 어댑터에서 누락되는 결함을 확인했다. 대입·복합 대입·증감·delete를 별도 mutation 단계로 추출하고, 논리 대입은 실행·건너뛰기 조건을 보존한다. 생성자 실행은 호출 단계로 표시하되 생성자 내부와 초기화 연결은 명시적인 분석 한계로 남긴다. 캐시 의미 버전은 `v12-expression-mutations`다. 이는 생성자 내부 실행 분석을 완료했다는 뜻이 아니다. 추가 리뷰에서 구조 분해 대입의 계산된 키와 기본값에 잘못된 실행 순서가 부여되는 사례도 확인했다. 구조 분해 대입은 우변 평가를 먼저 보존하고, 내부 키·기본값·반복자 실행은 분석 경계로 표시한다. 조건부 기본값을 무조건 실행하는 호출로 생성하지 않는다.

실행 탐색을 펼치면 관문 내부의 직접 선행 연결에 따라 `단계 N · 조건 참에서 연결` 또는 `여러 대체 경로가 연결됨`을 표시한다. 이 문구는 해당 단계의 직접 연결만 설명하며 모든 상위 조건이나 동시 완료를 추정하지 않는다. 기존 자식 순서와 단일 출현을 유지한다.

검증: 누락된 mutation을 확인하는 테스트가 수정 전 실패하고 수정 후 통과했다. TypeScript 전체 검사와 실제 sliceFlow 응답 검사에서 조건부 대입·증감·생성자 경계 및 중복 없는 mutation을 확인했다. Go 전체 테스트, 정적 검사, 명명 검사가 통과했다. 프런트엔드 33개 검사와 Svelte 오류·경고 0건, UI 빌드도 통과했다.

임시 체크아웃의 실제 API 분석 `4018249dc2cb875ad75d33d4387dc181569301e3bc6ed968350dd74576962d37`은 23개 관문과 26개 실행 단계를 반환했다. canCheckout의 조건 두 개와 반환 한 개는 하나의 관문이고 recordChoice·incrementChoice의 mutation과 createChoice의 생성자 경계는 별도 단계로 남았다. 저장된 뷰를 브라우저에서 열어 3개 자식과 합류 문구를 확인했고, 반환 자식 선택 시 같은 관문을 유지하며 해당 반환문을 코드뷰에서 강조했다. 이 증거는 조건부 반환의 제한된 묶음에 해당하며 전체 목적 기반 묶음, 대규모 사용성, 실제 사용자 이해도 검증을 대체하지 않는다.

### 16.18 관문 판정의 내부 검토 기록

`ReviewFlowSequence`는 공개 화면과 같은 생성 함수를 호출하면서 후보별 실제 판정 규칙, 생략 시 잃는 실행 정보, 최종 관문과 자식 소속, 병합·분리 이유, 직접 관계와 소스 근거 참조를 기록한다. 기록은 내부 검토용이며 공개 스키마나 기본 화면에 추가하지 않는다. 요청 문맥이 없으면 제공된 실행 범위만 다룬다. 요청 문구가 있어도 해당 문구에 특정 단계가 필수적이라는 근거가 없으면 요청별 필수성을 입증했다고 표시하지 않는다.

같은 함수의 모든 경로가 하나의 boolean 결과로 끝나더라도 같은 처리 목적이라고 판단할 수 없다. 권한 확인과 결제 한도 검사가 별도 if·return으로 구현된 반례가 있으므로 이 구조만으로 병합하는 규칙은 채택하지 않았다. 같은 진입점에 ‘접근이 거부되는 이유’, ‘결제 한도가 적용되는 이유’, 요청 문맥 없음의 세 경우를 적용한 검사에서 두 판단을 모두 유지한다. 요청 문구만으로 다른 소속을 만들어내지 않는 이유도 내부 기록에 남긴다.

관련 회귀 검사는 판정 기록의 반복 재현, 관계 열거 순서 독립성, 반환식의 최종 병합 이유와 소속, 빈 입력을 확인한다. 독립 리뷰에서 기존 관문 결과의 Condition과 SourceAnchor.SymbolRange가 원본 포인터를 공유하는 결함을 발견했다. 원본과 분리된 값을 생성하도록 수정했으며, 검토 결과 또는 일반 관문 결과의 값을 바꿔도 원본 조건·소스 범위가 변하지 않는 검사에서 수정 전 실패와 수정 후 통과를 확인했다. 이 기록은 요청별 의미 판정의 근거 부족을 추적하기 위한 것으로 AC-02 및 요청별 의미 큐레이션 전체를 완료한 것으로 보지 않는다.

### 16.19 257단계 실제 분석과 좁은 화면 검증

별도 임시 TypeScript 소스에 서로 다른 거부 조건 8개, 계산 호출 80개, 대입 80개와 반환 89개를 구성했다. 실제 분석 API는 총 257개 실행 단계와 256개 연결을 반환했고, 각 단계가 하나의 부모 관문에 속하며 8개 조건 판단이 각각 유지되었다. 저장 후 조회에서도 관문·단계·연결이 동일했다. 해당 분석의 viewId는 `89c33446ccf87cd5fb2f8b3eda1d4c1f827f42f9cd868d86e7b85d4a91bce710`이다. 관문도 257개인 결과이며, 이것을 의미 요약의 성공으로 평가하지 않는다. 화면에는 80개 관문의 요약 한계가 표시되었다.

`TestLargeSourceHierarchySurvivesStorageHTTPAndMCP`는 실제 TypeScript 어댑터를 실행해 같은 수의 단계와 독립 판단을 확인한다. 이어서 fusion, 공통 관문 생성, 저장, HTTP, MCP full/compact를 통과한 관문 ID·순서·역할·대표·자식 소속과 소스 참조·조건 관계를 비교하고 조회 전후 저장 bytes가 같음을 검사한다. 소스 구조에서 기대한 256개 관계도 독립적으로 구성해, 거부 조건의 참·거짓 연결과 각 호출 대상·후속 대입·다음 처리의 관계가 누락·중복·추가되지 않았는지 비교한다. 원본 소스 bytes도 분석 전후 같음을 확인한다. 선택적 빈 배열의 JSON 생략은 의미 변경으로 취급하지 않는다. 브라우저 검증은 이 자동 검사와 별도로 수행했다.

### 16.20 CLI 입력 계층의 보존과 외부 근거 구분

`codeflow view <JSON 파일>`과 `codeflow view -`는 입력한 관문·대표 단계·자식 소속·관계를 검증한 뒤 저장된 뷰를 연다. 기존처럼 입력을 버리고 초기화면을 열지 않는다. `-` 뒤의 옵션도 정상 해석한다. `--dry-run`은 입력 검증만 수행하고, 비대화형 실행은 브라우저를 자동으로 열지 않은 채 서버를 유지한다. JSON 입력과 새 분석을 지정하는 `--flow`·`--query`·`--entry`의 조합은 거부한다.

외부 JSON의 소스와 검증 완료 주장은 이 환경의 검증 근거가 아니다. 가져오기는 입력 bytes에 따른 새 식별자를 부여하고 계층을 다시 묶지 않는다. 외부 렌더링 소스·proof·현재 분석 권한·요구사항 확인 결과는 가져오지 않으며 단계의 evidence 참조를 제거하고 검증 완료 관문을 부분 확인으로 낮춘다. 기존 저장 뷰를 다시 쓰는 작업은 아니다. 사용자가 현재 코드를 명시적으로 다시 분석하기 전에는 소스 근거 미확인 안내를 유지한다.

검증: 실제 CLI 프로세스에 파일·표준입력·조작된 전체 뷰 JSON을 전달하고 반환된 viewId의 HTTP 조회에서 1개 관문과 2개 자식 및 지정한 대표 반환을 확인했다. 외부 소스·검증 주장의 제거, 미확인 상태와 잘못된 참조 거부를 검사했다. 독립 리뷰에서 이전의 외부 proof 신뢰 결함이 해결되었음을 확인했다. `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다.

브라우저 확인 중 소스가 없는 입력에도 ‘소스에서 확인한 연결’이 표시되는 문제를 발견해 개요와 전후 연결을 ‘입력된 연결 · 소스 근거 미확인’으로 구분했다. 구체적인 소스 안내를 일반 안내로 덮어쓰는 문제도 회귀 검사에서 실패를 확인한 뒤 수정했다. 프런트엔드 33개 검사, Svelte 오류·경고 0건, UI 빌드와 presenter 검사가 통과했다. 최종 바이너리의 실제 화면에서 미검증 안내와 1:N 펼치기를 확인했다. 이 작업은 CLI 입력 경로의 완성이며 일반적인 목적 기반 묶음이나 전체 사용성 검증의 완료를 뜻하지 않는다.

### 16.21 호출 결과를 대입하는 처리의 근거 계약

단순 식별자에 `=`로 우변의 단일 호출 결과를 직접 대입하는 경우, 호출 결과 수령과 대입을 하나의 처리로 표현한다. 호출의 순수성이나 사업 목적을 이름으로 추정하지 않는다. 최종 대입을 대표 코드로 삼고 호출된 함수 내부의 판단·효과·결과 관문은 그대로 유지한다. 별도 문장, 쉼표식, 계산된 대입 대상, 복합 대입, 내부 조건·추가 호출·상태 변경·미확인 경계는 이 규칙에 포함하지 않는다.

이를 위해 SliceStep·FlowStep·SemanticStep에 선택 필드 `assignmentSourceOrdinal`을 전달한다. 값은 AST가 확인한 직접 우변 호출의 기존 단계 순번이다. 같은 호출 문맥의 선행 call, 대입 소스 범위 내 포함, 같은 파일 내용, 무조건 직접 진행 관계가 모두 확인되어야 한다. 필드가 없는 기존 저장 데이터는 변경하지 않고 이 규칙을 적용하지 않는다. 어댑터가 사실을 추출하고 curator가 병합하며 화면·MCP가 재판정하지 않는 책임을 유지한다. 잘못된 명시 참조는 입력 검증에서 거부한다. 아래 구현·검증 결과는 수행 후 기록한다.

구현 결과: AST의 직접 우변 호출 참조를 Slice·FlowSpec·SemanticMap으로 전달하고, compact에도 원래 순번과 대입값 참조를 보존했다. 새 분석 캐시 버전은 `v13-assignment-value-source`다. 참조가 없거나 대상이 다른 호출 문맥·파일·내용·범위를 가리키면 병합하지 않는다. 단계 참조 입력 검증은 잘못된 명시 참조를 거부한다. 관문 생성은 외부 효과·조건·미확인 연결을 별도로 보존한다. 원래 단계와 연결을 변경하지 않고 최종 대입을 대표로 하는 두 자식 관문을 만든다.

검증: `TestAssignmentExpressionGateway`에서 직접 호출과 대입이 분리된 실패를 확인한 뒤 수정하여 통과했다. 실제 TypeScript 검사에서 단순 대입만 새 근거를 갖고 쉼표식·계산된 대입 대상·중첩 호출·논리 대입·속성 대입은 해당 근거를 갖지 않음을 확인했다. 잘못된 순번·호출 문맥·파일·해시·범위는 `TestAssignmentSourceReferences`로 거부를 확인했다. 대규모 실제 어댑터 기반 검사는 257개 단계와 256개 연결을 그대로 유지하면서 대입 80쌍을 묶어 177개 관문을 만든다. 독립 판단 8개와 호출된 함수의 반환 단계는 별도로 남으며 저장·HTTP·MCP full/compact에서도 동일한 소속·대표·참조를 확인했다. TypeScript 전체 검사, `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했고 독립 리뷰에서 확정 결함은 발견하지 못했다.

실제 API 분석의 viewId `1298f74b22d7bff29df779c0b8d3a85ffccc59a9352fbe4924af5f6249fcd8a4`에서도 177개 관문과 257개 단계를 확인했다. 브라우저에서 17번째 관문은 대입문 전체를 대표 코드로 강조하며, 두 자식 중 호출을 선택하면 같은 관문에서 우변 호출만 강조한다. 호출된 함수로의 별도 관계도 유지된다. 이 결과는 직접 호출 결과 대입에 대한 인과관계 묶음이며 일반 검증문·요청별 목적 판정의 완료는 아니다. 화면 확인에서는 실행 탐색에 소유 함수명이 반복되어 관문 간 구별이 어려운 문제도 확인했다. 확인된 호출 대상과 처리 목적을 사용한 목록 구별을 다음 UX 보완으로 남긴다.

### 16.22 실행 탐색에서 호출 대상과 처리 구별

원본 제목이 코드 문장일 때 소유 함수명만 대신 표시하던 실행 탐색은 같은 함수의 여러 관문을 구별하기 어려웠다. 이제 존재하는 대상 단계로 이어지는 확인된 호출 관계를 사용해 호출은 `applyAdjustment01 호출`, 직접 결과 대입은 `applyAdjustment01 결과 반영`으로 표시한다. 소유 함수는 보조 정보로 유지하며 원래 처리 목적 제목이 있으면 이를 우선한다. 조건 판단은 전달된 조건을 표시해 인증·권한 등의 서로 다른 판단을 구별한다. 소스 문장에서 호출 대상을 추출하거나 미확인 관계를 확인된 것으로 승격하지 않는다. 관문 소속·역할·대표·연결은 변경하지 않는다.

프런트엔드 35개 검사, Svelte 오류·경고 0건, UI 빌드와 presenter 검사가 통과했다. 검사에는 누락된 대상·미확인 호출·일반 진행 연결의 호출명 오인 방지와 중복 관계, 기존 목적 제목 보존을 포함한다. §16.21의 실제 저장 뷰를 최신 화면으로 열어 17·19번째 관문이 각각 applyAdjustment01·02 결과 반영으로 구별되고 독립 조건이 표시됨을 확인했다. 17번째 관문을 펼치고 호출 자식을 선택했을 때 부모 관문을 유지하며 우변 호출만 코드뷰에서 강조했다. 일반적인 의미 큐레이션과 사용자 이해도 검증은 계속 남아 있다.

FlowSequence 개요의 연결 행도 같은 표시 기준을 사용한다. 원본 코드 문장을 반복하지 않고 확인된 호출 대상, 단계 역할, 소유 함수·클래스 순서로 표시하며 실제 코드는 선택한 코드 패널에서만 읽는다. 실제 `checkout` 분석에서 `await reserve()`의 성공·실패 연결 출발이 ‘완료 대기’로, 일반 연결 출발이 `checkout`으로 표시되는 것을 포함 서버에서 확인했다.

### 16.23 표현식 본문 함수와 공유 소스 근거

TypeScript의 이름 있는 화살표 함수가 `value => value * 2`처럼 표현식 본문을 가질 때도 함수 검색과 바인딩 확인에 포함한다. 확인된 호출은 해당 본문으로 연결하고 표현식 평가 뒤 암시적 반환을 생성한다. 표시할 소스는 원래 표현식 범위이며 가상의 return 문장을 소스에 추가하지 않는다. 조건부 표현식·상태 변경·중첩 호출은 기존 실행 단계와 관계로 보존한다. 반환값이 함수인 경우 그 함수 본문을 호출된 것으로 펼치지 않는다. 새 분석 캐시 버전은 `v14-expression-function-body`다.

실제 분석 API 검증에서 같은 소스가 두 실행 문맥에 등장하면 동일 근거 ID를 중복 생성하여 스키마 검증이 실패하는 기존 컴파일 결함을 발견했다. 실행 단계의 식별자와 호출 문맥은 각각 유지하고, 파일·심볼·내용·바이트 범위로 식별되는 소스 근거만 한 번 저장하도록 수정했다. 모든 단계는 기존 소스 검증을 통과해야 하며 같은 근거를 참조한다는 이유로 실행 단계를 합치지 않는다.

`slice_expression_body.test.js`는 검색 누락으로 실패한 뒤 수정 후 통과했다. 스칼라·조건·객체 반환, 객체 멤버 화살표 함수, 상태 변경, 반환된 콜백, 동일 함수의 두 호출과 UTF-8 소스 범위를 확인한다. `TestExpressionBodyCallsPreserveReturnAndConditions`는 실제 어댑터·fusion·관문 생성에서 8개 단계와 참·거짓 연결을 검사한다. `TestCompilerSharesSourceEvidenceAcrossExecutionSteps`는 같은 표현식의 호출·반환과 서로 다른 호출 문맥에서 근거 중복으로 실패한 뒤 수정 후 통과했으며 최종 SemanticMap 스키마도 검사한다. 독립 리뷰는 표현식 범위와 공유 근거 수정에서 확정 결함을 발견하지 못했다.

실제 API 분석 `f71332f1461ea7922ab6b1cd9086222dd176b1c16540b3cced3e85092a6fb3cb`는 start → choose → price의 8개 실행 단계와 중복 없는 소스 근거 7개를 반환했다. 브라우저에서 price의 첫 호출 결과를 선택하면 원래 화살표 함수의 `value * 2`만 강조하고 해당 호출 `price(2)`로 돌아가는 연결을 표시한다. 두 번째 호출은 별도 단계로 유지된다. 이 구현은 표현식 본문의 누락 수정이며 비동기 완료·예외 연결이나 모든 함수 형태의 분석 완료를 뜻하지 않는다.

최종 검증: TypeScript 전체 검사와 `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다. 화면 변경 없이 현재 번들을 포함한 최종 바이너리로 실제 분석·소스 선택을 확인했다.

### 16.24 판단과 조건부 실행의 구분

조건이 전달되었다는 이유만으로 호출·대입·반환을 판단 관문으로 분류하지 않는다. 종류가 확인된 단계는 실제 역할을 유지하고, 조건은 해당 단계의 실행 조건으로 표시한다. guard·branch·decision·failure 및 종류가 없는 기존 조건 단계의 판단 분류는 유지한다. 코드 맥락 패널도 판단 조건과 실행 조건을 구별한다.

독립 리뷰에서 호출 문맥 식별자가 없는 기존 데이터의 조건부 호출을 앞 단계와 합치면 자식 조건이 무조건 실행되는 부모 관문으로 복사되는 회귀를 발견했다. 기존 병합은 어느 한 단계에 조건이 있거나 연결에 조건이 있으면 수행하지 않는다. 조건 문구가 같다는 사실만으로 같은 판단에 종속된 실행이라고 추정하지 않는다. 조건 없는 직접 연결에 대한 기존 동작은 유지한다.

`TestLegacyGroupingPreservesExecutionConditions`의 조건 진입·이탈·서로 다른 조건·같은 문구·조건부 연결 다섯 사례가 수정 전 실패하고 수정 후 통과했다. 역할 분류 테스트와 실제 어댑터를 사용하는 표현식 본문 E2E도 통과했다. 독립 재리뷰에서 추가 결함은 발견되지 않았다. 최종 `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다.

역할 구분을 적용한 실제 API 뷰 `783aa699d64803e0cf22ae2a1bbbf2ab8df8d139fbdc3f63108f6f050812b006`는 7개 관문과 8개 실행 단계를 유지한다. 브라우저에서 ready는 판단 관문이고 price(2)는 처리 관문이며, 호출 선택 시 실행 조건 ready와 원래 price(2) 코드 범위가 표시됨을 확인했다. 기존 데이터 병합 회귀는 별도 자동 테스트로 검증했다. 일반적인 처리 목적별 묶기와 전체 수용 기준 검증은 완료되지 않았다.

### 16.25 복합 검증 조건의 1:N 관문과 직접 진입 분석

하나의 guard 조건 안의 branch 평가와 최종 판단을 묶는다. 조건식 내부의 각 참·거짓 연결, 실패 반환, 다음 독립 판단은 원래 그래프에 그대로 남는다. `TestCompoundGuardGateway`의 정상 사례는 구현 전 실패하고 구현 후 통과했다. 호출 포함·독립 조건·결과 누락·미확인 경계·중간 외부 진입은 병합되지 않는다. 실제 TypeScript 어댑터 E2E `TestCompoundGuardKeepsIndependentDecisions`는 복합 인증 조건과 별도 한도 검사에서 6개 단계, 5개 관문, 조건 연결 6개를 확인했다. 독립 리뷰에서 추가 코드 결함은 발견되지 않았다.

실제 화면 확인 중 자동 후보에 없는 함수의 명시적 진입 분석이 빈 candidateId로 API 500을 반환하는 결함을 발견했다. 직접 진입도 기존 MCP와 같은 규칙인 진입 심볼 SHA-256 앞 8바이트로 후보 ID를 부여한다. 기존 후보의 ID는 유지한다. `TestResolveFeatureQueryTarget_ZeroEntrypoints`에서 누락을 재현한 뒤 수정했다.

수정 후 실제 API 뷰 `e1f43bc40ee43f1efa8a9e0a0da2aac2566eeace4defbb1ce91c696c884e073f`는 6개 단계와 5개 관문을 반환했다. 브라우저에서 복합 인증 조건 전체가 대표 코드로 표시되고, 타임라인의 내부 조건을 선택하면 같은 관문을 유지한다. 한도 판단과 각 반환은 독립 관문이다. 이 증거는 하나의 조건식 내부 평가 묶음이며, 서로 다른 검증문을 요청 목적에 따라 묶는 AC-02 전체 완료를 의미하지 않는다.

최종 검증: `make fmt`, `make vet`, `make check-naming`, `make test`가 통과했다. 이후 직접 진입 후보 ID를 정확한 해시 값으로 검사하도록 테스트를 강화하고 해당 테스트도 통과했다.

독립 소스 리뷰에서 `ProcessFlowPanel.svelte`의 대상 ID+관계 종류 키가 같은 대상으로 향하는 참·거짓 연결에서 충돌함을 발견했다. §16.25 실제 저장 뷰를 처리 보기로 전환하여 `each_key_duplicate` 오류를 재현했다. 연결을 각각 렌더링하고 조건 결과와 고유한 초점 복원 식별자를 표시하도록 수정했다. 복수 선행 관계만으로 ‘대체 경로’라고 단정하던 타임라인 문구도 ‘여러 선행 연결 · 실행 방식은 각 관계에서 확인’으로 변경했다.

검증: 프런트엔드 36개 검사, Svelte 오류·경고 0건, UI 빌드가 통과했다. 같은 저장 뷰를 새 번들에서 열어 처리 보기의 두 조건 연결이 각각 표시되고, 연결 선택 후 코드 보기로 돌아오는 동작을 확인했다. 새 분석이나 저장 데이터 변경으로 오류를 피하지 않았다.

이 시점에 남긴 자동 검증·분석 관계 보완 항목은 §16.27~16.70에서 구현하고 실제 제품 브라우저 과제로 검증했다. 현재 `saved-flowview.spec.ts`는 현행 접근성 영역·초기 화면·실제 저장 분석을 사용하며, 파일 존재만으로 통과를 주장하지 않는다. 남은 항목은 §16.59의 실제 개발자 이해 과제와 대안 배치 비교, 그리고 출시 판단에 필요한 성능 환경·수치 기준·지원 범위 확정이다.

### 16.27 현행 화면의 실패·취소·관계 복귀 검증

§16.26에서 확인한 현행 브라우저 검증 부족을 보완했다. 실제 저장 뷰와 최신 제품 번들을 사용하고, 로컬 시험용 프록시에서 `/api/task/view`에만 503 오류 또는 4초 지연된 다른 분석 응답을 주입했다. 저장 뷰·비교·목록 조회는 제품 서버에 그대로 전달했다. 시험용 프록시는 제품 코드나 배포 기능이 아니다.

- 관찰1: 처리 보기의 조건 관계를 선택하고 코드 보기로 전환한 뒤 ‘원래 장면 복귀’를 실행하면 처리 보기와 원래 관계 버튼의 초점이 복원됐다.
- 관찰2: 같은 요청·진입점의 두 소스 버전으로 비교를 열었다. 현재 뷰는 `3b18c15fe52f56eb4a8cdb46cae7befe56a9166e92ca98887e1648af53eed794`, 기준은 `e1f43bc40ee43f1efa8a9e0a0da2aac2566eeace4defbb1ce91c696c884e073f`다. 세 번째 한도 판단 선택 후 재분석을 503으로 실패시켜도 선택·비교 화면·기준 ID가 유지됐다.
- 관찰3: 같은 상태에서 재분석 지연 중 취소하고 4초 이상 지난 뒤에도 취소 안내, guard 흐름, 세 번째 판단, 비교 화면과 기준 ID가 유지됐다. 지연 응답은 다른 expression 뷰였으므로 기존 흐름 유지 여부를 구별할 수 있다.
- 관찰4: 요청 문맥이 다른 guard-review를 비교 기준으로 선택하면 `incomparable_basis: task scope mismatch`로 거부하고 기존 화면을 유지했다. 같은 진입점이라는 이유만으로 서로 다른 요청을 비교 가능한 것으로 취급하지 않았다.

`web/live-comprehension-workspace/tests/saved-flowview.spec.ts`의 제거된 FlowSequence·radar 선택자를 현재 접근성 영역으로 교체하고 초기 화면 문구를 맞췄다. 특정 가로 배치를 강제하던 검사는 관문 탐색 영역의 존재 검사로 변경했다. 비교 사례는 실제 소스 버전을 달리해 동일 ID를 기준으로 선택하는 오류를 방지한다. 취소 사례는 지연 응답 시점 이후에도 취소 상태가 남는지 검사한다.

갱신한 테스트 파일의 TypeScript 문법 검사와 diff 검사는 통과했다. 자동 Playwright 브라우저 묶음은 이번에 실행하지 않았으며, 통과한 것으로 집계하지 않는다. 위 관찰은 CUA로 실제 화면을 조작한 별도 증거다. DOM 스크롤 전체·브라우저 뒤로 가기·최초 실패 복구·중첩 조건의 모든 조합은 남아 있으므로 AC-08~10과 UX-AC-07·09 전체 완료를 선언하지 않는다.

독립 리뷰를 반영해 자동 취소 사례의 지연 응답도 별도로 실제 분석한 다른 진입점의 뷰로 변경하고 기존 URL 유지 검사를 추가했다. 전후 연결 제목만 검사하는 사례에서는 미확인 연결을 검증한다는 이름을 제거했다.

### 16.28 정상 복귀 관계의 구현 전 계약

AC-19의 정상 복귀를 조사한 결과, 현재 어댑터는 호출 대상 진입과 호출자 내부의 `control_flow`를 전달하지만 callee의 반환에서 호출자 재개 지점으로 향하는 관계를 만들지 않는다. `ValidateExecutionReferences`는 `control_flow`를 같은 호출 문맥으로 제한하고 반환·throw에서 나가는 일반 진행을 거부한다. 다른 명시적 대상은 현재 호출 대상의 첫 단계로 검증한다. 따라서 기존 관계 종류를 재사용하거나 배열상 다음 단계를 연결하는 방법은 허용하지 않는다.

복귀 관계는 ‘이 반환에 도달한 경우 호출자의 어느 표현식 평가 단계에서 이어지는가’를 뜻한다. 실제 정상 완료, 모든 반환 경로의 실행, 비동기 완료를 보증하지 않는다. 새로운 관계를 적용하더라도 기존 소스 단계·조건·호출·호출자 내부 연결을 삭제하지 않는다.

| 실제 소스 형태 | 보존해야 할 복귀 또는 제한 |
|---|---|
| `const result = price(); next(result)` | price의 명시적 반환에서 확인된 호출자 표현식 재개 지점으로 연결한다. 대입 단계가 존재하면 이를 건너뛰어 next로 연결하지 않는다. 재개 단계가 수집되지 않았다면 추정하지 않는다. |
| `outer(inner())` | inner 반환은 outer 호출로 이어진다. outer 반환의 재개 지점은 별도로 판정한다. |
| `first = price(); second = price()` | 두 price 호출 문맥의 반환과 재개 대상을 각각 유지한다. 같은 심볼로 합치지 않는다. |
| `function choose(flag) { if (flag) return 1; return 2; }` | 두 반환에서 같은 호출자 재개 지점으로 향하는 관계를 각각 보존한다. 조건은 원래 그래프에서 유지하며 두 반환이 함께 실행된다고 표시하지 않는다. |
| `function value() { return promise; }`와 `await value(); next()` | callee가 동기라는 사실만으로 next에 일반 복귀 관계를 만들지 않는다. await의 재개·실패 분석이 필요하다. |
| `try { return value; } finally { throw error; }` | return 구문만으로 정상 복귀를 만들지 않는다. finally가 종료를 바꾸므로 현재 미확인 범위를 유지한다. |
| generator·async 함수, yield 문맥, 분석이 잘린 호출 | 일반 동기 복귀 관계로 승격하지 않는다. 기존 단계·미확인 근거를 보존한다. |

구현1: 어댑터에서 호출 대상의 동기·generator 여부와 호출 위치의 await·yield·지원하지 않는 예외 문맥을 AST로 확인해야 한다. 현재 `scanSyntaxFunctions`의 isAsync만으로는 부족하다. 호출 이름이나 반환값 이름으로 분류하지 않는다.

구현2: 호출 관계·callee 호출 문맥·명시적 return·호출자 내부의 첫 재개 관계를 모두 검증해야 한다. 반환식 내부의 미확인 평가와 종료를 덮어쓰는 제어도 제외한다. 후보 문맥별로 검사하여 한 호출의 정보를 다른 호출에 적용하지 않는다.

구현3: sliced payload 관계 종류를 호환 가능한 방식으로 확장하기 전에 schema·fusion·compiler·FlowSpec 복원·compact·저장 검증을 함께 수정한다. 새 관계의 양 끝은 ordinal로 명시하고, 반환 source의 caller 참조와 target의 호출자 문맥을 왕복 대조한다. 기존 데이터에는 복귀 관계를 임의로 보충하지 않는다. 화면은 명시적으로 전달되고 검증된 관계만 ‘복귀’로 표시한다.

구현4: 위 실제 소스별 기대 관계를 먼저 검사하고, 저장·HTTP·MCP에서 관계를 보존한 뒤 브라우저의 복귀 대상 선택을 확인한다. 현재 공개 enum이나 분석 결과는 이번 조사에서 변경하지 않았다. 위 계약은 다음 구현의 기준이며 정상 복귀 기능이 완료됐다는 증거가 아니다.

독립 검토에서 await로 호출되는 동기 함수와 중첩 호출의 재개 지점을 주요 반례로 확인했다. 이 계약은 §16.26에서 남긴 AC-19·UX-AC-03·05의 분석 사실을 보완하기 위한 것이며, 미지원 사례를 화면 라벨만으로 성공 처리하지 않는다.

### 16.29 정상 복귀 관계 구현과 자동 검증

§16.28의 계약에 따라 동기 피호출 함수의 명시적 반환에서 호출자의 확인된 표현식 재개 단계로 `return` 관계를 추가했다. 피호출 함수는 동기·non-generator여야 한다. 호출자가 async여도 해당 직접 호출문이 `await`가 아니고 try 내부나 미확인 제어 대상이 아니며, 확인된 단일 재개 단계가 있을 때 대상이 된다. 함수의 다른 위치에 있는 `await`는 앞선 직접 호출의 반환 관계를 지우지 않는다. async 피호출 함수의 완료와 `await` 재개는 이 관계로 표현하지 않는다. 관계 생성은 기존 호출·조건·실행 단계를 삭제하지 않는다. 화면 관계명은 반환 구문과 구별하여 ‘복귀’로 표시한다.

검증1: 실제 TypeScript 소스에서 반복 호출, 중첩 호출, 두 조기 반환과 async 호출자가 직접 호출한 동기 함수의 재개 대상을 확인했다. 이후 `await`가 있어도 앞선 직접 호출의 복귀는 보존한다. 직접 `await`한 호출, async 피호출 함수·generator·try 내부와 finally 사례에는 일반 복귀 관계를 만들지 않는다. TypeScript 어댑터 테스트를 통과했다.

검증2: Go 검증은 호출자 참조, 호출 대상의 첫 단계, 무조건 재개 관계, 대상 호출 문맥과 심볼을 함께 대조한다. 호출 정보가 있는 분석에서 출발 단계가 없거나 해당 반환의 호출 정보가 누락된 경우 검증을 우회하던 두 사례를 재현하고 거부하도록 수정했다. 기존 호출 정보가 없는 관계 데이터에는 새 복귀 사실을 보충하지 않는다.

검증3: `TestAsyncCallerPreservesSynchronousReturn`과 `TestAsyncCallerPreservesSynchronousReturnBeforeLaterAwait`는 TypeScript slice부터 Fusion, FlowSpec 투영, FlowSequence 검증까지 `return 1;`·`return 2;`가 async 호출자의 `amount = price(true)`로만 복귀함을 확인한다. `await`한 호출의 완료를 복귀로 오인하지 않는다. 분석 의미가 달라져 slice cache identity를 `v41-async-caller-normal-return`으로 올렸다.

남은 검증: async 호출자가 직접 호출한 동기 함수의 복귀 대상은 브라우저에서도 확인했다. async 완료·예외·반복의 일반적인 실행 의미 분석과 §16.26의 전체 수용 기준은 계속 미완료다. 생성 HTML의 JavaScript 템플릿 문자열에 포함된 공백을 git diff가 trailing whitespace로 보고하므로 전체 diff 검사가 통과했다고 집계하지 않는다.

### 16.30 정상 복귀의 실제 화면 검증과 발견한 초기화 누락

실제 TypeScript 소스 `app/returnFlow.ts#checkout`를 새 실행 파일로 분석해 저장 뷰 `576198835cf312199b699de5374511a3bd8712f14475b7c1248fbab9c6b93c4e`를 열었다. `price`는 조건에 따라 두 명시적 반환을 가지며 `checkout`은 `const amount = price(value); return amount;`를 실행한다.

관찰1: 화면에서 `return 0;`의 ‘복귀’ 연결을 선택하면 checkout의 `return amount;`가 선택되고 해당 소스 범위가 강조된다. ‘원래 장면 복귀’를 누르면 `return 0;`, 조건 `value < 1`, 이전 복귀 버튼의 키보드 포커스가 복원된다. 이는 UI의 관계 탐색·복원 동작에 대한 증거다.

발견1: 위 결과의 분석 단계에는 `amount` 초기화가 없다. 현재 AST 수집은 `amount = price(value)` 같은 대입을 표현하지만 변수 선언의 초기화는 호출만 수집하므로 다음 반환 구문을 복귀 대상으로 삼는다. 화면이 전달된 관계를 정확하게 표시하더라도 반환값을 받는 실행을 생략하므로 §16.28의 재개 지점 요구를 충분히 충족하지 못한다. 이 사례는 정상 복귀 기능의 완료 근거로 사용할 수 없다.

후속1: 호출 결과를 변수에 받는 초기화 단계를 보존하고 복귀 대상을 그 단계로 지정해야 한다. 단순 식별자 초기화와 구조 분해·기본값 처리를 구분하고, 호출·초기화의 소스 범위 및 호출 문맥을 유지해야 한다. 실제 분석·저장 결과와 화면에서 초기화 선택을 다시 확인한다.

### 16.31 호출 결과 초기화와 정확한 복귀 코드 보존

§16.30의 누락을 수정했다. 변수 선언의 초기화식에서 수집한 실행이 있으면 초기화 완료 단계를 별도로 보존한다. 단순 식별자와 단일 직접 호출인 경우에만 호출 결과 참조를 붙인다. 구조 분해는 초기화식을 먼저 평가하고 키·기본값·반복자의 미확인 범위를 남기며, 기본값 호출을 무조건 실행한 것처럼 나열하지 않는다. 실행 단계가 없는 단순 상수 초기화 전체를 추가하는 변경은 아니다.

초기화 단계가 AST의 일반 expression/statement 분류에 포함되지 않아 소스 문맥이 누락되는 문제도 수정했다. 여러 선언을 포함하는 문장 전체 대신 각 선언의 정확한 범위를 보존한다. 소스 스냅샷을 사용하는 테스트가 이 범위와 단계 범위의 일치를 확인한다.

검증1: 누락 테스트의 실패를 확인한 뒤 단순 초기화의 두 복귀 대상, 호출 결과 참조, 정확한 소스 범위 및 구조 분해의 미확인 처리를 통과시켰다. 전체 TypeScript 어댑터 테스트와 전체 Go 테스트를 통과했다. 초기화 실행 순서와 구조 분해 처리에 대한 독립 리뷰에서 추가 결함은 발견되지 않았다.

검증2: 실제 저장 뷰 `308db0e30870cedcc9ddddf6e38856d48301090b617e7ec27606142e8a38d5c7`에서 `return 0;`의 복귀 연결을 선택하면 `amount = price(value)`가 선택된다. 소스 확인 표시와 정확히 해당 구문만 강조되는 것을 CUA로 확인했다. 다음 `return amount;`는 별도 후속 단계로 유지된다. HTTP의 해당 flowContext도 precision=exact다.

이 검증은 §16.30의 초기화 누락과 소스 선택 문제를 해결한다. 구조 분해·비동기·예외의 일반적인 실행 의미 및 §16.26의 나머지 수용 기준은 계속 미완료다.

### 16.32 배타적 결제 분기와 공통 처리의 통합 검증

`TestPaymentAlternativesPreserveSharedContinuation`을 추가했다. 테스트 소스는 checkout, 카드 처리, 계좌 처리, 영수증 처리를 네 TypeScript 파일로 나눈다. 실제 결제 서비스를 호출하는 시험은 아니며, 코드 분석기가 서로 다른 구현 파일의 배타적 경로와 합류를 보존하는지 검증하는 사례다.

검증1: 참 조건은 카드 호출, 거짓 조건은 계좌 호출로 연결된다. 각 피호출자의 반환은 자신의 결과 대입으로만 복귀한다. 두 결과 대입은 하나의 `receipt(payment)` 호출로 이어진다. 소스 범위, 투영 후 관계 개수, 모든 단계의 단일 부모도 검사한다. 어댑터에서 fusion·FlowSpec 투영·관문 검증까지 통과했다.

검증2: 실제 HTTP 분석과 저장 뷰 `d179e381ec52558395cdecfc6781859d823198f95a4a1061c5f1149617a8db6c`에는 10개 실행 단계와 9개 관문이 있다. CUA로 공통 반환 관문을 펼쳐 두 내부 단계가 나타남을 확인했다. 카드와 계좌 조건을 번갈아 선택해도 공통 영수증 호출·반환은 경로 포함으로 유지되고, 선택한 공통 호출에는 두 결과 대입의 선행 연결이 표시된다.

검증3: 공통 호출에서 `payment/receipt.ts`의 구현으로 이동하면 정확한 소스와 checkout으로의 복귀 관계가 표시된다. `make fmt`, `make vet`, `make check-naming`, `make test`를 통과했다.

§16.26의 AC-18·UX-AC-02에는 위 실제 분석·화면 사례를 추가 증거로 연결한다. 다른 파일 탐색의 AC-07·UX-AC-06도 보완한다. 비동기 결제 완료·외부 실패·트랜잭션을 검증한 것으로 확대하지 않으며 사용자 과제 관측도 대신하지 않는다.

### 16.33 완료 대기와 성공 후 재개의 구분

실제 소스 `const result = await save(); return result;`를 분석한 결과, 기존 모델은 save 호출과 결과 초기화만 연결하고 await 자체를 생략했다. 정상 복귀를 제외하는 것만으로는 사용자가 대기 지점을 이해할 수 없으므로, await 표현식을 별도 실행 단계로 보존했다.

계약1: `await` 단계는 피연산자를 평가한 뒤의 완료 대기를 뜻한다. 이 단계에서 같은 호출 문맥의 다음 단계로 향하는 `await_resume` 관계는 대기가 성공한 경우의 재개 지점이다. 실제 성공·완료 시간·거절 경로·병렬 작업의 전체 완료를 보증하지 않는다. 거절 이후 경로는 별도의 미확인 근거로 유지한다. `Promise.all` 이름만으로 병렬 완료 조건을 만들지 않는다.

계약2: sliced payload와 FlowSpec의 단계·관계 enum을 확장했다. 실행 참조 검증은 `await_resume` 출발이 await인지 검사하고, await에서 일반 control_flow가 나가는 것을 거부한다. 독립 리뷰에서 정상 복귀 관계가 없는 비동기 저장 그래프의 검증 누락을 발견하여, await 단계 또는 await_resume 관계만 있어도 공통 참조 검증을 수행하도록 수정했다. 해당 우회 사례의 회귀 테스트를 추가했다.

검증1: 실제 스냅샷 테스트에서 호출 피연산자, 대기 단계의 정확한 소스 범위, 결과 초기화로의 재개, 거절 경로의 미확인 상태를 검사한다. 전체 TypeScript 어댑터 검사와 Go 검사, Svelte 검사, 프런트엔드 36개 테스트 및 빌드를 통과했다. 최종 Go 검사는 리뷰 수정과 새 화면 번들을 포함한다.

검증2: 실제 저장 뷰 `d5e679f18db80d87fb1adc7acdee971e26d058d3acde0bc21487d69e877a786d`에서 ‘완료 대기’를 선택하면 `await save()`의 소스가 표시된다. ‘대기 성공 후 재개’를 선택하면 `result = await save()`로 이동하며, 다음 반환은 별도 단계로 유지된다. 대기는 연결 미확인 표시도 함께 유지한다. CUA로 이 선택과 코드 표시를 확인했다.

이 변경은 AC-19의 비동기 대기 지점과 이후 처리 구분을 보완한다. UX-AC-03의 병렬 완료 조건, 거절·catch·finally·재시도 관계 및 AC-15의 트랜잭션 실패 분석은 여전히 미완료다.

### 16.34 대기 관계의 FlowSpec·저장·MCP 전달 검증

`TestAwaitResumptionSurvivesStorageHTTPAndMCP`에서 실제 TypeScript 대기 소스를 adapter→fusion→FlowSpec 투영→저장→HTTP→MCP full/compact까지 전달한다. 대기 단계, 성공 후 재개 관계, 미확인 거절 설명, 관문 소속과 조회 전후 저장 bytes를 대조한다. 호출자 참조와 소스 위치도 compact에서 유지한다.

이 검사에서 FlowSpec 생성 오류를 발견했다. fusion은 자유 형식의 미확인 설명을 enum 필드인 `unknowns.reason`에 넣어 스키마 검증을 실패시켰다. 기존 유효한 사유 코드는 그대로 유지하고, 자유 설명은 resolution 상태에 맞는 사유 코드로 요약하도록 수정했다. 원문은 연결의 `unresolvedReason`에 보존되며 의미 그래프 투영에서 상세 미확인 사유로 전달된다.

통합 테스트는 대기 실패 설명이 HTTP와 MCP full/compact까지 유지되고, 대기 단계가 verified로 승격되지 않으며, 저장 데이터를 조회만으로 다시 쓰지 않는 것을 확인한다. 독립 리뷰를 반영하여 MCP full 응답도 계층뿐 아니라 연결과 미확인 사유를 비교한다. 집중 통합 테스트와 전체 Go 검사를 통과했다.

이 결과는 대기 전달 경로의 증거다. 성공 재개 연결을 실제 성공이나 거절 경로 검증으로 확대하지 않으며, §16.33에 기록한 비동기·예외의 미완료 범위는 유지한다.

### 16.35 선택한 코드의 미확인 사유 표시

기존 화면은 대기 단계에 ‘연결 미확인’을 표시했지만, 거절 이후 경로를 확인하지 못했다는 구체적인 설명을 선택 문맥에서 보여주지 않았다. 맥락 패널에 ‘관련 분석 한계’를 추가하여 코드 보기와 처리 보기 모두에서 확인할 수 있도록 했다.

단계 ID, 명시적인 boundary 참조, 해당 단계의 미확인 연결 대상과 일치하는 사유만 표시한다. 전역 내부 분석 상태와 다른 단계의 사유는 포함하지 않는다. 중복 설명은 한 번만 표시하고, 기존 고정 사유 코드는 한국어 설명으로 보여준다. 소스 범위 한계는 기존 별도 설명을 유지한다.

프런트엔드 38개 테스트, Svelte 검사, 빌드 및 Go 화면 서버 테스트를 통과했다. 기존 저장 뷰 `d5e679f18db80d87fb1adc7acdee971e26d058d3acde0bc21487d69e877a786d`를 새 화면으로 열어 대기 단계를 선택했다. 코드 보기와 처리 보기 모두 ‘대기 실패·거절 이후의 예외 경로를 확인하지 못했습니다.’라는 설명을 표시하는 것을 CUA로 확인했다. 이 검증에는 재분석이나 저장 데이터 변경이 필요하지 않았다.

이 변경은 선택 코드의 연결 미확인 이유를 설명한다. 세 종류의 요약 한계가 동시에 발생하는 전체 과제, 미확인 실행 관계 자체의 해소 및 사용자 과제 관측은 여전히 남아 있다.

### 16.36 실행 단계별 미확인 사유의 분리

§16.35의 화면 연결을 점검하면서 같은 함수의 서로 다른 한계가 하나의 `.control_flow` 대상 참조를 공유하는 문제를 재현했다. await와 생성자 한계가 같은 subject에 저장되면 해당 단계에 다른 설명까지 표시될 수 있다.

새 분석의 미확인 참조에 해당 실행 단계 또는 조건 관계의 ordinal을 포함하여 분리했다. 이는 분석 내부 참조이며 실제 코드 심볼이나 실행 순서 주장으로 사용하지 않는다. 기존 저장 분석의 참조는 다시 쓰지 않는다. 분석 캐시 버전을 갱신했다. TypeScript 테스트는 한 함수 안의 대기·생성자 사유가 서로 다른 대상을 갖는지 검사한다.

실제 저장 뷰 `21279af793de93c1b3ff58eda72b9fd15600a47c40c6762f9eebe66db31c4932`에서 대기 선택 시 거절 경로 설명만, 생성자 선택 시 생성자·초기화 설명만 표시되는 것을 CUA로 확인했다.

전체 Go 검사 중 예제 앱의 `.codeflow` 실행 상태를 테스트 디렉터리에 복사하여 스냅샷 상태가 충돌하는 별도 실패를 발견했다. harvest 테스트의 예제 복사에서 이 런타임 디렉터리를 제외하도록 수정했다. 제품 소스와 기존 실행 상태는 삭제하거나 수정하지 않았다.

수정 후 `make fmt`, `make vet`, `make check-naming`, `make test`를 모두 통과했다. 전체 TypeScript 어댑터 검사와 변경 소스의 diff 검사도 통과했다. 과거 저장 분석의 공유 참조까지 정확하게 재분리한 것으로 간주하지 않는다.

### 16.37 재시도 반복의 누락 재현과 구현 계약

실제 `app/retryFlow.ts#checkout`에서 `while (count < limit) { count++; if (attempt(count)) return count; } return -1;`를 분석했다. 저장 뷰 `44d094fbafc8d3f30f1c179f924e1d1cceb66db734cdda7e7e9f882b69802d38`에는 7개 실행 단계가 있으나 반복 진입의 참 조건, 내부 판단의 거짓 결과에서 다음 조건 검사로 돌아가는 관계, 반복 조건의 거짓 결과에서 최종 반환으로 가는 관계가 없다. 기존 일반 진행 연결로 실제 반복을 설명할 수 없다.

계약1: while 조건 평가의 첫 단계를 반복 진입점으로 유지한다. 조건에 호출이 있으면 반복마다 그 호출부터 다시 평가한다. 조건 판단의 참 결과는 본문으로, 거짓 결과는 반복 이후 처리로 연결한다. 본문의 정상 진행 끝에서만 명시적인 loop_back 관계로 조건 평가 시작에 돌아간다. return·throw에서 반복 연결을 만들지 않는다. 빈 본문의 자기 연결과 첫 검사부터 거짓인 경로를 보존한다. 관문이나 단계를 횟수만큼 복제하지 않는다.

계약2: 호출·복귀·대기 관계와 별도로 loop_back을 전달하고 검증해야 한다. 같은 호출 문맥 안의 양 끝 참조와 조건 판단의 결과를 유지하며, 저장·HTTP·MCP와 화면에서도 반복 연결임을 구별한다. break·continue·중첩 반복·예외 구문은 각 제어 대상과 종료를 입증한 뒤 지원한다. 단순 while 지원을 전체 반복·재시도 지원으로 집계하지 않는다.

계약3: 기존 조건 탐색은 단계 ID마다 결과를 한 번 고르고 방문 집합으로 탐색을 끝낸다. 독립 리뷰에서 이 방식이 반복마다 같은 결과를 강제하는 문제를 지적했다. `while(count < 2)`의 첫 결과가 참이더라도 이후에는 거짓이 되어 종료할 수 있다. 따라서 반복 연결을 일반 경로처럼 통과시키며 종료 경로를 영구 제외해서는 안 된다. 반복 연결에서 이후 조건 재평가의 한계를 표시하고, 선택한 결과를 모든 반복에 적용하는 경로 강조를 중단해야 한다. 원래 거짓 종료 연결은 항상 탐색 가능한 상태로 남긴다.

다음 검증은 참 진입·거짓 종료·정상 반복·조건식 호출 재평가·조기 반환·빈 본문과, 선택한 첫 조건이 이후 반복의 결과를 고정하지 않는 UI 사례를 포함한다. 이 항목은 구현 전 계약이며 반복 기능의 완료 증거가 아니다.

### 16.38 단순 while의 반복 관계 구현과 화면 검증

§16.37에 따라 단순 while의 참 진입, 거짓 종료, 정상 본문 끝에서 첫 조건 평가로 돌아가는 `loop_back`을 구현했다. 조건에 호출이 있으면 해당 호출부터 재평가한다. 반환·throw를 반복 복귀로 연결하지 않는다. 빈 본문은 참 자기 연결과 거짓 종료를 구별한다. break·continue·중첩 반복·label·try·switch·await·yield가 포함된 반복은 기존 미확인 경로를 유지한다.

sliced payload·FlowSpec enum과 실행 참조 검증에 loop_back을 추가했다. 같은 호출 문맥 안에서 앞선 단계 또는 자신으로 돌아가는 대상인지 확인하고, 조건이 있는 복귀의 판단·결과를 보존한다. 의미 그래프의 저장 검증도 이 관계가 있으면 실행 참조를 검사한다. 읽기 순서에서 반복 횟수를 만들거나 단계를 복제하지 않는다.

조건 탐색은 loop_back을 만나면 강조를 중단하고 다음 반복의 조건 재평가를 안내한다. 첫 결과를 모든 반복에 적용하지 않으며, 거짓 종료 연결과 다른 단계는 계속 접근할 수 있다. 프런트엔드 테스트는 참 선택의 강조 범위 제한과 거짓 선택의 종료 도달을 각각 검사한다.

검증1: TypeScript 실제 소스 테스트가 참·거짓 연결, 내부 guard의 거짓 복귀, 조건 함수 재호출, 빈 본문, 조기 반환 및 미지원 break를 검사한다. Go 통합 테스트 `TestWhileConditionRelationsSurviveProjection`은 adapter→fusion→투영→관문 검증에서 조건 호출로 향하는 복귀와 모든 관계 수를 확인한다. 별도 참조 테스트는 앞으로 향하는 복귀, 다른 호출 문맥, return에서 나가는 복귀를 거부한다.

검증2: 저장 뷰 `a59f583b2b3796a9a984b4e05d2513082f9aacf161dc1c349cd3225c2f7aad46`에서 ‘다음 반복의 조건 재평가’를 확인했다. 반복 조건 참을 선택하면 다음 반복은 이 선택으로 확정하지 않는다는 안내가 표시되고, 거짓 종료 연결을 눌러 `return -1;` 소스를 계속 볼 수 있다. CUA로 검증했다.

전체 TypeScript 어댑터 검사, 프런트엔드 39개 테스트, Svelte 검사·빌드, `make fmt`, `make vet`, `make check-naming`, `make test`를 통과했다. 독립 리뷰에서 추가 결함은 발견되지 않았다. 단순 while의 소스 관계와 조건 탐색에 대한 증거이며 전체 반복·예외 기반 재시도 지원의 완료로 집계하지 않는다.

### 16.39 단순 while의 break·continue 처리

라벨 없는 break와 continue를 별도 실행 단계로 보존했다. 지원하는 while마다 종료 경로와 다음 반복 경로를 모아, break는 반복 이후 처리에 `loop_exit`으로 연결하고 continue는 첫 조건 평가에 `loop_back`으로 연결한다. 제어 이동 뒤 현재 블록의 도달 불가능한 문장은 수집하지 않는다. 조건 판단→이동 단계→목적지로 나누어 조건 결과도 보존한다.

스키마와 저장 참조 검증은 새 단계·관계를 인식한다. break를 일반 control_flow나 loop_back으로 연결하거나 continue를 일반 control_flow로 연결하면 거부한다. 반복 종료는 같은 호출 문맥의 뒤쪽 단계로만 향한다. 라벨·중첩 반복·예외·비동기 반복의 미확인 범위는 유지한다.

TypeScript 테스트에서 break의 종료 대상과 continue의 조건 재평가 대상, 라벨 이동의 미확인 처리를 확인했다. Go 참조 테스트는 잘못된 이동 종류를 거부한다. `TestLoopControlTransfersSurviveProjection`은 실제 소스의 어댑터·fusion·FlowSpec 투영에서 두 관계와 단계 종류를 보존하는지 검사한다.

실제 저장 뷰 `c30544bffdf8c7fceec9c56945e3b4f596b22c1cfe5426d5c51fa7e3f2d1cfa9`에서 break의 ‘반복 종료 후 진행’을 선택하면 `return count;`로, continue의 ‘다음 반복의 조건 재평가’를 선택하면 `while (count < 3)`으로 이동하고 정확한 소스 범위를 강조한다. CUA로 확인했다. 독립 리뷰에서 추가 결함은 발견되지 않았다.

검증: 전체 TypeScript 어댑터 검사, 프런트엔드 39개 테스트, Svelte 검사·빌드와 `make fmt`, `make vet`, `make check-naming`, `make test`를 통과했다. 전체 Go 검사는 새 화면 번들과 break·continue 투영 검사를 포함한다. 이 증거를 중첩·라벨·예외 기반 재시도 지원으로 확대하지 않는다.

### 16.40 중첩 while의 제어 대상 구분

중첩된 지원 범위의 while을 분석하도록 확장했다. 각 반복의 제어 문맥을 따로 유지하여 안쪽 continue는 가장 가까운 반복 조건으로, 안쪽 break는 그 반복 이후의 처리로 이어진다. 안쪽 반복이 바깥 본문의 마지막 처리라면 break 직후 바깥 조건을 재평가한다. 이 관계는 일반 종료나 일반 반복 복귀와 혼동하지 않도록 `loop_exit_back`으로 보존하고 ‘내부 반복 종료 후 외부 조건 재평가’로 표시한다.

이 관계는 break에서 같은 호출 문맥의 앞선 단계로만 향할 수 있고 자기 자신으로 돌아갈 수 없다. 조건 탐색도 이 관계에서 강조를 중단한다. 안쪽 반복 뒤 바깥 본문에 실행 단계가 있으면 기존 loop_exit으로 그 단계에 이어진다. 라벨·try·switch·비동기 반복과 for/do 반복은 이번 확장 범위가 아니다.

검증1: 실제 TypeScript 소스에서 안쪽 break의 바깥 조건 재평가와 안쪽 continue의 가장 가까운 조건 복귀를 확인했다. Go 통합 테스트 `TestNestedWhileBreakResumesOuterCondition`은 4개 단계와 복합 종료 관계를 adapter→fusion→투영→관문 검증까지 대조한다. 프런트엔드 조건 검사는 일반 반복 복귀와 복합 종료·재평가 모두에서 강조를 중단하는지 확인한다. 독립 리뷰에서는 세 겹 while도 추가 점검했고 결함은 발견되지 않았다.

검증2: 저장 뷰 `30abc22c6d9e6929d1cb856920ec2a063d1411287135d90986767e94001f87d7`에서 안쪽 break의 연결을 선택하면 바깥 `while (outer)`로 이동하고 해당 소스를 강조한다. CUA로 확인했다. 이는 코드 연결 증거이며 실제 반복 횟수나 종료 가능성을 보증하지 않는다.

검증: 전체 TypeScript 어댑터 검사, 프런트엔드 40개 테스트, Svelte 검사·빌드, `make fmt`, `make vet`, `make check-naming`, `make test`를 통과했다. 전체 Go 검사는 새 번들과 중첩 반복 투영 검사를 포함한다.

### 16.41 실행 탐색의 코드 구문 중복 보완

증감·단순 대입·삭제·배열 구조 분해 같은 구문은 호출이나 세미콜론이 없으면 기존 제목 판별을 통과해 왼쪽 목록에 코드 그대로 표시됐다. 코드 구문만 제목으로 제공된 상태 변경은 단계 역할과 확인된 소속 심볼로 표시하고, 별도 처리명과 확인된 호출 대상·결과 반영 이름은 유지하도록 보완했다. 이 처리는 표시용이며 코드의 실행 의미나 관문 소속을 추론하는 기준으로 사용하지 않는다.

실행 탐색에서는 일반 상태 변경을 주 제목으로 반복하지 않는다. 소유 함수·클래스를 주 제목으로, ‘상태 변경’을 보조 정보로 표시한다. 확인된 호출 대상과 직접 결과 반영 이름은 기존처럼 주 제목으로 유지한다. 실제 저장 뷰에서 `count++`는 `checkout`과 ‘상태 변경’으로, 선택한 코드 패널에서는 원래 `count++`로 표시되는 것을 확인했다. 데이터나 소스의 재분석은 필요하지 않았다.

실제 API 브라우저 회귀는 코드 구문뿐인 상태 변경이 소유 구현과 역할로 표시되고, 원래 문장은 왼쪽 실행 탐색에 나타나지 않는지 확인한다. 일반적인 처리명 없이 같은 함수에 여러 상태 변경이 있는 경우의 구별성은 사용자 과제에서 계속 평가해야 하며, 이 변경만으로 이해 속도 향상을 입증했다고 간주하지 않는다.

### 16.42 호출·단일 반환·결과 적용의 하나의 처리 관문

직접 호출 결과를 대입하는 관문은 기존에 호출과 대입만 묶었다. 호출된 함수가 단순히 값을 반환한 경우에도 반환 단계가 별도 관문으로 남아, 하나의 값 전달을 세 개의 상위 관문으로 읽게 되는 문제가 있었다.

호출, 호출된 함수의 반환, 호출자 대입을 하나로 묶는 조건을 추가했다. 대입은 기존의 `assignmentSourceOrdinal`로 호출을 직접 가리켜야 하며, 호출 대상 실행은 반환 하나만 포함해야 한다. 호출에서 그 반환으로 향하는 확인된 호출 관계와 반환에서 대입으로 향하는 확인된 복귀 관계도 모두 필요하다. 대입을 대표 코드로 사용하고 세 단계는 실행 순서대로 자식 타임라인에 보존한다.

호출 대상에 판단·상태 변경·외부 효과·여러 단계·분석 경계가 있으면 이 규칙은 적용하지 않는다. 호출과 대입만 묶어 중간 처리를 건너뛰면 관문의 읽기 순서와 실제 단계 순서가 어긋나므로, 그 경우에는 세 단계를 분리한다. 이 규칙은 함수 이름이나 인접한 줄을 근거로 처리 목적을 추정하지 않는다.

`TestAssignmentGatewayIncludesOnlyProvenSingleCalleeReturn`은 단일 반환의 세 단계 관문과, 호출 대상에 자체 처리가 있을 때의 분리를 각각 검사한다. 실제 TypeScript 대규모 분석은 257개 단계 중 80개 호출·반환·대입 묶음을 97개 관문으로 전달하며, 저장·HTTP·MCP full/compact에서 각 자식 순서와 대표 대입을 대조한다. 실제 화면에서 17번째 관문을 펼쳐 세 자식을 확인했고, 긴 실행 탐색의 ‘선택한 흐름으로 이동’과 중앙의 ‘실행 탐색으로 이동’을 키보드 Enter로 실행해 같은 선택 자식으로 초점이 복귀하는 것을 확인했다. 단위 의미 그래프 검사와 실제 어댑터·전달 통합 검사를 통과했다.

이 변경은 확인된 단순 값 전달을 하나의 처리로 읽게 한다. 여러 내부 처리의 일반적인 목적 기반 병합, 요청별 중요도 판정과 사용자 과제 기반 이해 속도 검증은 여전히 별도 미완료 항목이다.

### 16.43 Next.js 접근 거부 관문과 민감 입력 표시

Next.js route의 `POST`에서 `request.headers.get('authorization')`로 credential을 얻고 `if (!credential)`에서 거부 응답을 만드는 사례를 실제 분석했다. `TestNextRouteAuthenticationDenialPreservesGateway`는 credential 확인이 대표 단계인 판단 관문으로 남는지, truthy 결과가 `Response.json(...)` 경계와 그 반환으로 이어지는지, falsy 결과가 정상 처리 호출로 이어지는지, 각 단계의 route 소스 위치가 보존되는지를 검사한다.

실제 저장 FlowView는 7개 관문과 8개 실행 단계를 보였다. credential 대입의 우변은 `credential = "***REDACTED***"`로 완전히 가리며, 대입문 안에 `***REDACTED***authorization')` 같은 잘린 코드 조각을 남기지 않는다. 헤더를 읽는 호출은 별도 실행 단계로 표시되고, 이 마스킹은 판단·분기·응답 경계·반환의 관계와 근거 위치를 유지한다.

이전 마스킹으로 저장된 잘린 slice 결과를 재사용하지 않도록 slice 캐시 의미 버전을 갱신했다. 같은 소스의 새 분석도 현재 마스킹 규칙을 거쳐 화면에 반영된다.

이 증거는 Next.js route handler 범위의 접근 거부 흐름이다. Express·Nest 등의 middleware 등록을 모두 분석한다는 의미는 아니며, 그 등록 관계를 요청 흐름에 포함하려면 별도 어댑터 근거와 사례 검증이 필요하다.

### 16.44 await 거절·복구·정리 관계

`try` 안의 `await`가 있고 대응 `catch`가 있을 때, 성공 재개와 거절 복구를 같은 일반 순서로 합치지 않는다. `await`에서 try의 다음 단계로 가는 관계는 `await_resume`이며, catch의 첫 단계로 가는 관계는 `failure`다. 정상 try 완료와 catch 완료는 모두 finally의 첫 단계로 향하고, finally가 끝난 뒤에만 다음 일반 단계로 이어진다.

이 규칙은 await가 있는 try/catch/finally와 같은 호출 문맥, 같은 파일·심볼에서 확인된 명시적 단계에만 적용한다. try 본문에 직접 적힌 `throw`는 catch 첫 단계로 `failure` 관계를 만들 수 있다. 동기 호출이 throw하는 catch 원인, 재시도 횟수, 병렬 완료 순서는 추정하지 않는다. catch가 없거나 거절 원인을 await 또는 직접 throw로 확인하지 못하면 기존 미확인 연결을 유지한다.

try 또는 catch가 `return`·`throw`로 끝나고 finally 첫 단계가 같은 호출 문맥에서 확인되면, 종료 단계에서 그 단계로 `finally` 관계를 만든다. finally 내부의 뒤이은 단계는 정리 실행 순서로만 보존하며, finally 다음 일반 문장으로 이어지는 정상 연결은 만들지 않는다. finally 자체가 return·throw하여 앞선 종료를 바꾸는 최종 결과, 동기 throw가 catch로 복구되는 원인은 확인하지 못한 범위로 남긴다.

`TestCaughtAwaitPreservesRecoveryAndFinally`은 `await reserve()`에서 `commit()`으로 가는 성공 재개, `rollback()`으로 가는 실패 관계, 두 경로의 `release()` 합류와 `complete()` 진행을 adapter→fusion→FlowSpec→SemanticMap→FlowSequence까지 대조한다. 실제 FlowView에서도 성공 재개와 실패 관계가 각각 표시되고, 두 경로가 `release()`와 `complete()`로 이어지는 것을 확인했다. 최신 캐시 의미 버전을 포함한 전체 검사는 후속 실행에서 다시 확인한다.

### 16.45 단순 동기 switch의 선택과 종료 관계

중첩 반복·예외·비동기 구문이 없는 동기 `switch`는 선택식, 각 `case` 또는 `default`, 절 내부 처리, 이후 처리의 순서로 보존한다. 선택식은 각 case 후보로 연결되고, case에 처리문이 있으면 그 첫 단계로 이어진다. 처리문 없이 다음 case로 떨어지는 경우와 case 끝에서 break 없이 다음 case로 이어지는 경우는 다음 case의 시작으로 연결한다. `default`가 없으면 선택식에서 switch 이후 처리로 갈 수 있는 경로를 함께 보존한다.

라벨 없는 `break`는 `switch_exit`으로 같은 호출 문맥의 switch 이후 단계에만 연결한다. 일반 진행이나 반복 종료 관계로 대신 표현하지 않으며, 뒤쪽 단계가 없으면 종료 목적지를 추정하지 않는다. 화면은 이 관계를 ‘분기 종료 후 진행’으로 표시해, 사용자가 break 뒤 실제로 이어지는 처리를 바로 선택할 수 있게 한다.

중첩 switch, 반복문·try·await·yield·라벨이 포함된 switch와 switch 안에서 호출이 던진 예외의 복구는 이 규칙에서 제외한다. 이 경우 기존의 미확인 경계를 유지한다. case 일치 조건은 현재 조건 결과 enum으로 환원하지 않으며, case 헤더 자체를 선택 근거로 표시한다.

`TestSwitchRelationsSurviveProjection`은 `switch (action)`에서 `case "approve":`, case에서 `approve()`, `break;`에서 `finish()`로의 `switch_exit`을 adapter→fusion→FlowSpec→FlowSequence까지 대조한다. `TestSwitchExitRequiresForwardBreak`은 break가 아닌 단계와 뒤로 향하는 종료 관계를 거부한다. 실제 FlowView에서 세 case 후보, case별 첫 처리, `break;`의 ‘분기 종료 후 진행’과 `finish()` 목적지를 확인했고, 실행 탐색도 break를 ‘분기 종료’로 표시했다. `make fmt`, `make vet`, `make check-naming`, `make test`, `make build`를 통과했다.

### 16.46 정적 Promise.all의 병렬 완료 대기

`await Promise.all([save(), notify()])`처럼 전역 `Promise`의 정적 배열에 두 개 이상 직접 호출이 있을 때, 호출 간에 일반 진행 관계를 만들지 않는다. 각 호출은 같은 `await` 단계로 `parallel_wait` 관계를 만들고, 그 대기 단계만 이후 처리로 `await_resume`한다. 따라서 호출 시작의 텍스트 순서는 보이더라도, 하나가 끝난 뒤 다른 호출이 실행된다고 표시하지 않는다.

배열이 아닌 인수, spread, 콜백·조건식·중첩 표현식, 하나뿐인 작업, 소스 안에서 `Promise`를 다시 선언한 경우에는 병렬 내부 관계를 추정하지 않는다. 해당 `await`만 보존하고 ‘병렬 대기의 내부 작업 관계를 확인하지 못했습니다.’ 한계를 남긴다. 모든 작업의 성공·거절 결과, 취소, 실제 완료 순서와 병렬 실행 가능성 일반화는 이 규칙의 범위가 아니다.

`parallel_wait`는 같은 호출 문맥의 call에서 뒤에 오는 await로만 검증한다. TypeScript 검사는 두 멤버가 await로 향하고 서로 직렬화되지 않으며, 미지원 Promise.all이 한계로 남는지 확인한다. 저장·HTTP·MCP 통합 검사는 이 관계가 전체 전달 경로에서 보존되는지 확인한다. 실제 FlowView에서 save·notify가 같은 await로 ‘병렬 완료 대기’로 연결되고 await 관문이 ‘2개 병렬 작업 완료 대기’로 표시되며, 이후 `finish(result)`로 성공 재개하는 것을 확인했다. `make fmt`, `make vet`, `make check-naming`, `make test`, `make build`를 통과했다.

### 16.47 비동기 while 재시도의 조건 재평가

단순 while 본문에 `await`가 있어도, finally 없는 단순 try/catch·중첩 반복·switch·yield·label이 없으면 대기 성공 뒤의 재시도를 확인한다. 본문의 마지막 await에서 같은 while 조건으로 향하는 관계는 `await_loop_back`이며, 일반 성공 재개나 동기 loop_back으로 표시하지 않는다. 조건의 거짓 경로는 반복 뒤 처리로 계속 남는다.

이 관계는 같은 호출 문맥에서 await 단계가 앞선 while 조건으로 돌아갈 때만 유효하다. 대기 거절의 원인·catch 복구, 재시도 횟수, timeout·backoff, 외부 호출의 실제 성공 여부는 추정하지 않는다. 조건 탐색은 이 연결을 만나면 이후 반복 결과를 고정하지 않고 재평가 안내를 표시한다.

`TestAwaitRetryLoopSurvivesProjection`은 `await retryRequest()`에서 `while (!done)`으로 돌아가는 `await_loop_back`과 거짓 조건의 `finish()` 경로를 adapter→fusion→FlowSpec→FlowSequence까지 검증한다. `TestRecoveredAwaitRetryLoopSurvivesProjection`은 같은 대기의 실패가 `recover()`로 향하고 복구 뒤에 `loop_back`으로 조건을 재평가하는지 대조한다. 실제 FlowView에서 성공 재시도의 ‘대기 성공 후 다음 반복의 조건 재평가’, 실패의 `recover()` 연결, 복구 후 조건 재평가와 조건 거짓의 `finish()` 연결을 확인했다. `make fmt`, `make vet`, `make check-naming`, `make test`, `make build`를 통과했다.

### 16.48 단순 for의 조건·증감·재평가 관계

단순 `for (초기화; 조건; 증감) { 본문 }`에서 조건 판단의 참 경로는 본문으로, 거짓 경로는 반복 뒤 처리로 향한다. 본문의 정상 완료와 라벨 없는 `continue`는 증감식으로 향하고, 증감식이 끝난 뒤에만 다음 조건 평가로 `loop_back`한다. 따라서 continue가 증감식을 건너뛰거나 본문이 조건으로 바로 돌아간다고 표시하지 않는다.

중첩 반복·try·switch·yield·라벨이 없는 형태만 지원한다. 비동기 대기가 있는 for, do/for-await, break 이후 바깥 반복 재개와 증감식 내부의 복합 실행 관계는 기존 미확인 범위로 남긴다. 반복 횟수와 실제 조건값은 정적으로 추정하지 않는다.

`slice_control_connections.test.js`는 조건 참의 본문 진입, 조건 거짓의 반복 종료, 본문에서 증감식으로의 진행, 증감식의 조건 재평가와 continue의 증감식 진입을 확인한다. `TestCountedForLoopRelationsSurviveProjection`은 이 관계가 adapter→fusion→FlowSpec→FlowSequence까지 보존되고 참·거짓 조건도 유지되는지 대조한다. 실제 FlowView에서 조건·본문·증감·다음 조건 재평가와 종료 경로를 확인했다. `make fmt`, `make vet`, `make check-naming`, `make test`, `make build`를 통과했다.

### 16.49 단순 do...while의 본문 재진입

단순 `do { 본문 } while (조건)`은 본문을 먼저 한 번 실행한 뒤 조건을 평가한다. 조건 거짓은 반복 뒤 처리로 진행하고, 조건 참은 앞선 본문 첫 단계로 `loop_reentry` 관계를 만들어 다음 반복의 본문 진입을 뜻한다. 기존 `loop_back`은 본문 끝에서 조건으로 돌아가는 관계이므로 do의 조건 참에 재사용하지 않는다.

`loop_reentry`는 같은 호출 문맥에서 branch가 앞선 본문 단계로 향하고, 그 branch의 truthy 조건을 가진 경우만 유효하다. 저장·FlowSpec·의미 검증은 일반 진행과 구별하며, FlowView는 ‘다음 반복 본문 진입’으로 표시한다. 반복 횟수와 실제 조건값은 정적으로 추정하지 않는다.

`slice_control_connections.test.js`, `TestLoopReentryRequiresTrueBranchAndEarlierBody`, `TestDoLoopRelationsSurviveProjection`은 본문→조건, 조건 참→본문 재진입, 조건 거짓→반복 이후 처리를 각각 검증한다. 실제 FlowView에서도 `apply()`→`while (again)`, 조건 참의 ‘다음 반복 본문 진입’, 조건 거짓의 `finish()` 경로와 코드 범위를 확인했다. `make fmt`, `make vet`, `make check-naming`, `make test`, `make build`를 통과했다. 중첩 do, try·await·switch·label이 든 do와 for-await는 미확인 범위로 남긴다.

이 기록을 작성한 시점에는 `for await...of`를 동기 `for...of` 규칙에서 제외했다. 현재 지원 범위와 검증은 §16.66이 대체한다. 중첩 반복, label, switch, finally, 동적 iterator와 iterator 정리·거절의 복구는 여전히 미확인 한계를 유지한다.

### 16.51 동기 호출 함수의 throw와 호출자 catch 관계

호출한 함수 안의 명시적 `throw`는 호출자 `catch`와 연결되지 않아, 실패 원인이 코드 흐름에서 끊겼다. 이를 보완하되 호출이 실패할 수 있다는 일반 추정을 추가하지 않았다.

- 피호출 함수가 동기·직접 호출이고, 명시적 `throw`가 그 함수 안에서 다시 catch 또는 finally로 처리되지 않으며, 호출자에 해당 호출을 감싸는 `catch`의 첫 실행 단계가 있을 때만 `failure` 관계를 만든다.
- 관계는 피호출 throw, 피호출 invocation의 caller step, 호출자의 resolved cross-file call, 호출자 catch 대상의 invocation과 소스 심볼을 함께 대조한다. 어느 하나라도 없으면 관계를 만들지 않는다.
- 호출자가 `async`여도 피호출 함수가 동기이고 호출문 자체를 `await`하지 않으면 throw는 호출 지점에서 발생하므로 같은 규칙으로 호출자 `catch`에 연결한다. `await`한 async callee는 별도 거절 관계를 사용한다. generator·callee 내부에서 이미 처리한 throw는 이 관계의 대상이 아니다. 기존 미확인 표시는 유지한다.
- 분석 의미가 달라져 새 `v37-sync-return-async-caller` slice cache identity를 사용한다. 저장된 FlowView는 재작성하지 않는다.

검증: `slice_control_connections.test.js`는 동기 호출 throw가 동기·async 호출자의 recover로 이어지고, catch가 없는 경우 관계를 만들지 않음을 검사한다. `TestCalledThrowFailureRequiresMatchingCallAndRecovery`는 위조된 호출·복구 관계를 거부한다. `TestCalledThrowPreservesCallerRecovery`와 `TestAsyncCallerCatchesDirectSynchronousThrow`는 TypeScript slice부터 Fusion, FlowSpec 투영, FlowSequence 검증까지 관계를 보존한다.

### 16.60 직접 await된 async 호출의 throw 복구

`try { await charge(); } catch { recover(); }`에서 `charge`가 async 함수이고 그 함수 안에 처리되지 않은 명시적 `throw`가 있을 때, throw에서 호출자 `recover()`로 실패 관계를 보존한다. 이는 throw가 async 함수가 반환한 Promise의 거절이 되고, 같은 직접 호출을 await한 try/catch가 그 거절을 받는 경우에만 성립한다.

호출자에서 await 없이 호출한 async 함수, 중첩·간접 호출, generator, callee 내부 catch 또는 finally로 이미 처리된 throw는 이 규칙의 대상이 아니다. 해당 경우에는 실패 관계를 추정하지 않는다. 캐시 의미 버전을 `v33-awaited-called-throw-recovery`로 올려 이전 slice 결과를 재사용하지 않는다.

`slice_control_connections.test.js`는 직접 await된 async throw의 호출자 catch 연결, await 없는 async 호출의 미연결, callee 내부 복구의 미전파를 대조한다. `TestAwaitedAsyncThrowPreservesCallerRecovery`는 adapter부터 Fusion, FlowSpec, FlowSequence까지 throw와 recover 관계가 유지되는지를 확인한다. 실제 저장 FlowView 브라우저 과제는 `charge()`의 throw 단계를 선택했을 때 `recover()`가 직접 후속 관계로 표시되는지를 확인한다.

### 16.61 중첩 조건의 선택·변경·해제

`if (first) { if (second) ... }`의 실제 분석을 FlowView에서 열어 상위 조건의 참을 고른 뒤 하위 조건의 참을 추가했다. 개요 카드의 경로 강조와 선택한 조건 목록이 함께 갱신되는지 확인했다. 이후 상위 조건을 거짓으로 바꾸면 도달할 수 없는 하위 조건이 목록에서 제거되고, 전체 조건 해제로 강조와 목록이 모두 사라지는지를 브라우저에서 대조했다.

이 검사는 확인된 조건 관계의 도달 범위를 표시한다. 선택한 조건 조합이 실제로 실행 가능하다는 뜻이 아니며, 반복·미확인 연결·복합 조건식의 모든 조합을 완료한 것으로 집계하지 않는다.

### 16.62 finalizer의 단일 반환이 호출자에 복귀하는 관계

동기 함수의 첫 처리인 `try`에 `finally { return replacement(); }`가 있고 finalizer가 단 하나의 return으로 끝나는 경우, finalizer return만 호출자의 기존 대입 또는 다음 처리로 `return` 관계를 만든다. try 안의 `return original();`은 finalizer 실행으로 대체되므로 호출자에 직접 복귀하지 않는다. 기존 return→finally→finalizer return 실행 연결도 유지한다.

조건부·복수 return, async·generator, try 앞의 다른 처리, 중첩 try는 이 규칙에 넣지 않는다. 이 경우에는 최종 결과를 추정하지 않는다. slice cache identity를 `v34-prevailing-finally-return`으로 올렸다.

`slice_normal_return.test.js`와 `TestFinallyReturnResumesCallerWithOnlyTheFinalResult`은 최종 return 하나만 호출자 대입으로 향하고 앞선 try return은 향하지 않는지를 검사한다. 실제 저장 FlowView에서도 finalizer return을 선택하면 `result = finish()`가 직접 후속 관계로 표시되는지를 확인한다.

### 16.63 대규모 관계 복귀의 패널 읽기 위치

150단계 초과 실제 분석에서 개요와 실행 탐색을 각각 스크롤한 뒤 확인된 후속 관계로 이동하고 `원래 장면 복귀`를 실행하는 브라우저 과제를 추가했다. 복귀 후 출발 관문 선택과 두 패널의 scrollTop이 이동 전 값으로 돌아오는지를 확인한다. 관계 탐색이 읽던 장면의 목록 위치를 잃지 않도록 `SavedNavigationState.panelPositions` 복원 경로를 실제 DOM에서 검증한다.

코드 패널과 비교 화면이 함께 열린 상태의 복합 복귀, 브라우저 뒤로가기에서 모든 패널 위치를 조합한 과제는 별도 범위다.

### 16.64 finalizer의 단일 throw가 호출자 복구로 이어지는 관계

동기 직접 호출 함수의 `finally`가 단 하나의 직접 `throw`로 끝나고, 호출자가 그 호출을 `try/catch`로 감쌌을 때 finalizer의 throw에서 호출자 catch 첫 단계로 `failure` 관계를 만든다. finalizer의 throw는 앞선 try·catch의 정상 완료 또는 종료를 대체하므로, 해당 try에 “finally 이후 진행을 확인하지 못했다”는 미확정 연결을 남기지 않는다.

조건부·복수 finalizer 문장, async·generator, await·간접 호출, callee 내부에서 이미 처리된 throw는 이 규칙에 넣지 않는다. 최종 예외 값이나 실제 런타임의 예외 종류는 소스만으로 추정하지 않는다. slice cache identity를 `v35-finalizer-throw-recovery`로 올렸다.

`slice_control_connections.test.js`와 `TestFinalizerThrowPreservesCallerRecovery`는 adapter부터 Fusion, FlowSpec, FlowSequence까지 `throw failure; → recover()` 관계를 대조한다. 실제 저장 FlowView 브라우저 과제는 finalizer throw 단계를 선택했을 때 `recover()`가 직접 후속 관계로 표시되는지를 확인한다.

### 16.65 같은 호출 문맥의 연속 내부 단계 타임라인

실제 TypeScript 분석 단계는 같은 함수 실행에도 `invocationId`를 가진다. 기존 관문 병합기는 이 값이 있으면 모두 분리했으므로, 역할상 중요하지 않은 연속 내부 호출도 각각 1단계 관문이 될 수 있었다. 이제 같은 `invocationId`, 파일·심볼·계층, 조건 없는 단일 확인 `control_flow`를 가진 연속 내부 단계는 현재 관문의 실행 타임라인으로 포함한다.

호출 문맥이 다르거나, 분석 경계의 앞뒤이거나, 조건·상태 변화·외부 효과·return·throw를 포함하면 병합하지 않는다. 호출 결과를 대입하는 경우에는 별도 값 전달 묶음이 정확한 세 단계를 보존해야 하므로 호출 출발 단계도 일반 병합에서 제외한다. 현재 단계에서 확인된 다른 구현으로 `resolved_cross_file`·`external`·`async` 연결이 나가면, 같은 호출 문맥이어도 그 호출은 요청 흐름의 전환이므로 독립 관문으로 유지한다.

`HomePage.onQuickCheckout` 실제 분석에서는 `orderPayload = ...`와 `api.orders.checkout(orderPayload)`가 별도 관문으로 나타나야 한다. 앞 단계는 요청값을 준비하고, 뒤 단계는 확인된 주문 구현으로 진입한다. 이 규칙은 호출 이름이나 외부 효과 추정이 아니라 분석 그래프의 확인된 연결만 사용한다.

`TestFlowSequenceFoldsContinuousStepsInOneInvocation`은 하나의 호출 문맥에서 시작·내부 호출 둘을 3단계 타임라인으로 묶는지 검사한다. `TestFlowSequenceDoesNotFoldSeparateInvocations`, `TestReturnExpressionPreservesIndependentBoundaries`, `TestLargeSourceHierarchySurvivesStorageHTTPAndMCP`는 호출 문맥, 미확인 경계와 호출·반환·대입 관계가 섞이지 않는 반례를 대조한다.

### 16.66 async iterator의 다음 항목 대기와 반복 관계

단순 `for await (const item of items) { 처리 }`는 각 항목을 받기 전에 대기한다. 이제 헤더를 `await` 단계와 뒤이은 분기 단계로 나눈다. 대기 성공 뒤에는 분기 단계가 본문 진입 또는 반복 종료를 결정하고, 본문 완료는 다음 항목 대기 단계로 `loop_back`한다. 본문 안에 별도의 `await`가 있으면 그 대기에서 다음 항목 대기로 향하는 관계는 `await_loop_back`으로 유지한다.

반복자 값의 출처, `next()` 거절, 조기 종료 시 iterator 정리와 catch 복구는 이 규칙으로 추정하지 않는다. 헤더 대기에는 이 한계를 계속 남긴다. 본문 안의 직접 `await`가 거절되어 같은 본문의 `catch`로 가는 경우는 기존 await 실패 관계로 표시하되, 이를 iterator 자체의 거절 복구로 표현하지 않는다. 따라서 화면은 반복이 확인된다는 사실과 반복자의 실패·정리 의미가 아직 확인되지 않았다는 사실을 함께 표시한다. 동적 iterator, 중첩 반복, label, switch, finally가 있는 반복은 기존 미확인 경계를 유지한다.

`slice_control_connections.test.js`는 항목 대기→분기, 참일 때 본문 진입, 거짓일 때 종료, 본문→다음 항목 대기와 본문 await의 catch 복구를 확인한다. `TestAsyncIterableLoopRelationsSurviveProjection`과 `TestRecoveredAsyncIterableLoopRelationsSurviveProjection`은 adapter→Fusion→FlowSpec→FlowSequence까지 같은 관계와 미확인 사유를 대조한다. FlowView 브라우저 과제는 실제 API·저장 뷰에서 대기·분기·본문·종료·다음 반복 연결을 열고, 본문의 전후 관계에서 두 `for await` 단계를 확인한다.

분석 의미가 달라져 slice cache identity를 `v38-async-iterable-relations`로 올렸다. 저장된 FlowView는 재작성하지 않는다.

### 16.67 finally 정리 뒤의 비동기 재시도

`while (!done) { try { await retry(); } finally { cleanup(); } }`에서 대기 성공은 `cleanup()`으로 재개하고, 정리가 끝난 뒤에만 while 조건으로 `loop_back`한다. 조건 거짓은 반복 뒤 처리로 향한다. 따라서 정리를 건너뛴 재시도나 await 성공이 곧바로 다음 반복으로 가는 관계를 만들지 않는다.

이 규칙은 try 본문이 하나의 직접 await이고 finally가 하나 이상의 직접 호출만 포함하는 좁은 형태다. catch가 있으면 하나 이상의 직접 복구 호출만 포함해야 하며, 대기 실패는 catch를 거쳐 finally로 진행한다. catch가 없을 때 await 거절은 반복 성공이나 종료로 추정하지 않으며, 기존 대기 실패 미확인 사유를 유지한다. 거절 시 finally가 실행된다는 언어 규칙을 전체 예외 복구 관계로 확대하지 않는다. 조건·반복·종료가 포함된 finally, 복수 try 경로, dynamic await는 기존 미확인 범위다.

`slice_control_connections.test.js`, `TestFinalizingAwaitRetryLoopSurvivesProjection`, `TestRecoveredFinalizingAwaitRetryLoopSurvivesProjection`은 성공 대기→정리→조건 재평가, 실패 대기→복구→정리→조건 재평가, 조건 거짓의 종료, 처리되지 않은 거절의 미확인 보존을 adapter→Fusion→FlowSpec→FlowSequence까지 대조한다. 분석 의미가 달라져 slice cache identity를 `v40-recovered-finalizing-await-retry`로 올렸다. 저장된 FlowView는 재작성하지 않는다.

### 16.68 자동 구현 검증 완료와 사용자 관문 검증 상태

2026-09-21에 전체 Go 검사(`make fmt`, `make vet`, `make check-naming`, `make test-all`, `make test-ui`, `make build`), TypeScript adapter 검사, Svelte 검사·단위 검사, `git diff --check`를 통과했다. 실제 API·분석·저장 FlowView를 여는 Playwright 과제는 `make test-flowview`로 실행하며, 31개가 모두 통과했다. 이 과제에는 관문과 타임라인의 1:N 탐색, 조건·분기·합류, await·반환·재시도·반복 관계, 다른 파일 코드 근거, 좁은 비교 화면, 키보드 탐색, 실패·취소 보존, 관계 복귀와 비교 상태 복원이 포함된다. 같은 실제 화면의 초기 화면·코드 보기·처리 보기에 WCAG 2A·2AA Axe 검사를 추가해 심각도 critical·serious 위반이 없음을 확인했다.

남은 검증은 구현 결함을 찾기 위한 추가 자동 검사가 아니라 §16.59의 실제 개발자 과제다. 사용자는 같은 Requested Flow에서 각 관문을 직접 따라가며 조건 경로, 공통 처리, 다른 파일 코드 근거, 비교 전후 코드, 미확인 연결을 확인한다. 과제별 정답, 근거 코드 도달, 복귀 성공, 관찰된 오해만 기록한다. 이 결과가 있으면 AC-14와 UX-AC-15·17의 사용자 검증 상태를 확정할 수 있다.

### 16.69 실제 요청 핸들러의 1:N 관문 보정

실제 `HomePage.onQuickCheckout`을 화면으로 열어 보니 12개 실행 단계가 11개 관문으로 나뉘어, 실행 타임라인이 아닌 카드 나열로 읽혔다. 원인은 `BuildFlowSequence`가 같은 요청 핸들러에서 호출한 helper의 반환과 `await` 재개를 모두 독립 관문으로 남긴 데 있었다.

이제 같은 핸들러에서 확인된 준비 구간, 직접 await한 호출 구간, 조건 판단과 그 직접 조건 결과를 각각 하나의 관문으로 묶는다. 다른 구현의 단계는 확인된 `resolved_cross_file` 연결로 도달한 경우에만 자식으로 넣는다. external effect, 실패, 독립 판단, 확인되지 않은 다른 호출 문맥은 묶지 않는다. boundary 자식은 제거하거나 verified로 바꾸지 않고 부모 상태를 `unknown`으로 낮춘다.

실제 요청 결과는 `orderPayload 준비` 6단계, `api.orders.checkout(orderPayload)` 4단계, `if (response.success)` 2단계가 됐다. Playwright 과제는 API 결과의 세 관문·자식 수와 실행 탐색에서 첫 관문의 6단계 타임라인을 함께 확인한다. `TestBuildFlowSequenceGroupsCoreFlowHandlerSegments`은 동일 규칙을 semantic 단위에서 검증한다.

### 16.71 긴 비교 코드의 패널 경계와 내부 읽기

실제 `setStatus` 호출의 인자를 긴 문자열로 바꾼 현재 분석과 이전 저장 분석을 비교했다. 390px 너비와 200% 확대에 해당하는 195px CSS 너비에서 대상 실행 단계를 선택한 뒤, 문서 전체는 가로로 넘치지 않고 이전·현재 코드 패널은 각각 뷰포트 안에 남는다. 긴 현재 코드 행은 패널 내부의 가로 스크롤로 끝까지 이동할 수 있다. 좁은 폭에서는 상단 흐름 제목과 관문 개요를 줄바꿈해 고정 최소 폭이 화면을 넓히지 않게 한다.

`saved-flowview.spec.ts`의 `long comparison source stays contained and remains horizontally readable` 과제는 이 경로를 실제 분석·저장·비교 데이터로 검증한다. `make test-flowview`는 31개 과제를 통과했다. 브라우저 확대와 보조기술 전체 조합은 §16.59의 실제 사용자 과제와 별도로 평가한다.


### 16.72 초기 화면의 확대 읽기

홈 화면도 200% 확대에 해당하는 195px CSS 너비에서 문서 전체 가로 넘침 없이 표시된다. 시작 입력과 `흐름 보기` 버튼은 화면 안에 남는다. `home entry remains readable at a 200 percent zoom equivalent width` Playwright 과제가 이 조건을 실제 제품 서버에서 확인한다.
