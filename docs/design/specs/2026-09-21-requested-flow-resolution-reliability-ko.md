- Related Contract: [Requested Flow 중심 FlowSequence 관문과 실행 타임라인 상세 명세](2026-09-18-flowsequence-requested-flow-hierarchy-ko.md). 이 계약은 관문을 만들기 전 요청 흐름을 확정하고 분석 실패를 전달하는 선행 계약이다. 관련 계약의 `architecture` 표현은 이 계약의 INV-08과 FA-08을 우선 적용한다.

## 1. 문제와 목표

사용자는 자연어로 이해하려는 기능 흐름을 요청한다. 현재 CodeFlow는 대화 에이전트가 선택한 진입 심볼을 신뢰하고, `open_review` 재분석에서 자연어 요청을 심볼 경로로 바꾼다. 잘못 선택한 대상과 메서드를 찾지 못한 분석도 정상 FlowView처럼 저장될 수 있다.

- INT-01: 사용자가 말한 흐름을 실제 코드의 하나의 Requested Flow로 근거 있게 확정한다.
- GOAL-01: 사용자는 FlowView에서 원래 요청, 선택된 진입점, 선택 근거와 분석 한계를 함께 확인한다.
- GOAL-02: 사용자는 분석기가 진입 메서드를 찾지 못했을 때 가짜 단일 흐름 대신 명확한 실패를 받는다.
- GOAL-03: 사용자는 확정된 Requested Flow에서 중요한 함수·클래스와 결정 코드로 짧은 읽기 경로를 따라가며 요청한 구현을 이해한다.

## 2. 범위

포함:

- 자연어 요청, 선택 후보, 진입 심볼, 선택 근거의 보존과 재사용
- 후보가 모호하거나 근거가 없을 때의 중단 동작
- Dart primary constructor가 있는 클래스의 메서드 탐색과 빈 결과 실패 처리
- 확인된 호출 문맥과 로컬 실행 관계를 FlowSequence에 전달하는 Dart 분석 계약
- FlowView의 요청-선택-분석 상태, 코드 읽기 경로와 실제 Molycard 검증

제외:

- 런타임 실행 관측, 원격 코드 전송, 전역 호출 그래프 제품화
- TypeScript·Go adapter의 실행 관계 확장. 동일 문제는 별도 계약으로 다룬다.
- 새 화면, 고정 레이아웃, 전역 호출 그래프 또는 프로젝트별 아키텍처 분류의 도입

## 3. 확인된 사실

- `harvest_flows`는 후보 필드의 문자열 포함으로 요청어를 필터링한다. 한국어 요청과 영문 코드 식별자의 의미 관계를 스스로 확정하지 못한다.
- `analyze_flow`는 `entrySymbolPath`를 요구하며 원문 요청을 받거나 보존하지 않는다.
- `open_review`는 FlowSpec에서 진입 심볼을 읽은 뒤 새 Task View 요청에 심볼과 FlowID만 전달한다.
- Molycard의 `BattleController._onEndTurn`은 유효한 Dart 코드지만, primary constructor 형태 때문에 현재 scanner가 메서드를 찾지 못했다. 결과가 비면 adapter는 전체 파일을 가리키는 단일 단계를 만들었다.
- FlowSequence의 1:N 병합에는 같은 호출 문맥과 확인된 `sequence` 또는 `control_flow` 관계가 필요하다. 현재 Dart slice는 이를 충분히 제공하지 않는다.

## 4. 불변식

- INV-01: 원문 요청은 분석 시작부터 저장 View, HTTP, MCP, 재분석까지 변하지 않는다. 심볼 경로는 원문 요청의 대체값이 아니다.
- INV-02: 선택된 Requested Flow에는 진입 심볼과 snapshot 안의 실제 코드 근거가 있어야 한다. 근거 없는 기본 후보 선택은 허용하지 않는다.
- INV-03: 후보가 여러 사용자 의도를 가리키거나 근거가 부족하면 새 분석·저장·화면 교체를 하지 않는다.
- INV-04: 진입 메서드를 찾지 못했거나 실행 가능한 메서드 본문이 분석 결과를 만들지 못하면 전체 파일 단계나 임의 entry/result를 만들지 않는다.
- INV-05: 확인되지 않은 실행 관계를 `sequence`, `control_flow`, 호출 문맥 또는 FlowSequence 병합 근거로 만들지 않는다.
- INV-06: 기존 source read-only, 인증, secret redaction, immutable View ID와 과거 View 복원 규칙을 유지한다.
- INV-07: 코드 읽기 경로의 각 항목은 요청을 설명하는 이유, 실제 심볼·소스 위치, 확인된 이전 또는 다음 관계를 가진다. 근거 없는 의미 제목이나 관계는 만들지 않는다.
- INV-08: `architecture`와 architecture label은 폐기된 개념이다. 새 분석·저장 View·MCP·FlowView는 이를 생성·저장·전달·표시하지 않으며, 코드 읽기 경로의 선정·정렬·병합에도 사용하지 않는다.

## 5. 요청 흐름 확정 동작

1. 대화 에이전트는 원문 요청으로 후보를 찾고 CodeGraph 또는 동등한 소스 탐색으로 관련 코드 근거를 확인한다.
2. 에이전트는 원문 요청, 선택한 후보, 진입 심볼, FlowID와 근거를 하나의 요청 흐름 확정 기록으로 `analyze_flow`에 전달한다.
3. CodeFlow는 선택 근거의 심볼·경로가 같은 snapshot에 존재하고 선택 대상과 연결되는지 검증한다.
4. 후보가 서로 다른 사용자 의도를 가리키면 후보와 근거를 반환하고 분석하지 않는다. 하나의 후보가 코드 근거로 수렴하면 사용자 재질문 없이 진행한다.
5. `open_review`와 명시적 재분석은 확정 기록의 원문 요청과 선택 대상을 그대로 사용한다.
6. FlowView는 원문 요청, 선택된 진입점, 선택 상태, 분석 한계를 표시한다. 선택이 확정되지 않았거나 분석이 실패하면 실행 타임라인을 표시하지 않는다.

## 6. 데이터와 공개 경계

새 분석과 저장 View에는 표준 필드 `flowResolution`을 정의하고 사용한다.

| 필드 | 의미 |
|---|---|
| `rawRequest` | 사용자가 말한 원문 요청 |
| `status` | `resolved`, `ambiguous`, `unresolved`, `analysis_failed` 중 하나 |
| `entrySymbolPath`, `flowId` | `resolved`일 때의 선택 대상 |
| `evidence` | snapshot 안의 경로·심볼과 선택 이유 |
| `candidates` | `ambiguous`일 때 사용자가 구분할 수 있는 후보와 근거 |
| `failure` | `analysis_failed`일 때의 원인과 재시도 방법 |

확정 기록은 FlowSpec과 Task View에 모두 저장한다. 기록의 `schemaVersion`, `candidateId`, `entrySymbolPath`, 재계산한 `flowId`, `snapshotId`, `computedBasisId`와 후보 설명은 같은 snapshot의 후보와 대조한다. 자연어 요청은 실행 중 선택에만 쓰며 저장·HTTP·MCP·화면에는 secret redaction을 거친 요청만 제공한다. 심볼로 시작한 직접 분석은 심볼 문자열 자체를 요청으로 기록할 수 있다. 기존 저장 View에 이 필드가 없으면 조회 결과는 그대로 복원하고, 새 분석으로 바꾸거나 성공으로 추정하지 않는다.

## 7. 실패와 경계

| 조건 | 관찰 결과 | 부작용 |
|---|---|---|
| 후보가 없음 | `unresolved`과 검색 범위 안내 | slice·저장 없음 |
| 서로 다른 의미의 후보가 남음 | `ambiguous`와 후보·근거 | slice·저장 없음 |
| 선택 근거가 snapshot과 맞지 않음 | 요청 흐름 확정 오류 | 기존 View 유지 |
| 진입 메서드를 찾지 못함 | `analysis_failed` | 전체 파일 fallback·새 View 없음 |
| 직접 실행 연결을 확인하지 못함 | 해당 연결을 미확인으로 보존 | 실행 순서·관문 병합 추정 없음 |

## 9. 수용 기준

- FA-01: 자연어 요청으로 분석한 결과는 원문 요청, 선택 심볼, FlowID, 소스 근거를 저장·HTTP·MCP·FlowView에서 같은 값으로 제공한다.
- FA-02: 여러 후보가 서로 다른 사용자 의도를 가리키면 시스템은 후보 근거를 반환하고 임의 FlowSpec이나 Task View를 만들지 않는다.
- FA-03: primary constructor가 있는 Dart 클래스의 대상 메서드는 실제 본문 범위에서 단계와 소스 근거를 만든다.
- FA-04: 대상 메서드를 찾지 못한 slice는 명시적 실패를 반환하며 전체 파일을 가리키는 단일 단계, 가짜 result, 새 저장 View를 만들지 않는다.
- FA-05: Dart가 확인한 같은 호출 내부의 로컬 후속 처리만 호출 문맥과 직접 실행 관계로 전달한다.
- FA-06: Molycard의 세균전 요청은 선택 근거와 실제 코드 문맥을 가진 FlowView로 열리고, 근거 없는 Battle 흐름으로 대체되지 않는다.
- FA-07: 확정된 View의 각 기본 탐색 항목은 실제 함수·클래스명, 이 항목이 요청을 설명하는 이유, 확인된 직접 관계를 제공하며 선택하면 관련 코드 범위를 연다.
- FA-08: 새 분석·저장 View·MCP·FlowView에는 `architecture` 필드나 label이 없으며, 폴더명·호출 횟수만으로 항목을 선정하거나 순서를 정하지 않는다.
- FA-09: CodeView를 대체하는 코드 본문 복사본은 탐색 항목에 넣지 않는다. 탐색 항목은 제목·심볼·관계·포함 이유를 제공하고 실제 소스는 CodeView에서 읽는다.

## 10. 품질과 검증

각 슬라이스는 변경한 Go·Dart·Svelte 경로의 행동 테스트를 먼저 실행한다. 전체 완료 전 `make fmt`, `make vet`, `make check-naming`, `make test`, `make test-flowview`, `make test-ui`, `cd adapters/dart && dart test`, `make build`를 실행한다. 저장·MCP 경계 변경은 호환성 왕복 테스트와 race 검사를 포함한다. 실제 Molycard View는 자연어 요청으로 생성하고, 요청·선택 근거·관문·코드 문맥을 화면에서 확인한다.

## 11. 완료 조건

- FA-01부터 FA-19까지 현재 실행 증거가 있다.
- 잘못된 후보 선택과 메서드 미발견이 정상 흐름으로 저장되지 않는다.
- 기존 FlowSequence 계약과 과거 저장 View를 임의로 변경하지 않는다.
- 네 슬라이스의 독립 검토가 통과하고 사용자가 슬라이스별 구현을 승인한다.

## 12. 요청한 구현을 코드로 읽는 경로

### 12.1 제품 모델

CodeFlow의 기본 산출물은 완전한 호출 그래프가 아니라 **코드 읽기 경로**다. 코드 읽기 경로는 사용자의 요청을 설명하는 데 필요한 실제 코드 지점을, 읽는 순서와 근거 관계로 정리한 결과다. FlowSequence는 이 경로의 상위 색인이고, 실행 관계 그래프는 항목을 포함하거나 다음 항목으로 이동시키는 근거다.

그래프의 모든 정점·간선을 화면에 먼저 펼치지 않는다. 반대로 그래프가 불완전하다는 이유로 근거 있는 코드 지점까지 숨기지 않는다. 직접 관계를 확인하지 못한 곳은 마지막으로 확인한 코드와 분석 경계를 남긴다.

### 12.2 입력과 확정 순서

1. 대화 에이전트는 원문 요청을 시작 상황, 알고 싶은 처리, 확인하려는 결과로 정리한다. 사용자가 말하지 않은 결과나 조건을 보충하지 않는다.
2. `harvest_flows`, CodeGraph 또는 동등한 현재 소스 탐색으로 실제 후보·진입 심볼·관련 구현을 찾는다.
3. VS-01의 요청 흐름 확정 기록으로 하나의 Requested Flow를 선택한다. 후보가 수렴하지 않으면 읽기 경로를 만들지 않는다.
4. analyzer는 선택된 진입점에서 실제 실행 단계와 직접 관계를 수집한다. VS-02의 진입점 실패는 정상 경로로 대체하지 않는다.
5. curator는 확인된 단계 중 요청을 이해하는 데 필요한 코드 지점만 코드 읽기 경로에 올린다. presenter와 UI는 그 결과를 다시 선정하거나 관계를 추정하지 않는다.

### 12.3 코드 지점 선정 기준

선정 질문은 하나다. **이 코드를 빼면 사용자가 요청한 구현의 결과, 결정 또는 다음 처리를 잘못 이해하는가?** 다음 기준은 고정 점수나 프로젝트 구조 순서가 아니라, 질문에 답하기 위한 확인 목록이다.

| 포함 이유 | 선정할 코드 지점 | 제외 가능한 예 |
|---|---|---|
| `entry` | 요청을 실제로 시작하는 이벤트, route, command, callback | 같은 화면의 무관한 lifecycle callback |
| `decision` | 결과·경로·권한·실패를 바꾸는 검증과 분기 | 결과를 바꾸지 않는 방어적 null 검사 |
| `transform` | 요청 입력을 다음 처리의 의미 있는 값·명령으로 바꾸는 코드 | 단순 포맷 변환이나 logging |
| `state_change` | 사용자 요청의 결과를 바꾸는 상태·영속 데이터 변경 | 요청 결과와 무관한 지역 변수 대입 |
| `effect` | 외부 시스템, 비동기 작업, transaction, 메시지로 넘기는 코드 | 근거 없는 이름 유사 호출 |
| `handoff` | 다음 중요한 함수·클래스로 직접 넘어가는 호출 지점 | 호출 대상·구현을 확인하지 못한 추정 연결 |
| `outcome` | 성공, 실패, 취소, 결과 반영 또는 분석 경계 | 단순 return 자체만으로 만든 가상 결과 |

하나의 지점은 둘 이상의 이유를 가질 수 있다. 반대로 표에 있는 코드라도 요청을 설명하지 않으면 기본 경로에서 제외한다. 제외한 확인된 단계는 관문 아래의 필요 시 열어 보는 세부 정보로 남길 수 있으나, 삭제하거나 실행되지 않은 코드라고 표현하지 않는다.

### 12.4 경로와 실행 관계의 표현

코드 읽기 경로의 항목은 다음 정보를 가져야 한다.

| 정보 | 규칙 |
|---|---|
| `nodeId` | 같은 분석 안에서 안정적인 식별자 |
| `frameId` | 소속 FlowSequence 관문. 모든 노드는 하나의 관문에만 소속 |
| `symbol`과 `sourceAnchor` | 실제 함수·클래스와 같은 snapshot의 코드 범위 |
| `inclusionReason` | §12.3의 포함 이유와 요청 문장 중 설명하는 부분 |
| `previous`·`next` | 확인된 `direct_call`, `control_flow`, `async_handoff`, `conditional`, `boundary` 관계만 사용 |
| `status` | `verified`, `partial`, `unknown` 중 하나. 관계의 상태를 항목의 코드 근거 상태로 승격하지 않음 |

### 12.4.1 요청-코드 근거 연쇄

사용자 요청을 설명하는 문장과 실제 CodeView 사이에는 다음 연쇄가 끊기지 않아야 한다.

`redacted request` → `선택 이유` → `실제 심볼` → `정확한 sourceAnchor와 코드 범위` → `확인된 관계` → `CodeView 표시`

각 코드 읽기 경로 항목은 최소한 아래 근거를 보존한다.

| 근거 | 요구 사항 |
|---|---|
| 요청 연결 | 원문 요청의 어떤 처리·결과·조건을 설명하는지. 요청에서 직접 확인되지 않은 의미는 추정으로 표시 |
| 선택 이유 | 후보를 선택한 소스 근거와, 같은 이름의 다른 후보를 제외한 이유 |
| 심볼 근거 | snapshot 안에 존재하는 함수·클래스·route 등 실제 심볼 경로 |
| 문장 근거 | 심볼 전체가 아니라 요청을 설명하는 정확한 문장·표현식 범위와 해당 범위의 span hash |
| 관계 근거 | 직전·다음 코드 지점과 연결하는 AST·CodeGraph·adapter 증거, 관계 종류와 상태 |
| 화면 근거 | CodeView가 같은 snapshot에서 심볼과 문장 범위를 실제로 열 수 있다는 확인 결과 |

자연어 의미 해석, 심볼 이름 유사성, 파일 경로 유사성, 모델이 만든 요약은 단독 근거가 될 수 없다. 대화 에이전트는 요청과 코드의 의미 연결을 제안할 수 있지만, CodeFlow는 그 제안이 가리키는 심볼·문장·관계를 현재 snapshot에서 검증한다. 검증된 코드는 사실로, 요청과 코드 사이의 해석은 선택 이유로 분리해 표시한다.

### 12.4.2 CodeView 표시 전 검증과 실패 처리

TaskView를 저장하기 전 presenter는 경로의 기본 항목마다 다음을 검증한다.

1. `sourceAnchor`의 파일 hash, byte range, enclosing symbol이 선택된 snapshot의 코드와 일치한다.
2. 강조 범위가 실제 실행 문장 또는 분기·호출·상태 변경·결과 표현식에 속한다. 메서드를 찾지 못했을 때 파일 전체를 대신 가리키는 범위는 허용하지 않는다.
3. CodeView source context가 같은 snapshot에서 읽히고, 선택한 심볼과 강조 범위를 포함한다.
4. 이전·다음 관계가 있으면 관계의 양 끝이 표시 가능한 실제 코드 범위를 가진다.

진입점 또는 관문의 대표 코드가 이 검증을 통과하지 못하면 `analysis_failed`로 반환하고 새 TaskView를 저장하지 않는다. 비대표 하위 단계의 코드 범위가 없으면 마지막으로 검증된 항목에서 `boundary`를 만들고, 누락한 코드·관계·원인을 명시한다. 다른 파일, 같은 이름의 심볼, 파일 전체 fallback으로 대체하지 않는다.

### 12.4.3 사용자에게 보이는 설명 고리

각 기본 탐색 항목은 사용자가 요청과 코드를 연결해 판단할 수 있도록 다음을 제공한다.

- `이 항목을 보는 이유`: 요청의 어느 처리·결과·조건을 설명하는지
- `코드 위치`: 함수 또는 클래스명과 실제 파일·줄 범위
- `이전/다음`: 확인된 관계와 조건 또는 분석 경계
- `근거 한계`: 요청 의미의 해석인지, 코드·관계가 partial 또는 unknown인지

이 정보는 코드 본문을 복제하는 설명문이 아니다. 사용자가 항목을 선택하면 CodeView에서 해당 문장과 필요한 주변 문맥을 읽어 스스로 확인할 수 있어야 한다. 화면은 설명 문구가 있어도 실제 코드 범위를 열지 못하면 성공으로 표시하지 않는다.

`await` 뒤의 코드는 호출이 정상 복귀한 경우에만 실행될 수 있다. 따라서 `await`와 다음 단계 사이에는 성공 복귀 또는 예외 처리를 근거로 확인한 관계만 표시한다. 확인하지 못하면 비동기 인계 또는 분석 경계로 표시하며, 단순 소스 줄 순서로 확정 실행선을 만들지 않는다.

관문과 실행 타임라인의 1:N 관계는 유지한다. 관문은 사용자가 멈춰 읽어야 하는 중요한 코드 결정·전환의 묶음이고, 자식 타임라인은 그 결정을 실제로 수행하는 코드 지점이다. 관문과 자식의 소속은 요약을 위한 것이며, 인접한 자식이 모든 조건에서 연속 실행된다는 뜻은 아니다.

### 12.5 FlowSequence와 그래프의 책임

- FlowSequence는 전체 읽기 순서, 관문별 코드 지점의 소속, 조건·합류·분석 경계를 제공한다.
- 실행 관계 그래프는 직접 호출, 확인된 제어 흐름, 비동기 인계, 미확인 경계의 근거를 제공한다.
- CodeView는 선택한 항목의 실제 함수 또는 클래스와 관련 줄, 필요한 주변 문맥을 제공한다.
- 어느 표현도 함수명 유사성, 파일 인접성, 폴더 구조만으로 새 관계나 처리 목적을 만들지 않는다.

### 12.6 UI·UX 적용 범위

새 레이아웃, 색상 체계, 패널, 전역 그래프 화면은 필수 사항이 아니다. 기존 흑백 테마, FlowSequence, 좌측 실행 탐색, 중앙 CodeView, 우측 직접 관계 탐색의 구조는 유지할 수 있다.

다만 현재 화면이 아래 정보를 제공하지 못하면 **내용과 상호작용은 수정해야 한다**. 시각적 배치는 유지해도 제품 행동은 바뀐다.

| 영역 | 필수 동작 |
|---|---|
| 요청 영역 | 원문 요청, 확정된 진입점, 선택 근거, 분석 한계를 표시 |
| FlowSequence | 관문 제목·조건·관계·한계를 표시 |
| 좌측 실행 탐색 | 코드 본문을 중복하지 않고 제목, 함수·클래스명, 포함 이유, 이전·다음 확인 관계를 표시 |
| 중앙 CodeView | 항목 선택 시 실제 소스의 포함 심볼과 관련 문장을 열고 주변 문맥을 보존 |
| 우측 직접 관계 | 현재 Requested Flow의 이전·다음 실행 관계와 요청 범위 밖의 caller/callee를 구분해 탐색 |

따라서 UI·UX의 대규모 시각 재설계는 필요하지 않다. 그러나 좌측에 코드 상세를 반복 표시하거나, 선택 항목이 CodeView의 정확한 심볼·문장을 열지 못하면 이를 고쳐야 한다.

### 12.7 저장·호환성과 실패

코드 읽기 경로는 `flowResolution`, semantic map, FlowSequence와 같은 snapshot·computed basis에 묶여야 한다. 새 공개 필드가 필요하면 schema, producer, consumer, 저장 복원과 MCP compact payload를 함께 변경한다. `architecture`를 담는 기존 데이터와 공개 계약은 호환 reader를 둔 이행 기간 없이 제거하지 않는다. 제거 전에는 저장 데이터, JSON schema, Go·Svelte 타입, MCP payload, FlowView UI와 fixture의 모든 producer·consumer를 목록화하고, reader와 writer를 같은 변경에서 제거하거나 명시적 migration으로 처리한다.

`ambiguous`, `unresolved`, `analysis_failed` 상태에서는 코드 읽기 경로나 정상 실행 타임라인을 렌더링하지 않는다. 분석 실패는 HTTP 500 일반 오류로 숨기지 않고, 대상 심볼·실패 이유·재시도 단서를 가진 구조화된 분석 실패로 반환하며 새 TaskView를 저장하지 않는다.

### 12.8 추가 수용 기준과 검증

- FA-10: 서로 다른 구조의 fixture에서 같은 요청 이해 기준으로 entry, 결정, 상태·외부 효과, 인계, 결과 또는 경계를 선정하며 `architecture` 값·필드·label 없이 경로를 만든다.
- FA-11: 선택한 코드 지점마다 FlowView에서 실제 심볼·관련 코드와 포함 이유를 확인할 수 있다.
- FA-12: `await` 실패 또는 취소 가능성이 있는 fixture에서 후속 코드를 확정 실행으로 표시하지 않는다.
- FA-13: FlowSequence 관문, 좌측 탐색, CodeView, MCP compact payload는 같은 항목·심볼·관계·근거 상태를 가리킨다.
- FA-14: 기존 흑백 테마와 현재 화면 구조를 유지한 상태에서도 좌측 항목에서 코드 본문 중복 없이 실제 CodeView까지 이동할 수 있다.
- FA-15: 기본 코드 읽기 경로 항목마다 요청 연결, 선택 이유, 실제 심볼·문장 범위, 관계 근거, CodeView 표시 가능 여부를 같은 snapshot 근거로 검증한다.
- FA-16: 메서드 미발견, 파일 전체 fallback, 다른 동명 심볼, 읽을 수 없는 source context는 요청 코드의 근거로 사용하지 않는다.
- FA-17: 대표 코드 범위를 열 수 없는 분석은 구조화된 `analysis_failed`가 되고 TaskView를 저장하지 않는다. 비대표 단계의 누락은 마지막 검증 지점의 `boundary`와 한계로 표시한다.
- FA-18: FlowView에서 기본 항목을 선택하면 설명 문구가 가리킨 정확한 심볼·문장 범위와 주변 문맥이 열리며, 선택 전후 snapshot·computed basis가 같다.
- FA-19: 이름·경로가 비슷하지만 요청 결과와 무관한 후보가 있는 fixture에서 선택 이유와 sourceAnchor가 올바른 후보만 가리킨다.

검증은 Go·Dart contract test, FlowView HTTP·저장 복원 test, Svelte interaction test, MCP compact payload 일치 test, 실제 Molycard 자연어 요청의 CUA 검증으로 구성한다. 실제 검증에서는 사용자가 요청을 설명하는 시작점, 중요한 결정, 다음 호출, 결과 또는 분석 경계를 CodeView 근거로 찾을 수 있는지 확인한다.

### 12.9 폐기된 `architecture` 이행

`architecture`는 CodeFlow에서 폐기한다. 관련 field, type, schema property, 화면 label, 테스트 fixture, 문서 규칙을 제거한다. 기존 저장 View와 외부 consumer가 있는 경우에는 다음 순서로 이행한다.

1. producer·consumer와 저장 데이터의 사용처를 목록화한다.
2. 새 schema version에서 field를 제거하고 새 writer가 더 이상 값을 만들지 않게 한다.
3. 기존 View를 읽어야 하는 기간에는 field를 무시하는 compatibility reader만 허용한다. 화면·MCP·새 분석 결과로 재노출하지 않는다.
4. 지원 기간이 끝나면 compatibility reader와 legacy fixture도 제거한다.

이 절은 관련 과거 명세에 남은 `architecture`의 선택 사항·보조 정보·계층 규칙을 폐기한다. `entry`, `decision`, `process`, `effect`, `result`, `boundary`는 프로젝트 architecture가 아니라 확인된 코드 역할이므로 유지한다.
