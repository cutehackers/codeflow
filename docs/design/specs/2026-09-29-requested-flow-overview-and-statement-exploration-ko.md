## 1. 문제와 목표

현재 FlowView는 문장과 소스 근거를 자세히 보여 주지만, 큰 요청에서는 개별 문장이 상위 관문으로 대량 노출되어 사용자가 처리의 맥을 파악하기 어렵다. 2026-09-28 Molycard 로컬 분석 사례에서는 390개 실행 단계가 312개 관문으로 표시됐고, 그중 277개 관문은 단계 하나만 담았다. 이는 이 사례의 관찰값이며 모든 요청의 수용 상한이나 성능 기준이 아니다. 별도로 선별한 짧은 코드 읽기 경로가 있어도 일반 분석 화면의 기본 결과가 자동으로 개선되지는 않는다.

이 계약은 개발자가 요청한 동작의 시작, 주요 판단과 처리 전환, 결과 또는 미확인 연결을 먼저 이해하게 한다. 현재의 문장별 흐름과 정확한 코드 접근은 별도 탐색 기능으로 유지한다. 특정 함수의 상세 동작을 독립적으로 탐색하는 기능은 향후 같은 탐색 기능을 활용할 수 있지만 이번 계약에서 새 진입 방식을 요구하지 않는다.

- INT-01: 많은 문장 사이에서 요청한 동작의 큰 처리 흐름을 먼저 이해한다.
- INT-02: 기존 문장별 탐색을 독립적인 상세 기능으로 보존하고 개요와 연결한다.

| 의도 | 사용자 목표 | 관찰 가능한 결과 |
|---|---|---|
| INT-01 | GOAL-01 | 사용자는 기본 개요에서 요청한 동작의 시작부터 결과 또는 미확인 경계까지 주요 처리 구간과 분기를 설명한다. |
| INT-02 | GOAL-02 | 사용자는 구간에서 관련 코드 블록을 열고, 필요하면 기존 문장별 탐색으로 내려가 실제 문장과 직접 관계를 확인한다. |
| INT-02 | GOAL-03 | 사용자는 개요와 문장별 탐색을 오가거나 저장된 화면을 다시 열어도 요청·선택·읽던 위치·비교 기준을 잃지 않는다. |

## 2. 범위와 기존 계약의 관계

### 포함

- 하나의 FlowView 안에 **요청 흐름 개요**와 **문장별 탐색**을 구별되는 기능으로 제공한다. 검증된 개요가 있는 새 요청에서는 개요가 첫 읽기 화면이다.
- 개요는 요청에 맞는 처리 목적별 구간, 구간 사이의 확인된 관계와 조건, 구간 안의 코드 블록, 문장별 탐색으로 이동하는 경로를 제공한다.
- 기존 문장별 탐색의 단계·조건·반환·호출·소스·직접 관계와 선택 기능을 보존한다.
- 새 결과의 저장·복원·HTTP·MCP에서 같은 개요와 근거를 제공하며 과거 저장 화면을 소급 변경하지 않는다.

### 제외

- 문장 수나 관문 수를 정해진 숫자로 줄이는 작업. 서로 다른 필수 판단을 감추기 때문이다.
- 새 언어 parser, 실행 추적, 원본 코드 변경, 자동 재분석, 별도 FlowView 제품. 이 기능 분리의 필수 조건이 아니다.
- 특정 함수만 입력받아 새 분석을 시작하는 독립 기능. 이번 범위는 기존 요청 분석에서 문장별 탐색으로 이동하는 경로까지다.
- 기존 스펙과 Vertical Slice의 상태·수용 기준·구현 기록 수정. 이 문서는 그 계약들을 보존한다.

### 기존 계약과 달라지는 공개 동작

2026-09-14·18 계약은 `FlowSequence` 관문을 기본 개요로 정의한다. 그러나 현 구현에서는 많은 관문이 문장 하나에 대응하므로 큰 흐름과 상세 탐색이 같은 목록에 섞인다. 이 계약은 **기본 표시의 책임**을 목적별 요청 흐름 개요에 두고, 기존 `FlowSequence`와 `SemanticStep` 탐색을 별도 상세 기능으로 남긴다. 기존 계약의 1:N 상세 보존, 조건·합류·미확인 경계, 코드 근거, 비교·복원 조건은 유지한다. 이 변경은 기존 계약이나 VS를 소급해서 완료·폐기·대체했다는 뜻이 아니다.

2026-09-21 계약에 따라 `architecture`와 architecture label은 개요의 선정·정렬·병합·표시에 사용하지 않는다. 기존 프로젝트 목적 문구의 계층 횡단은 실제 소스 연결을 따라야 한다는 범위로 읽되, 화면의 구간 종류를 계층명으로 정하지 않는다.

## 3. 사용자와 입력

- 주 사용자: 특정 동작의 구현을 이해하려는 개발자.
- 시작 조건: 원문 요청과 진입 코드가 기존 절차로 확정되고, 현재 snapshot에서 확인한 실행 단계·관계·소스가 있다.
- 개요의 입력: 확정된 원문 요청, 같은 분석의 `SemanticMapIR`, 코드 근거, 기존 `FlowSequence`와 검증된 요청 초점이 있는 경우 그 초점.
- 문장별 탐색의 입력: 현재 저장 View가 이미 제공하는 실행 단계·관계·코드 문맥. 개요를 만들기 위해 원본 분석을 다시 작성하지 않는다.

## 4. 용어와 처리 구간 규칙

**요청 흐름 개요**는 요청한 동작을 설명하는 처리 구간과 그 사이의 확인된 진행·분기·합류·종료를 먼저 보여 주는 읽기 기능이다. **처리 구간**은 사용자가 한 가지 처리 목적으로 이해할 수 있는 코드 묶음이다. **코드 블록**은 구간의 실제 구현을 읽는 소스 단위이며, 함수·파일 경계가 곧 구간 경계라는 뜻은 아니다. **문장별 탐색**은 현재의 `FlowSequence`·`SemanticStep`·CodeView를 따라 구체적 실행 문장과 직접 관계를 확인하는 별도 기능이다.

1. 개요는 요청의 시작 상황, 알고 싶은 처리와 확인하려는 결과를 기준으로 구간을 선정한다. 입력 확인, 경로 선택, 계산, 상태 반영, 외부 효과, 결과 등은 **가능한 처리 역할**이지 고정된 칸이나 필수 순서가 아니다. 제목은 확인된 처리 동작을 구체적인 동사로 설명한다.
2. 조건문·대입·호출·반환이 있다는 사실, 같은 파일·함수·폴더에 있다는 사실, 제목이나 코드 위치가 가깝다는 사실만으로 구간을 만들거나 합치지 않는다. 요청을 이해하는 데 필요한 판단, 다른 구현으로의 인계, 결과를 바꾸는 값·상태·외부 효과, 완료·실패·미확인 경계에서 구간을 나눈다.
3. 한 구간 안의 코드 블록과 문장에는 실제 단계 ID와 소스 범위를 연결한다. 구간 사이 관계는 분석에서 확인한 간선으로 추적할 수 있어야 한다. 배열 순서만으로 진행 화살표를 만들지 않는다.
4. 구간을 접어도 다른 조건 결과, 실패 경로, 반복과 합류, 미확인 연결은 사라지지 않는다. 기본 개요에서 해당 경로의 존재와 결과를 구별하고 필요할 때 상세로 들어갈 수 있어야 한다. 확인되지 않은 실행은 확인된 요청 경로에 포함됐다고 표시하지 않는다.
5. 구간 수를 맞추기 위해 필수 판단을 합치거나 근거가 없는 구간을 추가하지 않는다. 처리 목적을 확인하지 못하면 기술적으로 확인된 동작과 요약 한계를 보여 준다. 의미 라벨 제안은 단계 소속·관계·근거 상태를 바꾸지 못한다.

## 5. 사용자 흐름

1. 사용자가 새 요청의 검증된 View를 처음 열면 유효한 개요의 처리 구간과 확인된 연결이 먼저 보인다. 문장 300개를 첫 목록에 나열하지 않는다. 같은 저장 View를 다시 열 때는 보존된 읽기 상태가 있으면 마지막 탐색 기능·선택·위치를 복원하고, 없으면 개요에서 시작한다.
2. 사용자가 구간을 선택하면 그 목적을 뒷받침하는 코드 블록과 대표 코드, 관련 분기·결과를 본다. 코드 블록을 열면 주변 문맥과 정확히 강조된 문장을 읽는다.
3. 더 자세히 확인하려면 **문장별 탐색**으로 이동한다. 선택한 구간이나 코드 블록에 대응하는 기존 단계가 선택되고, 전체 단계·조건·직접 관계·코드 탐색을 계속 사용할 수 있다. 개요에서 숨긴 문장은 여기에서 찾을 수 있다.
4. 사용자가 개요로 돌아오면 출발 구간, 선택한 문장, 펼침과 스크롤 맥락을 복원한다. 명시적 재분석이나 비교만 기존 화면 교체 규칙을 따른다.

## 6. 데이터·호환성 불변식

- INV-01: 개요와 문장별 탐색은 같은 확정 요청, snapshot, computed basis, 저장 View의 분석을 참조한다. 다른 버전의 코드나 단계 ID를 섞지 않는다.
- INV-02: 개요는 기존 `SemanticMapIR`, `FlowSequence`, `CodeReadingPath` 또는 문장별 탐색 데이터를 삭제·덮어쓰지 않는 별도 버전 관리 결과다. 필요한 공개 필드와 schema는 구현 전에 기존 저장·HTTP·MCP 소비자와 대조해 확정한다.
- INV-03: 개요에 표시한 구간·코드 블록·대표 문장·연결은 실제 단계와 검증된 근거에 역추적된다. 정적 분석을 실제 실행 관측이라고 표현하지 않는다.
- INV-04: 개요에 선택하지 않은 확인된 단계도 문장별 탐색에서 접근 가능하다. 요약은 원본 분석의 완전성이나 근거 상태를 승격하지 않는다.
- INV-05: 과거 View는 그대로 복원한다. 새 개요가 없는 과거 View를 열 때 자동 분석·재저장·추정 개요를 만들지 않고 기존 상세 탐색을 제공한다.
- INV-06: 기존 인증, secret redaction, 읽기 전용 소스, immutable View ID, 명시적 재분석·선택 baseline 규칙을 유지한다. 화면 전환은 분석이나 저장을 자동 실행하지 않는다.

## 7. 실패와 경계

| 조건 | 사용자에게 보이는 결과 | 기존 데이터와 복구 |
|---|---|---|
| 요청 후보나 진입점이 미확정 | 기존 요청 확정 오류와 후보·근거를 표시한다 | 개요나 새 View를 만들지 않는다 |
| 관계 또는 처리 목적의 근거가 부족 | 확인된 부분과 요약 불가 구간을 구별한다 | 문장별 탐색은 유지하고 임의 연결·제목을 만들지 않는다 |
| 개요 생성·검증 실패 | 큰 흐름 개요가 준비되지 않았음을 알리고 문장별 탐색으로 들어갈 수 있게 한다 | 기존 View와 원본 분석을 유지한다. 300개 문장을 정상 개요인 것처럼 기본 표시하지 않는다 |
| 저장된 개요의 참조·snapshot 불일치 | 개요를 신뢰하지 않고 이유를 표시한다 | 과거 View와 기존 상세 탐색을 유지하며 자동 재분석하지 않는다 |
| 기존 분석의 대표 코드 근거가 없음 | 기존 계약에 따라 `analysis_failed`와 원인을 표시한다 | 새 View를 저장하지 않고 기존 View를 유지한다 |
| 기존 분석은 유효하지만 개요 후보의 코드 근거가 없음 | 해당 개요 후보의 소스 한계를 표시하고 검증된 개요로 채택하지 않는다 | 주변 함수 코드만을 정확한 문장 근거로 대체하지 않으며 문장별 탐색은 유지한다 |
| 문장별 탐색의 비대표 상세 코드가 없음 | 해당 문장의 소스 한계를 표시한다 | 다른 문장이나 주변 함수를 정확한 근거로 대체하지 않는다 |

‘빠르게 이해한다’는 임의의 관문 수나 클릭 수로 판정하지 않는다. 실제 사용자 과제에서 시작·핵심 판단·상태 변화·결과 또는 경계를 설명하고 해당 코드 근거에 도달하는지 측정한다. 합격 시간이나 지원 사례 범위는 기존 사용자 검증 계약에 따라 출시 판정 전에 확정한다. 큰 결과에서 기본 개요의 표시 비용과 문장별 탐색으로의 이동도 실제 지원 사례로 측정한다.

## 9. 기능 수용 기준

- FA-01: 확정된 요청에 검증된 개요가 있으면 FlowView의 첫 읽기 화면은 요청의 처리 구간과 확인된 진행·분기·결과 또는 경계를 보여 주며, 개별 문장 전체를 기본 목록에 나열하지 않는다.
- FA-02: 구간을 선택한 사용자는 그 처리 목적에 해당하는 실제 코드 블록을 열고, 강조된 문장을 같은 snapshot의 소스에서 확인할 수 있다.
- FA-03: 사용자는 개요의 구간·코드 블록에서 문장별 탐색으로 이동해 기존의 모든 실행 단계와 직접 관계를 계속 탐색하고 출발 구간으로 돌아올 수 있다. 같은 View를 다시 열면 보존된 탐색 기능·선택·읽던 위치와 비교 기준을 복원한다.
- FA-04: 기본 개요에서 독립적인 조건 결과·실패·반복·합류·미확인 경계의 존재와 결과를 구별할 수 있고, 상세 진입에서 관련 문장과 관계를 확인할 수 있다. 근거 없는 실행 순서나 완료 상태로 합쳐지지 않는다.
- FA-05: 저장·HTTP·MCP의 동일 View는 같은 개요 구간, 참조, 한계를 제공한다. 과거 View의 문장별 탐색과 원본 분석은 새 개요가 없어도 그대로 열린다.
- FA-06: 개요 생성·검증 또는 코드 읽기가 실패하면 새로 만든 내용을 정상 개요나 정확한 코드로 표시하지 않고 기존 View·선택·비교 기준을 보존한다.
- FA-07: 대표적인 큰 실제 요청을 대상으로 개발자가 기본 화면에서 흐름을 설명하고 각 설명을 실제 코드까지 추적하는 과제 결과를 기록한다. 문장 수 감소만으로 이 기준을 통과시키지 않는다.

## 10. 완료 조건

- 일반 요청 분석, 저장 View 복원, HTTP, MCP, FlowView에서 같은 검증된 개요와 상세 진입을 확인한다.
- 기존 문장별 탐색의 단계·관계·코드 선택과 과거 View 호환성 회귀 검사가 통과한다.
- 복잡한 실제 요청에서 분기·합류·미확인 경계를 포함한 사용자 이해 과제를 수행하고 결과를 기록한다. 로컬 테스트만으로 production-ready를 선언하지 않는다.
- 이번 계약에 따른 구현 전에는 별도 Vertical Slice로 범위를 나누고 공개 schema·저장 호환성을 검토한다. 이 문서는 구현이나 VS 승인을 뜻하지 않는다.

## 11. Open Decisions

현재 계약 승인을 막는 결정은 없다. 새 공개 필드명·schema version과 성능·사용자 과제의 합격 수치는 구현 및 출시 검증 전에 기존 소비자와 시험 환경을 확인해 정한다. 이 값이 미정이라는 이유로 확인되지 않은 개요를 정상 결과로 제공할 수는 없다.
