## 1. 문제와 성공 조건

개발자는 요청한 동작의 시작, 결과를 바꾸는 판단, 주요 처리와 인계, 결과 또는 미확인 경계를 먼저 이해하고 해당 코드로 내려가야 한다. 현 Molycard 로컬 분석 사례는 390개 실행 단계가 312개 FlowSequence 관문으로 표시되어 기본 목록만으로 처리의 맥을 읽기 어렵다. 이 수치는 한 사례의 관찰값이며 일반 상한이나 목표 관문 수가 아니다.

0.3.*의 핵심 흐름 중심 경험이 더 낫다는 사용자 의견을 검증 가능한 개선 기준으로 다룬다. 당시 결과가 현재보다 더 정확했다거나 모든 요청에서 더 빨리 읽혔다고 미리 단정하지 않는다. **동일한 요청과 가능한 한 동일한 소스 상태에서 시작·판단·결과 설명, 코드 근거 도달, 잘못 이해한 연결을 비교**한다. 비교가 불가능한 분석 조건은 기록하고 우열 판정에 사용하지 않는다.

- INT-01: 기본 화면에서 요청한 동작의 큰 처리 흐름을 이해한다.
- INT-02: 각 설명을 같은 분석의 정확한 코드와 확인된 관계로 검증한다.
- INT-03: 자세한 문장 탐색과 저장 View의 읽기 맥락을 보존한다.

## 2. 기존 산출물과의 책임

하나의 FlowView에 **Requested Flow Overview**와 **Statement Exploration**을 제공한다. 검증된 개요가 있는 새 View의 첫 읽기 화면은 개요다. Statement Exploration은 기존 FlowSequence, SemanticStep, CodeView의 모든 확인된 상세 단계와 직접 관계를 제공한다.

| 산출물 | 이 계약에서의 책임 |
|---|---|
| `SemanticMapIR` | 같은 요청·snapshot·computed basis에서 얻은 전체 단계, 관계, 근거와 한계의 기준 |
| `FlowSequence` | 기존 관문과 실행 타임라인을 보존하는 상세 탐색 색인 |
| `CodeReadingPath` | 요청에 필요한 선별 코드 지점의 검증된 읽기 경로. 존재하면 개요 후보의 입력으로 활용할 수 있으나 개요 자체나 전체 분기 증명은 아님 |
| Requested Flow Overview | 처리 목적별 구간, 구간 안의 코드 블록, 구간 사이의 증명된 관계와 공개할 한계를 가진 별도 버전 관리 결과 |

이 계약이 승인되면 2026-09-14·18·21·23 계약에서 FlowSequence 또는 짧은 코드 읽기 경로를 **기본 화면**으로 설명한 부분에 한해 개요가 표시 우선권을 갖는다. 기존 산출물의 검증·보존·상세 탐색 책임과 과거 구현 기록은 바꾸지 않는다. 새 개요가 없는 과거 View는 기존 상세 탐색으로 열린다.

## 3. 기본 사용자 흐름

1. 새 요청이 확정되고 상세 분석과 개요가 검증되면, 첫 화면에서 목적별 처리 구간과 확인된 진행·분기·합류·결과 또는 미확인 경계의 존재를 읽는다. 모든 문장이나 모든 FlowSequence 관문을 기본 목록에 펼치지 않는다.
2. 구간을 선택하면 선택 이유, 관련 조건·결과, 실제 코드 블록과 정확히 강조한 문장을 같은 snapshot의 저장된 소스 문맥에서 연다. 블록에 문장이 여러 개면 각 문장으로 이동할 수 있다.
3. 구간 또는 코드 블록에서 Statement Exploration으로 명시적으로 이동한다. 출발 구간에 대응하는 실제 단계가 선택되고, 개요에 올리지 않은 확인된 단계와 직접 관계도 계속 탐색할 수 있다.
4. 개요로 돌아오면 출발 구간, 선택 문장, 펼침, 스크롤, 비교 기준을 복원한다. 같은 View를 나중에 다시 열 때에도 이 읽기 맥락을 복원한다.
5. 개요가 없는 과거 View는 상세 탐색을 열며, 분석·저장·개요 추정을 자동 실행하지 않는다.

## 4. 개요 선정과 관계 증명

1. 시작 상황과 사용자가 알고 싶은 처리·결과에 해당하는 실제 단계에서 후보를 찾는다. 검증된 `CodeReadingPath`가 있으면 그 선택 이유와 지점을 후보로 사용하되, `SemanticMapIR`의 조건 결과·실패·반복·합류·미확인 연결을 다시 확인한다. 읽기 경로에 없는 필수 경로를 조용히 삭제하지 않는다.
2. 한 구간은 한 가지 처리 목적으로 설명 가능한 코드 묶음이다. 결과를 바꾸는 판단, 의미 있는 값·상태 변화, 다른 구현으로의 인계, 외부 효과, 완료·실패·미확인 경계에서 필요에 따라 구간을 나눈다. 고정 구간 수, 파일·함수·계층 경계, 문장 종류, 인접 순서로 구간을 만들거나 합치지 않는다. `architecture`와 architecture label은 선정·정렬·병합·표시에 사용하지 않는다.
3. 각 구간에는 한 개 이상의 실제 단계 ID와 코드 블록을 연결한다. 코드 블록은 검증된 source anchor, 정확한 강조 범위, 저장된 CodeView 문맥으로 추적되어야 한다. 제목은 확인된 처리 동작을 설명하되, 의미 라벨 제안만으로 단계 소속·관계·근거 상태를 바꾸지 않는다.
4. 구간 사이의 **확인된 진행**은 관계의 양 끝 단계와 이를 잇는 순서 있는 실제 간선 참조로 증명한다. 중간 단계를 접더라도 간선 경로와 그 단계의 상세 진입을 보존한다. 같은 구간을 여러 경로가 통과하면 조건 결과와 합류를 각각 식별한다. 반복의 되돌아가는 경로도 순방향 진행으로 바꾸지 않는다.
5. 확인되지 않은 인계나 후속 실행에는 진행 화살표를 만들지 않는다. 마지막으로 확인한 단계와 미확인 대상·이유를 경계로 표시한다. 조건의 다른 결과나 실패 경로가 요청 범위 밖이거나 개요 구간으로 선정되지 않았더라도, 기본 화면에 그 존재와 알려진 결과 또는 한계를 표시하고 상세 진입을 제공한다.
6. 처리 목적을 소스와 요청 근거로 설명할 수 없으면 추정 제목을 만들지 않는다. 확인된 기술적 동작과 요약 불가 이유를 표시한다. 개요는 정적 분석을 실제 실행 관측이나 완료 증명으로 표현하지 않는다.

## 5. 최소 개요 계약과 검증 위치

개요는 기존 분석을 덮어쓰지 않는 별도 버전 관리 결과다. 공개 schema의 최종 필드명은 구현 전 소비자 조사에서 정하되, 다음 정보는 저장·HTTP·MCP의 동일 View에서 의미가 같아야 한다.

| 정보 | 필수 의미 |
|---|---|
| 식별 | schema ID·version, 확정 요청, snapshot ID, computed basis ID. View ID는 상위 저장 View가 부여하고 연결하며 개요 생성 전 입력으로 요구하지 않음 |
| 구간 | 구간 ID, 근거 있는 목적 설명, 포함 단계 ID, 코드 블록의 실제 단계 ID와 source anchor, 선택 이유와 한계 |
| 연결 | 출발·도착 구간과 단계, 순서 있는 간선 참조, 조건 결과, 확인 상태. 미확인 연결은 마지막 확인 단계·이유를 별도로 기록 |
| 결과 상태 | 검증된 개요 사용 가능 여부와, 사용 불가 또는 일부 요약 불가의 이유 |

Curator는 같은 분석의 단계·간선·근거로 구간 소속과 연결을 검증한다. Presenter는 저장 전에 각 대표 코드 블록이 같은 snapshot의 정확한 CodeView 문맥으로 열리는지 검증한다. UI는 구간 소속, 연결, 실행 순서를 새로 추정하지 않는다. 공개 schema를 확정할 때 저장 writer와 reader, HTTP, MCP full·compact, Go·Svelte 타입과 fixture를 함께 조사한다. MCP compact는 코드 본문을 줄일 수 있지만 구간·단계·간선 참조, 조건 결과와 한계의 의미를 누락하지 않는다.

## 6. 저장, 실패, 읽기 상태

| 상황 | 새 저장 결과 | 사용자에게 보이는 동작 |
|---|---|---|
| 요청 또는 진입점 미확정 | 새 View 없음 | 기존 후보·근거와 확정 오류 표시. 열려 있던 View 유지 |
| 대표 코드 근거 등 상세 분석의 필수 검증 실패 | 새 View 없음 | 구조화된 `analysis_failed`와 원인 표시. 열려 있던 View·선택·baseline 유지 |
| 상세 분석은 유효하지만 개요 후보의 목적·관계·코드 검증 실패 | 유효한 상세 분석과 `overview unavailable` 이유를 가진 새 immutable View 저장 | 개요 실패를 알리고 새 상세 View를 명시적으로 열 수 있게 함. 열려 있던 View는 자동 교체하지 않음 |
| 검증된 구간은 있으나 일부 후속 연결이 미확인 | 확인된 개요와 명시적 경계·한계를 함께 저장 | 확인된 부분만 보여 주고 미확인을 완료 경로로 표시하지 않음 |
| 저장된 개요의 참조·snapshot·schema 불일치 | 원본 저장 View 변경 없음 | 개요를 사용하지 않고 이유를 표시. 기존 상세 탐색 제공; 자동 재분석하지 않음 |
| 개요가 없는 과거 View | 원본 저장 View 변경 없음 | 기존 상세 탐색 제공; 자동 개요 생성·재저장하지 않음 |

한 View ID가 가리키는 분석과 개요는 저장 뒤 변경하지 않는다. 나중에 검증한 개요를 기존 View에 붙여야 한다면 새 View ID로 저장하고 원본을 보존한다. 화면 전환이나 읽기 상태 저장은 분석을 실행하지 않는다.

탐색 기능, 구간·단계 선택, 펼침, 스크롤과 선택한 baseline View ID는 **immutable 분석과 분리된 로컬 작업 공간의 읽기 상태**에 View ID를 키로 저장한다. 같은 View를 새로고침하거나 나중에 다시 열 때 복원한다. 브라우저가 바뀌어도 같은 로컬 작업 공간을 사용하면 저장된 상태를 읽을 수 있지만, 다른 기기 간 동기화는 요구하지 않는다. 읽기 상태의 쓰기는 기존 로컬 인증을 요구하며 코드 본문이나 원문 secret을 저장하지 않는다. 대상 View나 baseline이 없어졌거나 선택 ID가 유일하게 대응하지 않으면 임의의 가까운 항목으로 이동하지 않고 복원할 수 없는 항목을 알린다. 새 분석 또는 비교 기준 변경은 사용자가 명시적으로 실행한 뒤에만 적용한다.

기존 인증, 단일 secret redaction 경계, 읽기 전용 소스, immutable View ID와 명시적 재분석·비교 규칙을 유지한다.

## 7. 검증 순서와 기능 수용 기준

### 7.1 사용자 이해 비교

구현 전에 Molycard의 대표 큰 요청을 고정하고, 가능한 경우 v0.3.6과 현재 작업 트리에서 같은 요청·소스 상태로 다음 과제를 수행한다: 시작 찾기, 결과를 바꾸는 판단과 각 결과 설명, 주요 인계와 결과 또는 경계 설명, 각 설명의 정확한 코드 도달. 과제별 정답과 코드 근거, 잘못 이해한 연결, 완료 여부, 걸린 시간, 분석 조건 차이를 기록한다. 비교 환경이 맞지 않으면 그 한계를 기록하고 직접 우열을 주장하지 않는다.

새 개요 구현 뒤 같은 과제를 반복한다. 출시 전 지원 사례와 합격 기준을 미리 정하고, 요청 흐름 설명과 코드 도달의 성공 여부를 우선 판정한다. 관문 수·문장 수·클릭 수 감소만으로 합격시키지 않는다. 큰 결과의 첫 화면 표시 비용과 상세 이동도 측정한다.

### 7.2 기능 수용 기준

- FA-01: 검증된 새 개요의 첫 화면에서 사용자는 시작, 주요 판단과 조건 결과, 처리 전환, 결과 또는 경계를 설명할 수 있으며 모든 문장이 기본 목록에 펼쳐지지 않는다.
- FA-02: 각 개요 구간의 설명과 코드 블록은 같은 snapshot의 실제 단계·정확한 source anchor·CodeView 강조 범위로 역추적된다.
- FA-03: 구간 사이 확인된 연결은 순서 있는 실제 간선 경로와 조건 결과로 역추적된다. 경유 단계, 분기, 실패, 반복, 합류와 미확인 경계가 접힌 상태에서도 잘못된 실행 관계로 합쳐지지 않는다.
- FA-04: 개요에서 상세로 이동하면 대응 단계가 선택되고, 기존의 모든 확인된 단계·직접 관계·코드를 탐색할 수 있다. 돌아오거나 같은 View를 다시 열면 읽던 기능·위치·baseline을 복원한다.
- FA-05: 저장 View, HTTP, MCP full·compact는 같은 개요 구간·참조·조건·한계를 제공한다. 과거 View와 기존 상세 분석은 개요 없이도 열린다.
- FA-06: 상세 분석 실패, 개요만 실패, 일부 연결 미확인, 저장 개요 불일치를 서로 구별하며 각 경우의 저장·화면 동작이 §6과 일치한다.
- FA-07: §7.1의 실제 개발자 과제 결과와 코드 근거 도달 기록이 있다. 과제 결과가 없는 로컬 자동 검사만으로 사용자 이해 개선이나 production-ready를 선언하지 않는다.

## 8. 구현 범위와 선행 결정

구현은 (1) v0.3.6·현재 결과 비교와 개요 후보 검증, (2) 버전 관리 결과·저장·HTTP·MCP 호환, (3) FlowView 기본 개요·상세 이동·읽기 상태, (4) 실제 사용자 과제로 나누어 검토한다. 새 언어 parser, 실행 추적, 별도 FlowView 제품, 과거 View의 소급 재분석, 기존 분석 데이터의 삭제·재작성은 요구하지 않는다.

구현 전에 공개 schema와 읽기 상태의 구체적 저장 형식을 확정하고 저장·HTTP·MCP 소비자 목록 및 과거 View 호환을 검토한다. 이 초안은 기존 승인 계약이나 Vertical Slice의 상태·구현 기록을 바꾸지 않으며, 구현 또는 출시 승인을 뜻하지 않는다.
