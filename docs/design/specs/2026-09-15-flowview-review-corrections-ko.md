# FlowView 리뷰 결함 수정 스펙

- Contract ID: FLOWVIEW-REVIEW-CORRECTIONS
- Contract Status: Proposed
- Intent Status: Interviewing
- Implementation Status: Not started
- Created: 2026-09-15
- Source: 사용자의 리뷰 문서화 요청과 같은 대화의 `review-agent` 리뷰 발견1~발견6, 실제 MCP 오류와 FlowView 복원 응답 확인
- Glossary: [기존 용어집](../glossary.md)

이 문서는 확인된 결함과 수정 수용 기준을 정리한다. 구현 승인이나 수정 완료를 뜻하지 않는다. 저장 호환성과 상태 표시의 미결정 사항은 8절에 별도로 남긴다. 이번 작업에서는 제품 코드, 테스트, 설치 환경을 변경하지 않는다.

## 1. 목적과 기존 계약의 관계

CodeFlow가 생성하는 FlowView에서 근거의 검증 상태와 분석 경계를 정확히 전달하고, 기존 결과 조회·장면 탐색·스킬 갱신의 결함을 수정한다.

| 의도 | 사용자 목표 | 연결된 발견 |
|---|---|---|
| INT-01: 분석 결과보다 강한 확신을 표시하지 않는다 | GOAL-01: 사용자가 검증된 코드와 확인하지 못한 연결을 구분한다 | 발견1, 발견2 |
| INT-02: 저장 결과와 탐색 기능을 일관되게 제공한다 | GOAL-02: 기존 flowId로 저장 결과를 열고 Radar·조건 강조를 정상 사용한다 | 발견3, 발견4, 발견5, 발견7 |
| INT-03: 설치된 사용 지침을 최신으로 유지한다 | GOAL-03: Codex·Claude Code·Antigravity에서 참조 문서를 포함한 최신 스킬을 사용한다 | 발견6 |

관련 계약은 [FlowView 코드 이해](2026-09-14-flowview-code-comprehension-ko.md), [Storyboard 전환](2026-09-15-flowview-storyboard-transition-ko.md), [전환 결정](../decisions/2026-09-15-flowview-storyboard-transition-ko.md)이다. 본 문서는 리뷰 후속 작업이며 기존 문서의 범위·상태·수용 기준을 수정하거나 대체하지 않는다. 기존 문서의 구현 완료 표시는 이 여섯 결함의 해소 증거로 사용할 수 없다.

## 2. 범위와 전제

- 범위1: 서버 장면 상태와 분석 경계 구성, HTTP·MCP의 저장 결과 식별과 실패 응답, 과거 `flow` URL 복원, Radar 호버, 조건 강조 상태, 스킬 전체 갱신.
- 범위2: 기존 프로토타입의 한 줄 스토리보드·실행 타임라인·코드/처리 보기·Radar·3열 구성을 유지한다.
- 범위3: 기존 인증, 소스 읽기 전용, 비밀정보 제거, 저장 근거, 명시적 재분석과 비교를 유지한다.

화면 재설계, 새로운 흐름 선택 막대, 자동 재분석, Live 기능 제거, 일반 코드 정리, 별도 HTML 수정은 제외한다. 상위 작업을 구현 단위로 나누는 별도 문서도 이번 문서화 범위에 포함하지 않는다.

주 사용자는 저장된 코드 흐름을 읽는 개발자이며, MCP 호출자는 에이전트다. 설치 사용자는 기존 CodeFlow 설치를 갱신한다. 검증에는 같은 분석의 SemanticMap·Evidence·Storyboard, 유효한 저장 결과, 실제 지원 어댑터와 제품 서버를 사용한다.

## 3. 발견과 수정 요구사항

### 발견1 · P1 · 근거가 미확인인데 장면을 verified로 표시

- 위치: [BuildStoryboard](../../../internal/semantic/storyboard.go)의 상태 계산.
- 확인된 동작: `EvidenceRefs`가 비어 있지 않으면 참조된 근거의 `validationStatus`를 확인하지 않고 `verified`를 부여한다. 리뷰에서 확인한 실제 저장 결과는 근거가 모두 `unknown`인데 장면 3개가 모두 `verified`였다.
- 요구1: 근거 참조의 존재와 검증 성공을 구분한다. 해당 분석에서 실제로 찾은 근거와 그 검증 상태를 확인한 뒤 장면 상태를 결정한다.
- 요구2: 누락된 참조, 미확인 근거, 서로 다른 검증 상태가 섞인 장면을 검증 완료로 승격하지 않는다. 접힌 내부 단계의 미확인 상태도 묶음 처리로 사라지지 않아야 한다.
- 요구3: 소스 문장 위치의 정확성, 연결 검증, 실행 관측은 서로 다른 사실이다. 연결이 미확인이라는 이유로 보존된 소스를 숨기거나, 정확한 문장 위치만으로 전체 장면의 실행·연결을 검증했다고 표시하지 않는다.

### 발견2 · P2 · 실제 분석 경계가 스토리보드에서 누락

- 위치: [isStepBoundary](../../../internal/semantic/storyboard.go), [CompileDeterministicFeatureMap](../../../internal/semantic/compiler.go).
- 확인된 동작: 컴파일러의 `BoundaryTargets`에는 기존 단계와 다른 경계 ID가 들어간다. 장면 구성은 이를 단계 ID·이름과 비교한다. 실제 저장 결과의 경계 5개가 스토리보드에서는 0개였다. 현재 단위 테스트는 경계 값에 단계 ID를 넣어 실제 생산 경로와 다르다.
- 요구1: 컴파일러가 확인하지 못한 호출과 그 출발 위치를 장면 구성까지 전달하고, 사용자가 스토리보드·타임라인에서 분석이 끊긴 지점을 확인할 수 있게 한다.
- 요구2: 경계는 하단 미확인 목록에만 남기지 않는다. 연속 내부 처리로 접더라도 미확인 연결과 그 이유에 접근할 수 있어야 한다.
- 요구3: 존재하지 않는 대상 단계나 소스를 만들지 않는다. 근거가 있는 호출 지점과 확인하지 못한 대상 정보를 구분한다. 이유를 확인할 수 없으면 그 한계도 표시한다.

### 발견3 · P2 · request.flowId에 후보 ID를 저장

- 위치: [HTTP 결과 저장](../../../internal/flowview/server.go), [MCP 결과 저장](../../../internal/mcp/semantic_handlers.go), [RestoreLegacyFlow](../../../internal/flowview/task_view_persistence.go).
- 확인된 동작: HTTP와 MCP가 `resolved.CandidateID`를 `request.flowId`에 저장한다. 리뷰의 실제 결과는 `cand-79b7311f1e89f483`였고 정식 ID는 `flow-79b7311f1e89f483`였다. 복원은 문자열 일치로 조회하므로 정식 flowId로 새 저장 결과를 찾지 못한다.
- 요구1: 새 결과는 정식 `resolved.FlowID`를 저장한다. 후보 ID와 저장된 흐름 ID를 서로 대체하지 않는다.
- 요구2: 같은 flowId로 결과를 조회할 때 대응하는 저장 FlowView를 찾고, HTTP와 MCP가 같은 viewId·분석 결과를 반환해야 한다. 열기만으로 추가 분석하지 않는다.
- 요구3: 이미 잘못된 후보 ID로 저장된 결과도 보존한다. 기존 viewId와 해당 내용의 해시 관계를 깨뜨리는 파일 덮어쓰기를 하지 않는다. 과거 저장 결과를 정식 흐름과 연결하는 호환 정책은 질문2에서 확정한다.

### 발견4 · P2 · Radar 호버 시 노드 위치 변경

- 위치: [BlastRadiusRadar.svelte](../../../web/flowview/src/components/BlastRadiusRadar.svelte)의 `.radar-node:hover`.
- 확인된 동작: CSS의 `transform: scale(1.04)`가 SVG 노드의 `translate(...)`를 덮어쓴다. 브라우저 재현에서 호버만으로 노드가 중앙 방향으로 이동했다.
- 요구1: 호버 효과는 노드의 배치 좌표를 보존한다. 확대가 필요하면 배치와 시각 효과가 서로 덮어쓰지 않게 한다.
- 요구2: 마우스로 보이는 노드를 클릭하거나 키보드로 선택하면 같은 검증된 직접 관계로 이동한다. 스토리보드·타임라인·소스 선택과 원래 장면 복귀가 유지되어야 한다.

### 발견5 · P2 · 조건 강조를 해제할 수 없는 장면 발생

- 위치: [App.svelte](../../../web/flowview/src/App.svelte)의 조건 목록, [FlowStore](../../../web/flowview/src/stores/flowStore.svelte.ts)의 선택·필터 상태.
- 확인된 동작: 조건 목록은 선택 장면의 단계로 제한하지만 `conditionFilter`는 이전 장면 값을 유지한다. 분기가 없는 장면으로 이동하면 코드가 흐려진 채 선택 상자가 비활성화되어 필터를 해제할 수 없다. 상태 전이로 재현했다.
- 요구1: 조건 필터와 선택 장면의 범위를 일치시킨다. 다른 장면의 필터가 남더라도 사용자가 현재 화면에서 그 상태를 확인하고 해제할 수 있어야 한다.
- 요구2: 조건이 없는 장면에 들어갔다고 해제 기능까지 차단하지 않는다. 표시된 선택 값과 실제 적용된 필터가 달라서는 안 된다.
- 요구3: 필터 변경·해제는 분석과 비교 기준을 변경하지 않는다. 장면 이동 때 필터를 초기화할지 유지할지는 질문3에서 확정한다.

### 발견6 · P2 · 참조 문서만 변경되면 스킬 갱신 누락

- 위치: [install.sh](../../../scripts/install.sh)의 스킬 복사 조건.
- 확인된 동작: 설치 스크립트는 `SKILL.md`만 비교한다. 이번 변경처럼 `references/static-flowview.md`만 바뀌면 새 사용 지침이 설치되지 않는다. 이번 로컬 설치는 수동 동기화로 보완했지만 스크립트 결함은 남아 있다.
- 요구1: 스킬 갱신 판정은 본문뿐 아니라 배포 대상 참조 파일·스크립트의 변경도 반영한다. Codex·Claude Code·Antigravity의 실제 스킬 경로에 적용한다.
- 요구2: 본문은 같고 참조 파일만 다른 기존 설치를 갱신하면 최신 참조 내용이 설치되어야 한다. 반복 설치 후에도 최신 상태를 유지한다.
- 요구3: 다른 스킬과 MCP 등록은 보존한다. 현재 사용자의 설치 지시인 백업 없이 최신으로 교체한다는 범위를 따르되, 일반 배포에서 기존 사용자 수정 보호 정책을 없애는 변경까지 확대하지 않는다.

### 발견7 · P1 · 기존 `flow` URL이 저장된 소스 문맥을 복원하지 못함

- 위치: [RestoreLegacyFlow](../../../internal/flowview/task_view_persistence.go), [FlowView 화면 초기화](../../../web/flowview/src/App.svelte), [코드 패널 빈 상태](../../../web/flowview/src/components/CodeFlowPanel.svelte).
- 재현 입력: MCP가 반환한 `?flow=flow-25c5394f47d167ae`, `?flow=flow-f7ead8a27fbc92ab`, `?flow=flow-2001a91cba9a0443` URL을 연다.
- 확인된 동작: 세 URL은 `viewId`가 아닌 과거 `flow` 조회 경로를 사용한다. 실제 서버의 과거 흐름 조회 응답은 세 경우 모두 `flowContexts`가 비어 있고 `sourceFiles`도 없다. 그 결과 코드 패널은 “이 분석에 연결된 소스가 없습니다. 코드 내용을 추정하지 않습니다.”를 표시한다.
- 원인1: 과거 흐름 복원은 저장 결과를 `request.flowId == flowId`로만 찾는다. 발견3의 후보 ID `cand-…`와 정식 흐름 ID `flow-…` 불일치 때문에, 소스 문맥이 저장된 결과도 찾지 못하고 빈 과거 데이터로 내려간다.
- 원인2: `onCellTapped → _executePlayerMove` 요청은 `ambiguous_target: duplicate structural step identity` 컴파일 실패로 끝났다. 실패 결과에는 성공한 저장 FlowView와 `viewId`를 만들 수 없다.
- 원인3: 독립형 오프라인 HTML은 서버 저장 결과 조회와 소스 문맥 복원의 근거가 아니다. 제품 FlowView와 같은 실제 분석 결과로 표시하거나 연결하지 않는다.
- 요구1: 성공한 HTTP·MCP 분석은 `viewId`와 `?viewId=…` URL을 반환하고, 해당 URL을 열면 저장된 `flowContexts`·`sourceFiles`·분석 식별 정보를 조회만으로 복원한다. 열기 중 분석은 0회다.
- 요구2: 기존 `?flow=…` URL은 정식 flowId, 보존된 후보 ID, entry symbol을 사용해 저장 결과를 안전하게 찾는다. 하나로 확정할 수 없으면 빈 코드 패널 대신 “과거 분석에 보존된 소스 문맥이 없어 재분석이 필요함” 상태와 이유를 표시한다.
- 요구3: 컴파일 실패·후보 미선택·저장 실패에는 FlowView 바로가기 URL을 만들지 않는다. MCP는 실패 코드, 원인, 사용자가 선택할 수 있는 후보 또는 재시도 방법만 반환한다.
- 요구4: 과거 URL의 호환은 기존 저장 파일과 viewId를 덮어쓰거나 변경하지 않는다. 후보 ID와 정식 흐름 ID의 대응이 모호하면 임의의 다른 분석을 열지 않는다.

## 4. 불변식과 실패 처리

| 규칙 | 보장할 동작 |
|---|---|
| 불변1 | Storyboard는 해당 분석의 근거보다 강한 검증 상태를 주장하지 않는다. |
| 불변2 | 미확인 연결은 관계 없음·성공한 결과·구현되지 않음으로 바꾸어 표시하지 않는다. |
| 불변3 | 저장된 결과 열기는 조회다. 재분석·비교는 명시적인 요청으로만 실행한다. |
| 불변4 | 기존 viewId, flowId, URL, 저장 근거와 인증·비밀정보 제거 규칙을 보존한다. |
| 불변5 | 복원 실패와 목록 조회 실패는 빈 결과로 숨기지 않는다. 잘못된 대응은 임의의 흐름으로 대체하지 않는다. |
| 불변6 | 화면 상호작용과 스킬 갱신은 무관한 사용자 데이터나 설정을 변경하지 않는다. |
| 불변7 | 소스 문맥이 없는 과거 결과와 분석 실패를 성공한 FlowView로 표시하거나, 빈 코드 상태를 분석 결과 부재와 구분 없이 표시하지 않는다. |

저장 호환 조회에서 하나의 흐름으로 확정할 수 없으면 미확인 이유를 반환한다. 설치 갱신이 실패하면 성공으로 보고하지 않는다. 이번 수정과 무관한 인증·취소·응답 역전 처리의 의미는 바꾸지 않는다.

## 5. 사용자 흐름

1. 사용자가 CLI 또는 MCP에서 성공한 분석 결과를 연다. `viewId`로 같은 결과와 소스 문맥을 조회한다.
2. 스토리보드에서 주요 처리와 분석 경계를 보고, 장면을 선택해 보존된 소스와 미확인 이유를 확인한다.
3. 조건 강조 후 다른 장면으로 이동해도 필터 상태를 이해하고 해제할 수 있다.
4. Radar 노드에 마우스를 올려도 위치가 유지되며, 선택과 원래 장면 복귀가 동작한다.
5. 사용자가 과거 `flow` URL을 열면 대응하는 저장 결과를 복원하거나, 재분석 필요 이유를 확인한다.
6. 사용자가 설치를 갱신하면 세 앱 모두 최신 스킬 참조 문서를 사용한다.

## 6. 수용 기준과 필요한 증거

| 수용 기준 | 합격 조건 | 검증 경로 |
|---|---|---|
| FA-01 · 발견1 | 검증됨·미확인·참조 누락·혼합 근거에 대해 확정된 장면 상태 규칙을 지킨다. 근거 전체가 unknown인 실제 분석을 모두 verified로 표시하지 않는다. | Go 장면 구성 테스트와 실제 HTTP·MCP 결과 |
| FA-02 · 발견2 | 실제 컴파일러가 출력한 경계가 장면·타임라인에서 확인된다. 외부 대상 미포함과 다중 후보 모호성을 구분하며 가짜 단계·소스를 만들지 않는다. | 실제 어댑터 → 컴파일러 → Storyboard → 브라우저 |
| FA-03 · 발견3 | 정식 flowId로 HTTP·MCP 저장 결과의 viewId를 찾는다. 새로고침·재시작 후 동일 근거를 복원하고, 과거 cand ID 결과의 기존 viewId도 유효하다. 조회 중 분석 호출은 0회다. | 저장·HTTP·MCP 계약 테스트 |
| FA-04 · 발견4 | 실제 관계가 있는 Radar 노드의 배치 중심이 호버 전후 유지되고, 마우스·키보드 선택과 복귀가 같은 단계에 도달한다. | 실제 제품 번들의 브라우저 상호작용 |
| FA-05 · 발견5 | 조건 선택 → 분기 없는 장면 이동 → 강조 해제가 가능하다. 선택 상자와 필터 상태가 일치하고 코드·처리 보기 모두 정상 표시한다. | Svelte 상태·컴포넌트 및 브라우저 테스트 |
| FA-06 · 발견6 | SKILL.md는 같고 참조 파일만 다른 기존 설치에서 참조 파일이 갱신된다. 반복 설치와 세 앱의 설치 경로를 확인하고 다른 설정은 유지한다. | 격리된 설치 환경과 파일 내용 비교 |
| FA-07 · 발견7 | 성공한 MCP 결과의 `viewId` URL을 열면 분석 ID·소스 문맥·소스 파일이 저장 결과와 일치한다. 기존 `flow` URL은 대응 저장 결과를 복원하며, 대응 불가·컴파일 실패에는 재분석 필요 또는 실패 상태를 명확히 표시하고 빈 성공 화면이나 새 분석을 만들지 않는다. | 실제 HTTP·MCP → 저장소 → 서버 재시작 → 브라우저 계약 테스트 |

테스트는 실패 동작을 먼저 재현한 뒤 수정 후 통과를 확인한다. Radar가 비어 있는 테스트나 실제 컴파일러 형식과 다른 경계 fixture만으로 해당 기능을 검증했다고 판단하지 않는다. 구현의 단순한 복사나 문자열 존재 검사만 수행하는 테스트는 위 사용자 동작 검증을 대체할 수 없다.

## 7. 검증 명령과 현재 증거의 한계

- 검증1: Go 변경 시 `make fmt`, `make check-naming`, `make vet`, `make test`를 실행한다. 저장·공유 요청 경계 변경에는 `go test -race -p 1 ./internal/...`를 추가한다.
- 검증2: UI 변경 시 `npm --prefix web/flowview test`, `make build-ui`, `npm --prefix web/live-comprehension-workspace run test:flowview`를 실행한다. Svelte 산출물과 Go 내장 화면의 일치를 확인한다.
- 검증3: 설치 검증은 격리된 HOME에서 기존 설치를 구성하고 실제 설치 스크립트로 수행한다. 어댑터 변경이 없다면 어댑터 구현 테스트를 무조건 확대하지 않는다.

리뷰 당시 UI 테스트 12개는 통과했지만 발견1~발견7의 실패 경로를 모두 다루지 않았다. 실제 저장 결과의 ID·경계·검증 상태 확인, 상태 전이 재현, 호버 브라우저 재현, 과거 URL의 빈 소스 응답은 결함 확인 증거이며 수정 완료 증거가 아니다. 재현 명령·입력·소스 리비전·기대값·실제 결과를 후속 구현 검증에 남겨야 한다.

## 8. 가정과 미결정

| ID | 확인할 내용 | 선택지 또는 후속 조치 |
|---|---|---|
| 가정1 | 이번 문서의 범위는 리뷰의 여섯 결함과 실제 URL 복원 결함이다. | 추가 결함은 별도로 기록한다. 범위 확대가 필요하면 본 계약을 명시적으로 개정한다. |
| 질문1 | 여러 단계와 근거가 섞인 장면에서 partial과 unknown을 어떻게 구분할 것인가? | 검증 완료를 부당하게 부여하지 않는다는 요구는 확정한다. 소스 확인과 연결 검증을 분리한 상태표를 구현 전에 확정한다. |
| 질문2 | 이미 cand ID로 저장된 결과를 정식 flowId와 어떻게 연결할 것인가? | 보존된 entrySymbol로 조회 시 대응하거나 별도 호환 색인을 둘 수 있다. 기존 결과의 내용과 viewId를 바꾸지 않는 방식을 선택하고 모호성 처리를 검증한다. |
| 질문3 | 장면 이동 시 이전 조건 필터를 유지할 것인가? | 해당 장면에 속하지 않으면 초기화하거나, 유지하되 현재 화면에서 표시·해제 가능하게 한다. 선택·읽기 위치 보존 규칙과 함께 확정한다. |
| 질문4 | 과거 `flow` URL에서 여러 저장 결과가 대응될 때 무엇을 열 것인가? | 시간순으로 임의 선택하지 않는다. viewId 선택을 요구하거나 entry symbol·분석 식별 정보로 하나로 확정하는 정책을 구현 전에 정한다. |

질문1~질문3은 이 문서에서 사용자 결정으로 간주하지 않는다. 새로운 저장 형식이나 상태 정책을 승인한 ADR도 아직 없다. 기존 용어를 사용하므로 이번 문서화에서는 용어집을 변경하지 않는다. 상태 매핑·호환성·필터 정책을 확정하기 전에는 구현 승인이나 계약 확정을 주장하지 않는다.

## 9. 완료 조건

- 완료1: 미결정 사항을 확정하고 필요 시 별도 결정 기록에 근거·대안·영향을 남긴다.
- 완료2: FA-01~FA-07에 각각 실제 실패 재현과 수정 후 통과 증거가 있다.
- 완료3: 해당 변경에 필요한 Go·UI·설치 검증이 통과하고, CLI·MCP가 제공하는 번들로 브라우저 동작을 확인한다.
- 완료4: 설치 파일 일치와 앱의 실제 연결 상태를 구분해 보고한다. 실행 중인 앱이 옛 프로세스를 유지하면 재연결 필요 상태를 명시한다.

문서 작성 완료와 결함 수정 완료를 구분한다. 현재 완료한 범위는 리뷰 내용의 스펙 문서화다.
