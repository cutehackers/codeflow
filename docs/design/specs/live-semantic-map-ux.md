# Live Semantic Map UX 최종 설계

상태: `live-semantic-map-prototype.html`을 Live Semantic Map의 고정 화면 템플릿으로 지정. 이해도 향상 효과와 백엔드 지원 범위는 별도 검증 필요.

스킬과 MCP의 Live Semantic View/Map 요청은 이 템플릿의 제품 화면을 사용한다. `query_task_view`의 feature 응답은 `flowView.template`과 같은 coordinator의 `/live` URL을 반환한다. 화면 변경은 `docs/samples/live-semantic-map-prototype.html`에서 수행한 뒤 `go generate ./internal/flowview`로 제품 HTML을 갱신한다. 제품에서는 샘플 초기화만 실제 API·이벤트 초기화로 교체한다. Go 테스트가 템플릿과 제품 렌더러의 일치를 검증한다.

작성일: 2026-09-09

샘플: [실시간 흐름 이해 프로토타입](../../samples/live-semantic-map-prototype.html). HTML 파일을 브라우저에서 열면 동작한다. 모든 코드·분석·실행 사례는 설명용 데이터이며 실제 프로젝트 분석 결과가 아니다.

## 목적과 최종 방향

개발자가 요청한 시나리오가 코드에서 어떻게 처리되는지 빠르게 이해하고, 작성 중 발생한 동작 변화를 기존 맥락 안에서 확인하도록 한다.

화면의 중심은 **실행 순서로 연결된 실제 코드**이다. 시작 이벤트부터 각 아키텍처 계층의 처리, 조건 분기, 데이터 전달, 외부 처리와 최종 응답까지 관련 소스 구간으로 연결한다. 단계 설명은 한 줄로 제한하고 조건·호출의 이해에 필요한 코드를 기본으로 노출한다. 변경은 해당 코드 위치에서 비교한다. 사용자가 읽는 위치와 비교 기준은 실시간 갱신 중에도 유지한다.

Static FlowView는 기존 화면과 진입점을 유지한다. Live Semantic Map은 `/live`에서 별도 HTML로 제공한다. 이전 `/?live=1` 링크도 Live 전용 화면으로 연결한다. `query_task_view`의 feature 응답은 같은 coordinator의 Live URL에 요청과 시작 심볼을 포함한다. 클라이언트는 반환 URL을 열거나 사용자에게 제시해야 한다. `autoOpen` 값 자체가 브라우저 실행을 보장하지는 않는다.

핵심 흐름은 요청된 시작 이벤트에서 처리가 끝날 때까지의 모든 아키텍처 계층 통과와 처리 단계를 포함한다. 동일 계층 재진입, 비동기 후속 처리, 실패 이후의 응답도 포함한다. 계층 수나 단계 수를 고정하지 않는다. 계층 통과를 진행하지 않는 세부 문장은 상세 근거에서 확인한다.

## 결정1. 코드 흐름과 처리 흐름의 공유 화면

기존 코드 흐름을 기본 보기로 유지하고 상단의 `코드 흐름 / 처리 흐름` 버튼으로 중앙과 우측을 함께 전환한다. 왼쪽 처리 타임라인은 두 보기에서 공유한다. 코드 흐름은 넓은 중앙에 실제 소스를, 처리 흐름은 행동·계층·조건·확인된 연결을 표시한다. Static FlowView는 별도 화면으로 유지한다.

선택 단계와 조건 위치, 펼친 코드는 유지한다. 중앙은 높이 제한 없이 페이지 아래로 이어지고, 타임라인·우측 맥락·보기 전환은 스크롤 중에도 접근할 수 있게 한다. 보기 전환 시 읽던 단계와 화면 내 위치를 복원하되 페이지 끝에서는 브라우저의 스크롤 한계가 적용된다. 전환에는 짧은 투명도 변화만 사용하고 동작 감소 설정에서는 생략한다. 보기 전환 자체는 새 분석 요청이나 도착한 변경 적용을 일으키지 않는다.

상단은 요청한 흐름의 제목, 확인된 단계 수와 포함 계층, 최초 표시 코드 대비 변경된 단계를 짧게 표시한다. 포함 계층의 나열을 실제 실행 경로로 표현하지 않는다. 샘플 상태 변경 버튼은 기본적으로 접힌 `샘플 시나리오`에 둔다.

| 영역 | 기본 내용 | 조작 |
|---|---|---|
| 요청과 안내 | 요청한 흐름, 읽기 고정·변경 도착·소스 미확인 안내 | 갱신 일시정지·재개, 도착한 변경 적용 |
| 처리 목록 | 행동 한 줄과 계층 | 중앙의 해당 코드로 이동 |
| 중앙 코드 흐름 | 파일·함수·계층, 줄 번호가 있는 실제 소스, 조건·호출 문장 강조, 다음 구현 연결 | 관련 코드 펼치기, 함수 전체, 연결된 구현 이동, 이전 코드 비교 |
| 중앙 처리 흐름 | 행동과 계층, 판단 조건, 외부 처리, 확인된 호출·반환·분기 연결 | 단계 선택, 연결된 처리 이동 |
| 선택 맥락 | 조건, 외부 처리, 확인된 상태 변경, 호출한 곳 | 선행 코드 이동, 소스 범위 상세 확인 |

우측은 코드 보기에서 호출한 코드와 소스 범위를, 처리 보기에서 판단 조건·상태 변화·외부 처리·이어지는 연결을 제공한다. 처리 보기의 `이 단계의 코드 보기`는 같은 단계를 선택한 상태로 코드 보기로 이동한다. 제공된 근거가 없는 정보는 생성하지 않는다.

단계 이름은 `재고 확인`과 `Inventory.checkStock`을 함께 표시하는 식으로 행동과 구현을 연결한다. 함수 이름만으로 비즈니스 동작을 추정하지 않는다. 중앙의 소스는 선택한 분석과 동일한 스냅샷에서 가져온다. 소스가 없으면 미확인으로 표시하며 현재 파일 내용이나 설명 문장으로 대체하지 않는다. 정확한 문장 범위를 확보하지 못했다면 주변 코드는 읽을 수 있게 제공하되 특정 줄을 실행 문장으로 강조하지 않는다.

분기 라벨은 `충분 / 부족`처럼 조건을 읽을 수 있게 한다. 선택하지 않은 분기도 존재를 유지한다. 접힌 구간에는 숨겨진 단계와 분기 수를 표시한다. 분석이 끝난 지점과 실제 처리가 끝난 지점을 구분한다. 범위 밖의 처리는 `이후 처리 미확인`으로 표시한다.

비동기·병렬 처리는 하나의 직렬 경로로 바꾸지 않는다. 분기 시작, 재합류 조건, 요청 응답 이후 계속되는 처리를 명시한다. 샘플의 직렬 주문 시나리오가 제품의 전체 처리 모델을 제한하지 않는다.

## 결정2. 조건 탐색과 데이터 추적

중앙 상단의 조건 위치 선택은 두 보기에서 공유한다. 현재 구현은 해당 조건과 직접 연결이 확인된 단계를 강조하고 다른 단계도 유지한다. 현재 데이터에는 참·거짓과 연결 대상의 명시적 대응이 없으므로 가능한 실행 경로를 계산하거나 결과를 가정하지 않는다. 데이터 추적과 실행 기록 탐색은 아래의 설계 방향이며 이번 보기 전환 구현에는 포함하지 않는다.

데이터를 선택하면 생성·입력 위치, 사용하는 조건, 변환 지점, 전달 대상만 강조한다. 각 단계에 전체 JSON을 반복하지 않는다. 값이 없으면 식과 출처를 표시한다.

예: `요청 수량 → 재고 비교 → 예약 요청 → 예약 결과의 식별자 → 주문 생성`.

실행 기록을 선택하면 해당 코드 버전·입력·실행 시점에 관측한 경로와 값을 표시한다. 과거 실행 기록을 최신 코드의 실행 증거로 재사용하지 않는다. 다른 코드 버전의 기록은 버전 차이를 명시한다.

## 결정3. 변경을 동작의 전후 차이로 표시

변경 위치에 짧은 표시를 두고 상세에서 같은 조건의 이전·현재 결과를 비교한다.

예:

> 이전: 재고 부족 조건에서 주문 생성으로 진행한다.
> 현재: 재고 부족이면 오류 응답으로 종료한다.

양쪽 근거가 확보됐을 때만 이렇게 표현한다. 예외 발생만 확인했다면 `부족 조건과 예외 발생 추가`까지만 확정하고 화면 표시 결과는 미확인으로 둔다.

비교 기준은 `작업 시작 시점`을 기본값으로 고정한다. 사용자는 `직전 분석` 또는 보존된 시점을 선택할 수 있다. 비교 기준과 표시 버전을 항상 식별할 수 있어야 한다. 삭제된 처리도 비교 중에는 남겨둔다. 이름 변경을 동작 변경으로, 대응 관계가 모호한 이동을 확정 이동으로 처리하지 않는다.

여러 파일의 수정이 하나의 동작을 완성하면 일관된 분석 결과 단위로 함께 반영한다. 서로 다른 버전의 노드·설명·근거를 섞지 않는다.

## 결정4. 읽는 동안 맥락을 보존하는 갱신

| 상태 | 화면의 표현 | 전환 규칙 |
|---|---|---|
| 편집 감지 | 관련 범위에 `수정 감지 · 분석 대기` | 기존 의미 설명을 새 결과처럼 바꾸지 않는다. |
| 분석 중 | `이전 분석 표시 중`과 영향 범위 | 미완성 구문을 새로운 동작으로 확정하지 않는다. |
| 분석 완료 | 일관된 새 결과와 변경 요약 | 선택·스크롤·확대·펼침 상태를 보존한다. |
| 읽기 고정 | 표시 버전 유지, `새 변경 도착` | 수신·분석은 계속하고 사용자가 적용한다. |
| 분석 실패 | 마지막 결과와 실패 범위·이유 | 오래된 결과를 최신으로 표시하지 않는다. |
| 연결 끊김 | `최신성 확인 불가` | 재연결 후 최신 버전을 확인하기 전까지 해제하지 않는다. |

일시정지는 화면 적용만 멈춘다. 재개 또는 변경 적용 시 완성된 최신 결과를 보여주며 표시 버전과 비교 기준을 갱신한다. 사용자가 코드 근거나 비교 상세를 읽는 중에는 내용이 자동 교체되지 않게 한다.

편집 위치 따라가기는 선택 기능이다. 에이전트가 다른 파일을 편집해도 사용자의 선택을 자동 이동시키지 않는다. 선택 단계가 삭제되면 삭제된 단계의 비교 내용을 유지하고 다음 이동을 선택하게 한다.

지연 피드백은 편집 수신 직후 보여주되, 의미 결과는 분석 완료 후 반영한다. 초기 사용성 실험의 수신 피드백 목표는 200ms 이내로 둔다. 이는 구현 보장이나 연구에서 확인된 이해 속도가 아니다. 의미 분석 지연은 별도로 측정한다.

## 결정5. 근거 수준과 최신성을 분리

| 표시 | 필요한 근거 | 표현 제한 |
|---|---|---|
| 코드에서 확인 | 특정 코드 버전의 조건·호출·데이터 관계 | 실제 실행 성공으로 표현하지 않는다. |
| 실행에서 관측 | 버전과 입력이 연결된 실행 기록 | 다른 입력에서도 성립한다고 일반화하지 않는다. |
| 추정 | 추론 내용과 그 근거 | 확정 경로와 구분하고 수정·반박할 수 있게 한다. |
| 미확인 | 누락된 근거 또는 분석 범위 | 빈칸이나 정상 통과로 표시하지 않는다. |

`최신 분석 반영`은 최신성만 뜻한다. 요구사항 충족, 버그 없음, 테스트 성공을 뜻하지 않는다. 코드 근거는 선택한 주장에 해당하는 최소 범위를 제공하고 원본 위치로 이동할 수 있게 한다.

호출 관계는 영향 가능성의 근거이지 실패의 근거가 아니다. 실제 실패 기록이 없으면 `관련 테스트`라고 표시한다. 요구사항에 관련된 구현을 찾았다는 사실과 요구사항 검증 완료를 분리한다.

## 결정6. 시각적 우선순위

흰색·검정·중립 회색만 사용한다. 녹색을 포함한 유채색은 코드와 강조에도 사용하지 않는다. 위치·짧은 문장·기호로 의미를 전달한다. 선택 문장은 회색 배경과 검정 줄 표시로 구분한다.

내부 컴파일러 상태, epoch, lag, settlement, 벤치마크 지표를 기본 화면에 노출하지 않는다. 읽는 코드의 한계는 `이전 코드 표시 중`, `정확한 문장 범위 미확인` 등 이해에 필요한 문장으로만 알린다.

선택 단계, 선택 경로, 이번 변경의 강조를 서로 구분한다. 선택은 굵은 외곽선, 변경은 `+ 추가` 또는 `변경` 라벨, 미확인은 명시적 문구를 사용한다. 삭제 내용을 읽기 어려운 투명도로 낮추지 않는다.

상시 펄스·깜빡임·스캔·카운트다운을 사용하지 않는다. 갱신 시 화면 전체를 다시 배치하지 않는다. 연결을 읽기 어려워질 때는 사용자 요청으로 재정렬할 수 있게 한다. 키보드 선택과 명확한 포커스, 읽을 수 있는 대비, 좁은 화면의 세로 배치를 제공한다.

| 제외4 | 분석 내부 단계와 게이트의 상시 계측 | 사용자의 흐름 이해를 방해한다. 지연·실패 원인의 상세 진단으로 제한한다. |
| 제외5 | 별도 스토리보드·타임라인의 중복 | 같은 순서를 반복해서 읽게 한다. 핵심 흐름과 선택 상세로 통합한다. |

| 참조 | 범위 | 필요한 데이터 |

## 실제 편집 경로 검증

`web/live-comprehension-workspace/tests/live-semantic-mcp.spec.ts`는 임시 프로젝트와 실제 MCP·TypeScript 어댑터를 실행한다. MCP가 반환한 고정 템플릿 URL에서 연속 편집 자동 반영, 읽기 고정 중 변경 보류·적용, 분석 실패 시 이전 코드 유지, 분석 조건 복구 후 자동 반영을 검증한다. 분석 결과나 브라우저 이벤트를 테스트에서 주입하지 않는다. 편집은 파일에 기록하고 `submit_versioned_edit`로 제출한다. 일반 파일 저장만의 자동 감지는 이 검증에 포함되지 않는다.

실행: `cd web/live-comprehension-workspace && npx playwright test tests/live-semantic.spec.ts tests/live-semantic-mcp.spec.ts --workers=1`.

## 검증 계획

현재 화면과 제안 화면에 같은 변경 기록과 동일한 질문을 제공한다. 순서에 따른 학습 영향을 줄이도록 화면 순서와 동등 난도의 과제를 교차 배정한다. 직접 작성과 에이전트 작업 관찰을 나누고, 익숙한 코드와 익숙하지 않은 코드를 포함한다.

| 참조 | 과제 | 측정 |
|---|---|---|
| 검증1 | 시작부터 결과까지 설명 | 처리 순서 정확도와 완료 시간 |
| 검증2 | 실패 조건과 데이터 전달 설명 | 조건·결과·데이터 출처의 정답률 |
| 검증3 | 연속 편집의 동작 차이 설명 | 놓친 변경과 잘못 이해한 변경 수 |
| 검증4 | 분석 실패·일시정지 상태 판단 | 오래된 결과를 최신으로 오인한 비율 |

주요 판단 기준은 정답률을 낮추지 않으면서 근거를 포함한 설명 시간이 줄어드는가이다. 최신성·실행 여부의 오인은 별도로 줄어야 한다. 탐색 클릭 수와 주관적 부담은 보조 지표로 측정한다. 효과가 확인되기 전에는 `1초 이해`나 `100% 이해`를 성과로 주장하지 않는다.

## 샘플 체험

샘플은 제품의 Live 전용 렌더러와 같은 HTML/CSS/JavaScript에 설명용 데이터를 넣은 독립 HTML이다. 중앙 소스, 호출·분기 이동, 이전 코드 비교와 읽기 고정을 체험한다. 샘플에서는 코드 분석이나 제품 API 호출을 수행하지 않는다. 실제 진입 및 소스 제공은 별도의 MCP·HTTP·브라우저 통합 검증으로 확인한다.

| 참조 | 체험 | 확인할 내용 |
|---|---|---|
| 체험1 | 호출·반환·오류 연결 선택 | 중앙에서 해당 구현으로 이동한다. 반환 관계를 호출자로 오인하지 않는다. |
| 체험2 | 관련 코드·함수 전체 펼치기 | 한 줄 설명과 실제 코드, 조건·호출 강조를 함께 확인한다. |
| 체험3 | 수정 전 코드 → 재고 부족 조건 추가 → 이전 코드 비교 | 같은 위치에서 전후 소스를 읽는다. |
| 체험4 | 읽는 동안 변경 도착 → 새 변경 적용 | 읽던 코드와 선택한 단계가 유지된다. |
| 체험5 | 분석 미완료 | 새 변경을 확인하지 못했음을 표시하고 이전 코드를 유지한다. |

최종 제품 방향은 **Static 화면을 유지하면서, 별도의 Live 화면 중앙에서 실제 코드의 호출·조건·변경을 연속해서 읽도록 하는 것**이다.
