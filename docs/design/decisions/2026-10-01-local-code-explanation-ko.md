# 로컬 코드 해설 설계 제안

- Status: Proposed
- Created: 2026-10-01
- Intent Status: Interviewing
- Parent: [로컬 코드 해설 스펙](../specs/2026-10-01-local-code-explanation-ko.md)
- Source: 사용자 인터뷰, 현재 코드 점검. 역할1·2·3과 현재 왼쪽 처리 구간·코드뷰 보존은 사용자 요청이다. SLM은 기존 구조의 Semantic Assistant다. 기술 정책은 아래의 제안이다.

## 결정1. 기존 읽기 대상의 의미를 해설한다

- 문제: 기존 라벨러는 제목·역할·조건만 읽으며, 실제 코드의 처리 의미를 충분히 설명하지 못한다.
- 제안: 코드 블록, 이미 구성된 처리 구간, 선택 문장의 조건과 결과를 각각 해설한다. 모델은 구간 소속·관계·분석 상태를 수정하지 않는다.
- 대안: 기존 관문 제목만 바꾸기, SLM에게 개요 구성을 맡기기, 메인 에이전트가 모든 세부 해설까지 수행하기.
- 이유: 사용자가 요청한 역할은 사람이 코드를 이해하기 쉬운 해석이다. 현재 개요·블록·상세의 선택 단위를 그대로 사용할 수 있다.
- 결과: 독립된 해설 데이터와 세 역할 출력 계약이 필요하다. 전체 흐름 추론이나 메인 에이전트용 새 API는 이번 범위에서 제외한다.
- 근거: 사용자 지시, `internal/curator/slm_labeler.go:115`, `RequestedFlowBlockPanel.svelte:9`.
- 적용: INT-01~03, GOAL-01~03, INV-01·05, FA-01~03.
- 후속: 질문1·5의 실행·평가 정책 확정.
- 상태: 역할 범위는 사용자 확인. 구체적인 표시·출력 정책은 Proposed.

## 결정2. 서버가 같은 View의 근거로 입력을 구성한다

- 문제: 기존 라벨 endpoint는 클라이언트 frames를 사용한다. 새 해설은 실제 소스와 주변 문맥이 필요하며 현재 파일을 읽으면 과거 분석과 섞일 수 있다.
- 제안: View·대상 ID만 받아 저장된 소스·문장·관계를 검증하고, 추가 문맥은 원래 snapshot에서 확보한다. 문맥과 실행 근거를 구별한다.
- 대안: 브라우저에서 보이는 소스만 전송, 최신 `/api/source` 조회, 모델의 자율 파일 탐색, 새로운 전체 소스 수집 엔진.
- 이유: 기존 저장 View·digest·정확한 문장 검증과 snapshot VFS를 재사용하면 분석 기준과 읽기 전용 경계를 보존할 수 있다.
- 결과: 해설 문맥 구성과 참조 매핑 기능이 필요하다. 정의·타입·callee 구현이 없을 때 부분 해설 또는 해설 불가를 제공한다. 추가 근거는 기존 화면으로 해당 소스 범위를 확인할 수 있을 때만 사용한다. 기존 경로가 없는 추가 문맥은 입력에서 제외한다. 별도 발췌 뷰·새 분석 단계·최신 파일 조회로 대체하지 않는다.
- 근거: `requested_flow_overview.go:36`, `flow_context.go:244`, `flow_context_source.go:105`, `workspace/vfs.go:115`.
- 적용: INV-02·03·07·08, FA-04·05·09.
- 후속: 질문3·4의 로컬 endpoint와 입력 제한, 추가 문맥의 언어별 확보 범위 확인.
- 상태: Proposed. 기존 snapshot·보안 불변식은 승계한다.

## 결정3. 해설을 원본과 분리하고 참조 검증과 의미 평가를 구별한다

- 문제: 유효한 코드 참조가 붙은 해설도 내용이 틀릴 수 있다. 기존 store는 모델 라벨을 frame.text에 적용한다.
- 제안: 내부 모델 해설 상태·응답 계약을 원본과 분리한다. 표시에는 기존 설명 지점만 사용하며 새 해설 영역을 추가하지 않는다. 구체적인 표시 매핑은 질문6으로 추적한다. 소속·소스 참조·응답 구조는 자동 검사하고 실제 의미와 한국어 이해는 고정 corpus와 사람 평가로 확인한다.
- 대안: 유효한 참조를 의미 검증 성공으로 표시, 원본 제목 덮어쓰기, mock 테스트만으로 기능 완료 판정.
- 이유: 확률적 제안을 코드 사실로 승격하지 않고 해설 전후를 실제 소스로 확인할 수 있어야 한다.
- 결과: 독립 해설 요청·취소·재사용 키, late response 검사, 모델 평가 산출물이 필요하다. 기존 라벨 API와 저장 데이터는 보존한다.
- 근거: `flowStore.svelte.ts:676`, `storage/views.go:109`, 기존 FlowView와 코드 블록 읽기 계약.
- 적용: INV-01·04~06·09·10, FA-06~08·10~12.
- 후속: 질문2의 영구 저장 여부, 질문4·5의 장비·상한·품질 기준.
- 상태: Proposed. 영구 저장은 아직 결정되지 않았다.

## 승인과 관련 미결정

이 기록은 기존 계약을 대체하거나 승인 상태를 바꾸지 않는다. 실행 시점, 저장, 활성화·로컬 경계, 실제 장비·상한과 품질 수용 조건을 부모 스펙의 질문1~6로 추적한다. 답변 전에는 제안을 Accepted로 바꾸지 않는다.

## 결정4. 현재 처리 구간과 코드뷰를 유지한다

- 상태: Accepted. 현재 사용자 지시로 확인된 제약이며 부모 스펙 전체의 승인은 아니다.
- 문제: 이전 초안은 코드 위 해설 영역과 중앙 추가 소스 발췌를 제안해 기존 화면·코드뷰 보존 요구와 충돌했다.
- 결정: SLM을 기존 구조의 Semantic Assistant로 둔다. 왼쪽 처리 구간의 탐색 역할과 코드뷰의 소스 확인 역할, 화면 배치·원문·강조·접기·선택·탐색을 유지한다.
- 대안: 새 해설 영역·패널 추가, 코드뷰를 해설 중심으로 변경, 별도 소스 발췌 뷰 추가. 사용자 요구와 충돌하므로 채택하지 않는다.
- 이유: 현재 왼쪽 처리 구간과 코드뷰의 역할이 이미 정립되어 있으며 사용자는 이 구조 안에서 의미 해석을 보조하기를 원한다.
- 결과: 별도 해설 영역·추가 발췌 뷰 제안을 철회한다. 기존 설명 지점의 적용 가능성은 질문6으로 확인하고, 표시할 수 없는 내용을 위해 화면을 확장하지 않는다.
- 근거: 2026-10-01 사용자 후속 지시.
- 적용: INV-05·06, FA-01~03·05·06. 세 역할의 의미 해석 범위는 유지하되 구체적인 표시 방식은 미확정이다.
- 후속: 질문6의 기존 설명 지점 매핑과 적용 전후 화면·코드뷰 대조 검증.
