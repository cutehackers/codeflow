# 요청 흐름 개요와 문장별 탐색 분리 결정

- Source: 2026-09-29 사용자 지시, 2026-09-18·21·23 계약, 현재 FlowView와 Molycard 로컬 분석 사례

## 결정1. 하나의 FlowView 안에서 읽기 목적을 분리한다

검증된 새 요청은 큰 처리 흐름의 개요를 먼저 연다. 사용자가 개요의 구간이나 코드 블록에서 기존 문장별 탐색으로 명시적으로 이동하고 돌아올 수 있게 한다. 문장별 탐색을 삭제하거나 기능을 축소하는 대안과 별도 FlowView 제품을 만드는 대안은 채택하지 않는다. 이 결정은 INV-04·06과 FA-01~03·05에 적용한다. 새 개요가 없는 과거 View는 기존 상세 탐색을 유지한다.

## 결정2. 처리 목적과 확인된 인과관계로 개요를 만든다

요청의 시작·주요 판단·처리 전환·결과 또는 경계에 근거하여 구간을 선정한다. 계층명, 문장 종류, 같은 파일, 고정 관문 수로 구간을 정하는 대안은 채택하지 않는다. 이는 `architecture`를 흐름 분류에 사용하지 않는 2026-09-21 계약과 일치한다. 의미 제목만으로 단계 소속이나 실행 관계를 확정하지 못한다. 이 결정은 INV-01·03·04와 FA-01·02·04·07에 적용한다.

## 결정3. 기존 분석과 저장 결과를 보호한다

개요는 기존 상세 분석 위에 검증된 참조를 가진 별도 버전 관리 결과로 둔다. 개요 생성 실패 시 300개 문장을 성공한 개요처럼 보여 주는 대안과 과거 View를 자동 재분석·덮어쓰는 대안은 채택하지 않는다. 기존 인증·secret redaction·snapshot 근거·명시적 재분석·비교 기준을 보존한다. 이 결정은 INV-01~06과 FA-03~06에 적용한다.

## 영향과 후속 확인

이 결정은 기존 2026-09-14·18 계약이 `FlowSequence`를 기본 개요로 설명한 부분과 **기본 화면 책임**에서 겹친다. 기존 문서나 VS의 상태를 바꾸지 않으며, 새 구현에서는 이 계약의 목적별 개요를 먼저 보여 주고 기존 `FlowSequence`·문장별 탐색을 상세 기능으로 유지한다. 새 공개 필드와 schema는 저장·HTTP·MCP 소비자를 조사한 뒤 호환 가능한 형태로 확정한다. 실제 사용자 이해와 성능은 출시 전에 별도 검증한다.
