## 결정1. 구현 소유자를 새 VS 세트로 통합한다

2026-09-21 VS-01은 완료 기록으로, VS-02·03은 구현 후 검토 기록으로 유지한다. 제안 상태의 2026-09-21 VS-04, 2026-09-23 코드 읽기 VS-01~06과 adapter 적합성 VS-01의 구현 범위는 새 부모의 VS-01~07로 교체한다. 이전 제안을 그대로 병렬 진행하면 CodeView·관계·요약의 완료 주체가 갈라진다. 기존 2026-09-18 승인 VS와 그 사용자 검증 조건은 유지한다. 영향을 받는 기준은 새 FA-01~08이다.

## 결정2. 언어별 사실과 공통 후속 처리를 구분한다

Dart·Go·TypeScript는 각각 해당 언어 도구로 문법, 심볼, 실제 문장 범위와 확인 가능한 직접 관계를 수집한다. 공통 Core는 같은 snapshot에 대한 소스·해시·참조 검증, 읽기 경로 선정, 저장·화면·MCP 의미를 맡는다. 단일 언어 독립 parser나 정규식만으로 모든 실행 의미를 증명하는 대안은 채택하지 않는다. 현재 payload는 간선의 AST 출처를 보편적으로 증명하지 못하므로, 언어별 소스 사례의 기대·금지 관계를 별도로 검사한다. 구현 부담은 완전히 사라지지 않지만 반복되는 후속 규칙과 품질 판정은 줄인다. INV-02·03·05와 FA-01·02·05~07에 적용한다.

## 결정3. 코드 표시를 제품 결과로 검증한다

소스 범위나 schema의 존재만으로 완료하지 않는다. 요청의 기본·상세 항목을 실제 제품 화면에서 선택해 같은 심볼과 문장이 열리는지 확인한다. 대표 코드가 열리지 않으면 기존 2026-09-21 계약에 따라 저장을 중단한다. 실패를 UI의 다른 코드나 파일 전체 fallback으로 숨기는 대안은 채택하지 않는다. INV-01·02·04와 FA-03·04·08에 적용한다.

## 결정4. 구현 완료와 출시 판정을 분리한다

이 VS 세트가 통과해도 실제 사용자 이해 과제와 대규모 입력 성능, 지원 범위, 대상 플랫폼 설치 검증은 남는다. 이를 같은 VS의 테스트 통과로 대체하지 않고 2026-09-18 계약의 출시 조건으로 유지한다. 새 FA-01~08과 §8에 적용한다.

## 후속 확인

사용자의 2026-09-23 통합 방향 지시에 따라 이 구현 방향을 채택한다. 개별 VS는 여전히 제안 상태이며 독립 검토와 사용자 승인이 필요하다. 새 protocol 필드나 저장 migration이 필요하면 그 영향 범위를 별도 기록으로 판단한다.
