# Requested Flow 중심 관문 구성과 표현 결정

- Source: 2026-09-18 사용자 대화. 중요도 점수만으로 빠른 이해를 보장할 근거가 없으며, 요청 흐름의 주요 처리와 계층별 결정 파악이 목적이라는 확인, 후속 인과관계 기준 수용 및 발견1~3 종합 반영 지시.

## 결정1. Requested Flow의 주요 처리와 인과관계를 관문 선정 기준으로 사용

- 맥락: 문장 종류나 역할 점수만으로 중요도를 정하면 사용자 질문에 필요한 판단이 숨겨진다.
- 결정: 시작 상황·알고 싶은 동작·확인하려는 결과를 요청에서 정리하고, 실행 여부·경로·상태·결과·인계를 설명하는 처리를 보존한다. 각 후보에 요청 관련성, 생략 시 놓치는 내용과 단계·관계 근거를 연결한다. curator가 판정하며 계층과 코드 출처는 강제 분류 기준이 아니다.
- 대안: 역할별 고정 점수, 계층별 한 관문, 모든 단계의 개별 카드.
- 이유: 세 대안 모두 요청의 핵심 결정과 관문이 일치함을 보장하지 못한다.
- 결과: 근거가 부족하면 보수적으로 분리하고 요약 한계를 표시한다. 판정은 코드 이해를 위한 인과관계에 한정하며 실제 실행 관측을 주장하지 않는다. framework 코드도 요청 결과에 필수라면 노출한다.
- 영향: INV-01·04·09, AC-01·02·12·15.
- 후속: 대표 실제 요청에서 필수 판단과 근거를 먼저 기록한다. 의미 추론의 품질은 코드 클릭 성공과 별도로 검증한다.

## 결정2. 4~7개를 참고 범위로 두고 양방향 의미 검토 수행

- 맥락: 서로 다른 필수 판단이 8개여도 7개로 줄이면 의미를 잃을 수 있다.
- 결정: 4~7개를 병합 목표로 사용하지 않는다. 합쳐도 필요한 구별이 남으면 병합하고, 핵심 판단이 숨겨졌으면 분리한다. 필수 판단 보존이 필요하면 7개 초과를 허용한다.
- 대안: 최대 7개 강제, 추가 관문을 기본 접근 불가능한 별도 목록으로 이동.
- 이유: 개수를 맞추는 것이 요청 흐름 이해보다 우선할 수 없다.
- 결과: 목록이 길어질 수 있으며 스크롤과 선택 유지가 필요하다. 불확실성 때문에 단계 나열이 남은 결과는 탐색 가능하지만 요약 성공으로 판정하지 않는다. 요약 한계와 코드 근거 상태를 분리해 보존한다. 기존 명세 §3.3·§8.4·AC-02·AC-07과 충돌한다.
- 영향: INV-11, AC-03·04·16·17. 기존 문서는 보존하며 채택 시 관련 수용 기준을 명시적으로 조정한다.
- 후속: 큰 흐름의 필수 판단 보존과 사용자의 탐색 결과를 함께 검증한다.

## 결정3. 공통 관문 결과를 생성·저장·표현 경로에서 공유

- 맥락: FlowView의 `SaveTaskView`와 MCP 압축 응답이 서로 다른 생성 알고리즘을 사용한다. 근거는 부모 명세 §3이다.
- 결정: curator의 동일 결과를 검증·저장·표현한다. 저장 시 별도 규칙으로 덮어쓰지 않는다.
- 대안: 각 출력에서 별도 큐레이션, 프런트엔드 재구성, 기존 `CurateMap` 단순 교체.
- 이유: 출력 불일치를 유지하거나 근거·식별자 손실을 유발한다.
- 결과: FlowID, 단계 관계, 검증 상태를 보존한 통합이 필요하다. 기존 저장 뷰는 소급 재작성하지 않는다.
- 영향: INV-02·03·05·07·08·10, AC-05·09·11·13.
- 후속: 실제 producer·consumer 및 저장 fixture를 확인한다. 공개·저장 형식 변경이 필요하면 별도 변경 결정을 먼저 기록한다.

## 결정4. 관문과 실행 단계의 선택·펼침 상태를 구분

- 맥락: 선택한 다단계 관문에서만 타임라인을 표시하면 포함 관계를 발견하기 어렵다.
- 결정: 모든 관문에 자식 수와 펼치기를 제공한다. 관문 선택은 대표 코드, 자식 선택은 부모 맥락을 유지한 해당 코드 선택이다.
- 대안: 선택 전 상세 존재 숨김, 자식마다 최상위 카드 생성, 관문 전환 때 펼침 초기화.
- 이유: 계층 발견과 코드 탐색의 연속성을 방해한다.
- 결과: 펼침과 코드 선택을 독립적으로 관리하며 코드 근거를 유지한다. 배치는 결정13에 따라 검증으로 선택한다.
- 영향: INV-06, AC-06·07·08·10.
- 후속: 마우스·키보드 조작, 다른 파일 자식, 접기 및 관계 탐색 복귀를 브라우저에서 검증한다.

## 결정5. 의미와 실제 사용자 경로를 함께 완료 기준으로 사용

- 맥락: 큐레이터 단위 테스트는 FlowView가 해당 큐레이터를 사용하는지 증명하지 못한다.
- 결정: 소스에서 독립적으로 정한 필수 판단 목록, API·저장·MCP 통합 검증, 실제 브라우저 탐색과 사용자 이해 검토를 수행한다.
- 대안: 카드 수와 버튼 클릭만 검증, 생성 결과를 그대로 기대값으로 사용.
- 이유: 기능 부분 동작과 제품 목적 달성을 혼동하게 된다.
- 결과: 테스트 통과와 사용자 이해·시간 개선 주장을 분리한다. 근거 없는 성능 수치는 도입하지 않는다.
- 영향: AC-01~AC-20와 부모 명세 §12.
- 후속: 구현 시 수용 기준별 실행 증거를 남긴다. 현재 문서 작성은 기능 구현 완료가 아니다.

## 결정6. 포함 관계와 실행 연결을 분리

- 맥락: 단일 부모 규칙만으로는 분기 이후 공통 처리, 반복과 비동기를 표현할 수 없다. 배열의 읽기 순서를 실행 순서로 오해할 수 있다.
- 결정: 단계는 하나의 부모에 소속하고 실행 연결은 별도로 보존한다. 공통 후속 처리는 한 번 소속시키고 복수 선행 연결을 표시한다. 관문 간 연결은 실제 단계 간 연결에서 도출한다.
- 대안: 공통 단계를 분기별로 복제, 한쪽 분기에만 배정, 모든 단계를 직렬 타임라인으로 표시.
- 이유: 실행 근거를 왜곡하거나 다른 경로에서 공통 처리로의 연결을 숨긴다.
- 결과: 내부·관문 간 분기와 합류를 구별한다. 경로 선택에도 다른 경로의 존재와 합류가 남는다. 비동기 대기는 확인된 관계만 표시하고 배타적 분기 합류와 혼동하지 않는다.
- 영향: INV-02·04·12, AC-18~20, 부모 명세 §6.2·§7.2·§7.3.
- 후속: 같은 심볼의 별도 호출과 공통 단계를 구별하는 사례, 내부 분기, 조건부 합류, 재시도와 비동기를 통합·브라우저 검증에 포함한다. 공개·저장 표현을 바꿔야 하면 호환성 계약을 먼저 확정한다.

## 결정7. 전체 관계와 상세 소속을 다른 영역에서 표현

맥락은 상단과 좌측의 중복 관문 표시다. 상단은 위에서 아래로 읽는 조건·합류·인계 관계, 좌측은 관문 안의 실행 단계로 정한다. 중앙은 코드와 요청 흐름 안의 전후 처리, 우측은 직접 호출 관계를 담당한다. 같은 상세 카드를 두 곳에 반복하거나 전체를 전역 호출 그래프로 확장하는 대안은 목적과 정보 밀도를 흐린다. 이 배치는 초기 비교안이며 후속 사용자 지시에 따라 고정하지 않는다. 정보 역할을 보존하면서 실제 복잡한 사례에서 더 잘 이해되는 배치·탐색을 선택한다. 영향은 UX-AC-01·02·03·06·10이다.

## 결정8. 조건 선택은 가능한 연결 강조

조건별 강조를 실제 실행 결과나 전체 조건의 실행 가능성으로 제시하지 않는다. 확인된 관계 범위만 계산하고 근거 부족 시 직접 연결로 범위를 명시한다. 중첩 조건과 합류를 보존하며 코드 선택과 강조를 분리한다. 조건 선택마다 코드를 강제 이동하거나 대안 경로를 삭제하는 방식은 원래 문맥을 잃게 한다. 필요한 관계 데이터의 전달 여부는 OPEN-UX-01에서 확인한다. 영향은 UX-AC-02~05다.

## 결정9. 탐색 상태를 분석 데이터와 분리

관문·단계·펼침·조건·패널별 읽기 위치·초점을 같은 뷰의 탐색 상태로 복원한다. 단일 문서 스크롤만 복원하는 대안은 독립 패널의 위치를 잃는다. 세션 사이 위치를 영구 저장하는 기능은 추가하지 않는다. 분석 bytes와 baseline은 기존 계약을 유지하고 자동 분석은 하지 않는다. 영향은 UX-AC-07·09·13이다.

## 결정10. 실패의 범위와 한계의 종류를 드러냄

요약 한계, 실행 연결 미확인, 소스 한계를 해당 영역에서 별도로 알린다. 모든 실패를 전면 모달이나 같은 partial 상태로 묶으면 사용자가 무엇을 신뢰하고 다음에 무엇을 할지 알 수 없다. 정상 코드 탐색을 유지하며 재시도·명시적 재분석을 제공한다. 표시 정보는 코드 근거 상태를 변경하지 않는다. 영향은 UX-AC-08·09다.

## 결정11. 복잡한 관계도에도 동등한 탐색 수단 제공

그래프와 텍스트 관계 목록에서 같은 조건·대상·근거에 접근한다. 키보드와 좁은 창에서도 선택·복귀 기능을 유지한다. zoom이나 hover만으로 정보를 제공하는 대안은 접근과 가독성을 제한한다. 반응형 임계점은 실제 겹침으로 검증하고 고정 화면 크기만으로 제품 품질을 선언하지 않는다. 영향은 UX-AC-10~12다.

## 결정12. 제품 품질은 실제 데이터와 사용자 과제로 검증

실제 분석 API, 저장·재조회, 브라우저 조작과 사용자 이해 검증을 모두 요구한다. 정적 시안·샘플 데이터·단위 테스트만으로 출시 가능하다고 판단하는 대안은 기존 생성 경로 단절을 다시 놓칠 수 있다. 오류 관계 표시와 잘못된 소스 이동 등은 출시 차단 결함으로 삼고, 성능 수치와 지원 범위는 OPEN-UX-02에서 측정 후 확정한다. 영향은 UX-AC-14·15와 명세 §12이다.

## 결정13. 흑백을 유지하고 이해도 기준으로 배치·탐색을 선택

- Status: Accepted for design direction. 후속 사용자가 흑백 테마 고수와 요청 흐름 인지를 위한 UX 대안 허용을 명시했다. 후속 사용자 지시로 구현도 진행한다. 별도 출시 승인 절차를 뜻하지 않는다.
- 맥락: 3열이나 상단 관계도를 고정하면 실제로 더 빠르고 정확한 이해를 돕는 UX를 배제할 수 있다.
- 결정: 흑백 테마와 근거·맥락 보존을 고정하고 배치·방향·점진적 공개·탐색 방식은 같은 과제로 비교한다. 오류·상태·코드 강조에도 유채색을 추가하지 않는다.
- 대안: 기존 배치 무조건 보존, 시각적 선호만으로 변경, 모든 대안을 제품 모드로 추가.
- 이유: 디자인 수단보다 요청한 흐름의 정확한 이해와 근거 접근이 우선이다.
- 결과: 정확성·누락·오해를 먼저 평가하고 이를 충족한 안의 시간·불필요한 이동을 비교한다. 기존 3열 보존 문구와의 차이는 부모 명세 §2.3에 명시한다.
- 영향: 부모 명세 §7.1·§7.7·§12, UX-AC-16·17.
